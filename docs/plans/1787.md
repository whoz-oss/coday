# #1787 — Have a better namespace selector

Ticket: https://github.com/whoz-oss/coday/issues/1787. GitHub issue, no Jira ticket, no comments, no linked ticket.
Work branch: `work/forge/1787-improve-namespace-selector`. Base and PR target: `workstream/forge/master` (forge workstream).
Type: **user story / improvement**. Both sides: a small backend part (namespace favorites) and the selector UI.

Ticket text:

> In the namespace selector we want to display the default namespace linked to the user but only the starred one then
> and by alpha order. User namespace should be first with a separator. We should be able to filter them.

## 1. Expected outcome

The namespace selector of the case shell shows the user's personal namespace first, then a separator, then only the
namespaces the user has starred, in alphabetical order. It has a filter field that searches all the namespaces the
user can reach, and a star toggle on each entry.

Today (observed): the selector lists **every** reachable namespace in server order (Neo4j order, effectively random).
There is no personal namespace first, no separator, no filter, and namespaces cannot be starred (favorites exist only
for cases). For a super-admin who sees every namespace, this list is long and unsorted.

### Interpretation of the ticket (architect decisions, flagged)

- **"default namespace linked to the user"** = the personal namespace created by `PersonalNamespaceProvisioner`,
  identified by the existing contract `externalId == "user:<user externalId>"`.
- **"only the starred one then"** = when the filter is empty, the list below the separator holds only the starred
  namespaces. A namespace is not lost because it is not starred: the filter searches **all** reachable namespaces, and
  each entry has a star toggle to add it to the short list.
- **Starring needs a backend**: there is no favorite on namespaces today. It is added on the same `[:WATCHES]` edge as
  case favorites (see §6).
- **Safety nets (derived)**, so that nobody is left with an empty or unusable selector:
  - the namespace currently open is always shown, even if it is not starred (otherwise the user could not see where they
    are);
  - when the user has **no** starred namespace at all, the list below the separator shows all namespaces,
    alphabetically (no regression for users who never star anything, and for installs without personal namespaces).

## 2. Acceptance criteria

From the ticket:

1. The personal namespace of the current user is the first entry of the selector.
2. A separator follows it, then the starred namespaces, sorted alphabetically (case and accent insensitive, numbers in
   numeric order: "ns 2" before "ns 10").
3. Non-starred namespaces are not listed while the filter is empty.
4. A filter field at the top of the selector filters the namespaces by name.

Derived by the architect:

5. With a filter typed, the selector lists every reachable namespace whose name matches (starred or not), the personal
   one still first and separated when it matches, the others alphabetically. No match shows "No namespace matches".
6. Each entry has a star toggle (filled when starred). Clicking it stars or unstars the namespace for the current user
   only, without selecting the namespace and without closing the menu. The change is applied at once (optimistic) and
   reverted with a message if the server refuses it. It persists across reloads.
7. The currently selected namespace is always visible in the unfiltered list, even when not starred.
8. When the user has starred nothing, the unfiltered list shows all namespaces alphabetically.
9. The separator is shown only when there is a personal entry **and** at least one entry below it.
10. Same behaviour in the three places the selector is rendered: expanded sidebar, compact rail, mobile top bar.
11. Opening the menu focuses the filter; closing it clears the filter; `Escape` closes it.
12. With no `?ns` in the URL, the shell opens the personal namespace if there is one, otherwise the first namespace
    (alphabetically) — instead of the first one in server order.
13. Unchanged: the "Configure <namespace>" entry at the bottom of the menu, `showNsPicker` rules, the Namespaces admin
    page (`/namespaces`), the factory-cockpit selectors.

## 4. Analysis (why it behaves like this today)

- `CaseShellComponent.namespaces` is `toSignal(namespaceController.listAllNamespace())`, passed as is to
  `ShellSidebarComponent` and `ShellTopbarMobileComponent`, which render `@for (ns of namespaces())` in three
  duplicated menus (`shell-sidebar.component.html`: expanded `.shell-sidebar__ns-menu` and compact
  `.shell-sidebar__compact-ns-menu`; `shell-topbar-mobile.component.html`: `.shell-topbar-mobile__ns-menu`). No sort, no
  grouping, no filter.
- `NamespaceController.listAll` returns `findAll()` / `findByIds()` unsorted, and `NamespaceListItem` carries no
  favorite nor personal flag.
- `FavoriteRepository`/`Neo4jFavoriteRepository.setFavorite` supports only `EntityType.CASE` (the `else` branch logs and
  returns false). Its Cypher guard requires a direct `[:ADMIN|MEMBER]` edge, which does not fit namespaces: a
  super-admin reads every namespace without any direct edge.
- The auto-select effect of `CaseShellComponent` picks `nsList[0]`, i.e. server order.

## 6. Backend — scoped change

### 6.1 Storage: `(u:User)-[:WATCHES {favorite}]->(n:Namespace)`

Same edge type and property as case favorites, so one model of per-user state. **Guard differs from cases**: the right
to star a namespace is the right to READ it, checked by `@PreAuthorize` on the endpoint (covers super-admins, who have
no direct edge). The Cypher only requires both nodes to exist.

`NamespaceNodeNeo4jRepository.kt`, add:

```kotlin
@Query($$"""MATCH (u:User {id: $userId}), (n:Namespace {id: $namespaceId})
    WHERE n.removed IS NULL OR n.removed = false
    MERGE (u)-[s:WATCHES]->(n) SET s.favorite = true RETURN count(n)""")
fun mergeFavorite(@Param("userId") userId: String, @Param("namespaceId") namespaceId: String): Long

@Query($$"""MATCH (u:User {id: $userId}), (n:Namespace {id: $namespaceId})
    OPTIONAL MATCH (u)-[s:WATCHES]->(n)
    FOREACH (rel IN CASE WHEN s IS NOT NULL THEN [s] ELSE [] END | SET rel.favorite = false)
    RETURN count(n)""")
fun clearFavorite(@Param("userId") userId: String, @Param("namespaceId") namespaceId: String): Long

@Transactional(readOnly = true)
@Query($$"""MATCH (:User {id: $userId})-[s:WATCHES]->(n:Namespace)
    WHERE s.favorite = true AND (n.removed IS NULL OR n.removed = false)
    RETURN n.id""")
fun findFavoriteIds(@Param("userId") userId: String): List<String>
```

(Import `org.springframework.data.repository.query.Param` and `org.springframework.transaction.annotation.Transactional`
as in `CaseNodeNeo4jRepository`.) No migration needed: absence of the edge means "not starred".

```kotlin
@ResponseStatus(HttpStatus.OK)
@PreAuthorize("hasPermission(#id, 'Namespace', 'READ')")
override fun starNamespace(@PathVariable id: UUID) = setFavorite(id, true)

@DeleteMapping("/{id}/star")
@ResponseStatus(HttpStatus.NO_CONTENT)
@PreAuthorize("hasPermission(#id, 'Namespace', 'READ')")

        throw ResourceNotFoundException("Namespace not found: $id")
    }
}
```

## 7. Frontend — scoped change

Principle: one presentational menu component replaces the three duplicated menus; the shell (smart) owns the data and
the star mutation; the ordering/filtering rule is a pure function, unit tested on its own.

### 7.1 New pure rule `case-shell/namespace-menu/namespace-menu.ts`

```ts
export interface NamespaceMenuModel {
  personal: NamespaceListItem | null   // shown first, then the separator
  others: NamespaceListItem[]          // alphabetical
}
export function buildNamespaceMenu(
  namespaces: readonly NamespaceListItem[],
  query: string,
  selectedId: string | null
): NamespaceMenuModel
export const compareNamespaceNames = (a, b) =>
  a.name.localeCompare(b.name, undefined, { sensitivity: 'base', numeric: true })
```

Rules:

1. `personal` = the first item with `personal === true` (null if none).
2. Filter: `query.trim()` non-empty → keep items whose name contains the query, compared after
   `normalize('NFD').replace(/\p{Diacritic}/gu, '').toLowerCase()` on both sides. `personal` is null when it does not
   match. `others` = all other matches.
3. Empty query → `others` = items with `favorite === true` plus the item whose id is `selectedId` (if not personal),
   without duplicates. **If no item at all is starred**, `others` = all non-personal items.
4. `others` sorted with `compareNamespaceNames`; never contains the personal item.

- New handler, mirroring `onStarToggled`:

```ts
protected onNamespaceStarToggled(event: { id: string; starred: boolean }): void {
  const patch = (favorite: boolean) =>
    this.namespaces.update((list) => list.map((ns) => (ns.id === event.id ? { ...ns, favorite } : ns)))
  patch(event.starred)
  const request = event.starred
    ? this.namespaceController.starNamespace(event.id)
    : this.namespaceController.unstarNamespace(event.id)
  request.pipe(takeUntilDestroyed(this.destroyRef)).subscribe({
    error: (err) => {
      patch(!event.starred)
      console.error(`[CaseShell] Failed to update star for namespace ${event.id}:`, err)
      alert('Could not update the favorite namespace. Please try again.')
    },
  })
}
```

## 8. Contract between frontend and backend

| Call | Request | Response | Errors |
|---|---|---|---|
| `GET /api/namespaces` | — | `NamespaceListItem[]`, each with new `favorite: boolean` (caller's star) and `personal: boolean` (`externalId == "user:" + caller.externalId`) | unchanged |
| `PUT /api/namespaces/{id}/star` | no body | `200`, empty | `403` without READ on the namespace, `404` unknown/removed namespace |
| `DELETE /api/namespaces/{id}/star` | no body | `204` | same as above |

Idempotent: starring twice or unstarring a non-starred namespace succeeds. Generated client methods:
`NamespaceControllerService.starNamespace(id)` / `unstarNamespace(id)` (operation ids follow the existing
`<method>Namespace` naming of the generator; if the generator names them differently, use the generated names).
