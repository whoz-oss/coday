# Implementation plan — #1744 Unified skill-equipped `Builder` agent

Ticket: https://github.com/whoz-oss/coday/issues/1744 (GitHub issue, type: enhancement / user story — not a bug)
Work branch: `work/forge/1744-builder-agent` (from `workstream/forge/master` @ `44e4740`)
PR target: `workstream/forge/master`

## 1. Expected outcome

A single `Builder` agent, defined in `agents/Builder.yaml`, carries the universal engineering posture and the
implementation integrations, and loads the stack-specific knowledge (Angular/design system, AgentOS
Kotlin backend, Coday TypeScript/Nx) on demand from three filesystem AgentOS Skills under `skills/<name>/SKILL.md`,
so that a Factory implementation step can target `Builder` whatever the stack.

## 2. Acceptance criteria

From the ticket:

- **AC1** Domain-specific instructions and reference pointers from `Frontay`, `Dev` and `Sway` are extracted into
  modular AgentOS Skills (`SKILL.md` + optional resources).
- **AC2** A unified `Builder` agent configuration (`agents/Builder.yaml`) is created with universal engineering
  instructions, the required integrations (`FILES`, `GIT`, `GITHUB`, `FACTORY_WORKER`, `CHROME`, `FETCH`, `MEMORY`,
  `AI`) and `skillSelectors` enabled for the technical skills.
- **AC3** Existing Factory workflow definitions can assign implementation steps to `Builder` without requiring a
  front/back split.

Derived by the architect (flagged **[derived]**):

- **AC4 [derived]** Each skill is discoverable by AgentOS: valid frontmatter (`name`, `description`, non-blank), name
  matching `^[a-zA-Z0-9_.-]+( [a-zA-Z0-9_.-]+)*$`, flat layout `skills/<name>/SKILL.md`, file < 512 KiB.
  `GET /api/skills/effective?namespaceId=<coday ns>` lists the three skills.
- **AC5 [derived]** `Builder` does **not** inject the stack docs permanently: its `docs` list holds only what is
  universal (the dev workflow); stack documents are reached through the skills.
- **AC6 [derived]** `Frontay`, `Dev` and `Sway` stay untouched and usable (PM delegates to them, existing registered
  workflows reference role names). Their retirement is a separate ticket.
- **AC7 [derived]** `skillSelectors` lists the three skills by exact name (not `"*"`), so that adding an unrelated
  skill to the namespace later never silently widens Builder's catalogue (design decision 1 of
  `docs/study/agentos-skills.md`).

## 4. Key files (read-only analysis)

Runtime mechanism (unchanged by this ticket):

- `agentos/agentos-service/src/main/kotlin/io/whozoss/agentos/agentConfig/FilesystemAgentConfigRepository.kt` —
  loads `<configPath>/agents/*.yaml`. Reads `name, description, instructions, modelName, integrations, subAgents,
  docs, skillSelectors, ...`. **`mandatoryDocs` is ignored** by AgentOS; only `docs` (resolved relative to the YAML
  file, hence the `../` prefix in existing agents) is injected, by `AgentDocumentResolver.kt`.
- `agentos/agentos-service/src/main/kotlin/io/whozoss/agentos/skill/FilesystemSkillRepository.kt` — discovers
  `<configPath>/skills/<name>/SKILL.md` (flat, `MAX_WALK_DEPTH = 2`, 5 min cache). The Coday namespace configPath is
  the repo root (it contains `agents/` and `integrations/`), so skills go in **`skills/`** at the repo root.
- `.../skill/SkillFileParser.kt` — frontmatter rules, name regex, 512 KiB limit, sibling files loaded as resources
  (symlinks and files outside the skill directory are rejected, so a skill cannot embed repo docs by link).
- `.../skill/SkillServiceImpl.kt` (`findSkills`: exact, case-insensitive name match or `*`),
  `SkillCatalogRenderer.kt` (injects name + description only), `SkillToolGrantService.kt` (grants `readSkill` /
  `readSkillResource` when the catalogue is non-empty).

Agents to extract from (not modified):

- `agents/Frontay.yaml` — component architecture rules (small/focused, smart/dumb, composition, `@Input`/`@Output`
  contract), working method; docs: `apps/client/docs/*`, `libs/`, `libs/design-system/GUIDELINES.md`,
  `libs/agentos-ui/GUIDELINES.md`, `libs/agentos-api-client/GUIDELINES.md`.
- `agents/Dev.yaml` — `agentos/` domain: Kotlin, Spring Boot 3, Spring AI, Gradle composite builds, PF4J, SDK/service
  split, entity framework, OpenAPI client pipeline; docs: `agentos/README.md`, `agentos/agentos-sdk/README.md`,
  `agentos/docs/*`.
- `agents/Sway.yaml` — business-to-code posture; docs: `docs/to-rework/ARCHITECTURE.md`,
  `docs/to-rework/HANDLER_DESIGN.md`; CHROME tool allowlist.
- Common to the three: `docs/to-rework/DEV_WORKFLOW.md`, restrictions (no extra markdown docs unless asked, tests only
  in established patterns, never fake test runs), working alone.

## 5. Scoped change, file by file

All changes are **configuration and markdown only**. No Kotlin, TypeScript, Angular or test source is modified.

### 5.1 `skills/angular-frontend/SKILL.md` (new)

Frontmatter:
```yaml
name: angular-frontend
description: Angular client and AgentOS UI work in apps/client and libs (components, services, styles, design system tokens, agentos-ui and agentos-api-client). Read before changing any browser-side code.
```
Body, extracted from `Frontay.yaml`: scope (`apps/client`, `apps/factory-cockpit` if Angular, `libs/agentos-ui`,
`libs/design-system`, `libs/agentos-api-client`), component architecture rules (small and focused, smart/dumb,
composition over inheritance, explicit `@Input()`/`@Output()` naming, no DOM-clashing outputs), API vs State service
separation (components never call API services), tokens over hardcoded styles, "do not invent backend APIs: describe
the contract you need", generated API client is never edited by hand. A **"Read before coding"** section lists the
repo paths to open with `FILES` according to the task: `apps/client/docs/angular-guidelines.md`,
`apps/client/docs/architecture.md`, `apps/client/docs/entity-crud-pattern.md`, `libs/design-system/GUIDELINES.md`,
`libs/agentos-ui/GUIDELINES.md`, `libs/agentos-api-client/GUIDELINES.md`. Verification commands: `pnpm nx lint|test
<project>`, `pnpm nx affected -t lint test`.

### 5.2 `skills/agentos-backend/SKILL.md` (new)

Frontmatter:
```yaml
name: agentos-backend
description: AgentOS backend work in agentos/ (Kotlin, Spring Boot 3, Spring AI, Spring Data Neo4j, PF4J plugins, Gradle composite build, OpenAPI generation). Read before changing any Kotlin or AgentOS service code.
```
Body, extracted from `Dev.yaml`: scope (`agentos/`; never `apps/` or `libs/` under this skill), SDK vs service module
boundary, entity framework and hybrid Neo4j-primary / filesystem-secondary repositories (decorator pattern), PF4J
plugin contract, OpenAPI → generated TypeScript client pipeline (regenerate, never hand-edit), Kotlin/Kotest test
conventions, the KDoc "no slash-star" trap. "Read before coding" pointers: `agentos/README.md`,
`agentos/agentos-sdk/README.md`, `agentos/docs/architecture.md`, `agentos/docs/code-style.md`,
`agentos/docs/testing.md`, `agentos/docs/entity-framework.md`, `agentos/docs/neo4j-persistence.md`,
`agentos/docs/plugin-system.md`, `agentos/docs/openapi-and-client.md`. Verification: the `GRADLE` /
`PROJECT_SCRIPTS` tools (`:agentos-service:test --tests ...`).

### 5.3 `skills/coday-typescript/SKILL.md` (new)

Frontmatter:
```yaml
name: coday-typescript
description: Coday TypeScript runtime and Express server work in libs/ and apps/server (handler design, Nx library boundaries, TypeScript conventions). Read before changing non-Angular TypeScript code.
```
Body, extracted from `Sway.yaml` and its docs: Nx monorepo layout and library boundaries, handler patterns (nested
handlers, add→edit delegation, `parseArgs`), server route/service layering, the fact that `apps/server` is a prototype
to be replaced by AgentOS (keep changes minimal there). Pointers: `docs/to-rework/ARCHITECTURE.md`,
`docs/to-rework/HANDLER_DESIGN.md`, `apps/client/docs/nx-tasks.md`.

No resource files are needed in this first iteration: the skills point at the living repo docs instead of copying
them (no duplication, no drift). Resources can be added later if a skill must work outside this repository.

### 5.4 `agents/Builder.yaml` (new)

```yaml
name: Builder
description: Implementation agent for any stack of the repository (Angular, AgentOS Kotlin, Coday TypeScript), loading stack knowledge on demand through skills
modelName: BIG
integrations:
  FACTORY_WORKER:
  FILES:
  GIT:
  GITHUB:
    - gh
  FETCH:
  AI:
  MEMORY:
  CHROME:            # same allowlist as Sway.yaml (navigate/snapshot/click/fill/wait...)
  GRADLE:            # only if the integration exists in the namespace; harmless otherwise
  PROJECT_SCRIPTS:
skillSelectors:
  - angular-frontend
  - agentos-backend
  - coday-typescript
instructions: |
  <universal posture, see below>
docs:
  - ../docs/to-rework/DEV_WORKFLOW.md
```

Instructions (universal posture, merged from the three agents, no stack content): read the step brief and the
architect plan (`docs/plans/<KEY>.md`) first; identify which areas the change touches and call `readSkill` for **each**
matching skill before editing (several for a cross-stack change); read existing code before writing; strictly respect
the assigned scope, no opportunistic refactoring, note out-of-scope ideas as suggestions; follow established test
patterns, never fake a test run, say plainly what could not be verified; work alone, do not delegate; commit only
scoped files with the conventional message, push without force; submit the Factory result through `FACTORY_WORKER`
only when done (attemptId / Idempotency-Key from the brief). Restriction: no new markdown docs unless asked.

Notes for the implementer:
- `mandatoryDocs` is deliberately **not** used: AgentOS ignores it (Coday-only key), `docs` is the effective one.
- `GRADLE` and `PROJECT_SCRIPTS` are optional additions to the ticket's list; keep them only if the namespace exposes
  them (`integrations/PROJECT_SCRIPTS.yaml` exists in the repo; GRADLE is a namespace integration). If unsure, keep
  exactly the ticket's list.
- No `subAgents`.

## 7. Verification criteria

No application code changes, so no new unit test is required; adding a spec that parses the repository's own
`skills/` directory would couple service tests to repository content and is not recommended.

Checks to perform:
1. Static: each `SKILL.md` starts with `---` frontmatter, `name` matches the directory and the regex, description
   non-blank and ≤ 500 chars; `agents/Builder.yaml` is valid YAML (parse it, e.g. `node -e` with `yaml` or any YAML
   linter) and every `docs` path resolves from `agents/`.
2. Every path cited in the skills' "Read before coding" sections exists in the repo.
3. Runtime (when an AgentOS stack is available): `GET /api/skills/effective?namespaceId=<ns>` lists the 3 skills;
   `Builder` appears in the namespace agents with `skillSelectors` populated; in a Builder case the system prompt
   contains the "Available Skills" catalogue and `readSkill("agentos-backend")` returns the body.
4. Existing tests that must stay green (unaffected, run only if convenient):
   `FilesystemAgentConfigRepositoryUnitSpec`, `AgentDocumentResolverUnitSpec`, skill specs under
   `agentos/agentos-service/src/test/kotlin/io/whozoss/agentos/skill/`.
5. Neighbouring behaviour: `Frontay`, `Dev`, `Sway`, `PM` still load unchanged; no other agent gains skills (none has
   `skillSelectors`).

**Risk level: low.** Additive configuration only; the only runtime effect is a new agent and three new namespace
skills (5-minute discovery cache). Rollback = delete the four files.
