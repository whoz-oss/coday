# WZ-36374 — Step FAIL with `outcomeTransitions.fail: return` must not surface the run as FAILED

Jira: https://whoz.atlassian.net/browse/WZ-36374 (Bug, parent epic WZ-36044 "FP - Forge - Feb 2027")
Work branch: `work/forge/WZ-36374-return-fail-keeps-run-active` → base `workstream/forge/master`
Sides: **frontend** (factory-cockpit, primary) + **backend** (factory-service, small)

## 1. Expected outcome

When an agent step submits an accepted FAIL and its `outcomeTransitions.fail` is `return` with budget left,
the run keeps showing RUNNING/active, the failed attempt stays visible with its FAIL verdict, and the replayed
region shows as pending/ready (never failed or blocked). Only an exhausted budget (or `block` / no return)
stops the run (waiting for a human).

- **Observed**: during the correction cycle the cockpit shows the run as FAILED (or flips between FAILED and
  RUNNING), replayed steps that already ran show as failed, and the rejecting step shows as blocked.
- **Expected**: run RUNNING / queued, replayed steps pending/ready, the rejected attempt FAIL only in the
  attempt history.
- **Reproduction steps**: complete (4 steps in the ticket). They can be replayed with unit fixtures (see §6).

## 2. Acceptance criteria

From the ticket:

- AC1: FAIL on a step with `fail.return` and budget left keeps the run RUNNING (ACTIVE), never FAILED.
- AC2: the failed attempt stays in the attempt history with its FAIL verdict and findings.
- AC3: replayed steps reset to READY/PENDING with no conflicting status in the cockpit.
- AC4: when `maxCycles` is used up, the return is not taken and the run stops (waiting for a human).

Derived by Archay (needed to check the ACs):

- AC5 (derived): workflows that do not use outcome transitions (legacy, no `stepExecutions`) keep their current
  status rendering, including "failed code verification ⇒ run failed" (`code-evidence.spec.ts`).
- AC6 (derived): a technical failure (AGENT_INDETERMINATE, runtime error) on a step with `fail.return` still ends
  as FAILED once the session ends. The backend already does this; the cockpit must keep showing it.

## 4. Analysis and root cause

### What the backend already does correctly

- `SessionRunService.persistProgressProjection`
  (`factory/factory-service/src/main/kotlin/io/whozoss/factory/workflow/service/SessionRunService.kt`):
  `progress.executions.isNotEmpty() && any FAILED -> RUNNING`. A configured failure never publishes FAILED
  while the router has not decided.
- `OutcomeTransitionService.advance`
  (`factory/factory-service/src/main/kotlin/io/whozoss/factory/workflow/service/OutcomeTransitionService.kt`):
  - marks the triggering execution FAILED in `stepExecutions` (AC2, attempt kept),
  - appends new PENDING executions for the whole replay region,
  - resets the step states and projected steps to PENDING with the new `executionId`,
  - sets projection status `READY`,
  - when the budget is used up: `correction.status = waiting_human` and a `correction_exhausted` interaction
    (AC4).
- Each `session-step` evidence carries `facts.executionId` (`SessionRunService.recordStepEvidence`), and each
  projected step carries its current `executionId`.

### Root cause (cockpit): evidence from the previous execution overrides the reset steps

File `apps/factory-cockpit/src/app/core/mappers/workflow.ts`, function `mergeCodeEvidenceIntoSteps`, called on
the first lines of `mapProjectionToSessionDetail`:

1. It keeps, per `stepId`, the **latest** `session-step` / `code-verification` evidence that has timing facts,
   **without looking at `facts.executionId`**.
2. When the projected step is `pending` or `ready` (exactly the state `advance` sets for the replay region), it
   replaces the status with an `evidenceStatus` computed from that evidence:
   `recordedStatus === 'running' ? 'running' : recordedStatus === 'needs_research' ? 'waiting_human' :
   exitCode === 0 && !timedOut ? 'completed' : 'failed'`.
3. Agent `session-step` evidence has no `exitCode`. So:
   - every replayed step that **completed** in cycle N-1 (for example tech-assessment, implementation) maps to
     **`failed`**,
   - the rejecting step (code-review, recorded `failed`) maps to `failed`.
4. Then `derivedStatus = mapWorkflowStateToRunStatus(undefined, steps)` → `deriveStatusFromSteps` → `'failed'`,
   and
   `status = isActivelyRunning || waitingHuman ? 'running' : derivedStatus === 'failed' ? 'failed' : projectedStatus`
   overrides the backend status (`ready`/`running`) with **FAILED** every time no step is running: between two
   steps, before the target is claimed, or after a reload. While a step is running, the run is RUNNING but the
   step list and timeline show red failed steps. This is the RUNNING/FAILED flip-flop in the ticket.
   `mapSessionDetailToRunSummary` copies `detail.status` onto the run card (`cardState = 'failed'`).

Proof by reading the code: the replay region states are set to PENDING by `advance`, the previous execution's
`session-step` evidence is still in the evidence log (append-only), and the merge has no execution filter.
A fixture in §6 reproduces it with no running step.

### Contributing factor (backend): stale attempt blocker

`WorkflowService.workflowActions`
(`factory/factory-service/src/main/kotlin/io/whozoss/factory/workflow/service/WorkflowService.kt`), attempts loop:
for each step's **latest** attempt, `AgentAttemptStatus.FAILED → blocker(ATTEMPT_FAILED, stepId)`. The new
correction attempt is only created when the step is claimed again (`CapabilityExecutionService.prepareCorrectionAttempt`).
So for the whole replay (tech-assessment → … → code-review), the latest attempt of code-review is still the
rejected FAILED one, and an `ATTEMPT_FAILED` blocker is published for a step that is now `pending`. In the
cockpit, `blockedStepIds` marks that step `blocked` (`mapStepsToSessionSteps`) and the run card becomes
`cardState = 'blocked'`, and the blockers bar shows a "Root failure". This breaks AC3.

### Residual window (cockpit)

Between `finalizeStep` (step FAILED) and the next `advance` call (same thread, under a second), the projected
step is `failed` while the backend projection status is `running`. The `derivedStatus` override shows FAILED for
that moment. For an outcome-managed run, the backend projection status is the authority and must win while it
is not `failed` (AC1). AC6 stays true: at the end of the session `persistProjection` writes the terminal
`failed` and the cockpit shows it.

## 5. Scoped change

No opportunistic refactoring. No API shape change: the fields used already exist.

### Backend — `factory/factory-service/src/main/kotlin/io/whozoss/factory/workflow/service/WorkflowService.kt`

In `workflowActions`, attempts loop (`when (attempt.status)`), branches `FAILED` and `INDETERMINATE`
(not `AGENT_NEEDS_RESEARCH`):

- When the run is outcome-managed (`governedInstance?.projection?.containsKey("stepExecutions") == true`) and
  the attempt is **not bound to the step's current execution**, do not emit the attempt-derived blocker.
- "Bound" means: `AttemptContextEnvelope.fromJson(attempt.contextEnvelope).inputs["stepExecutionId"]` equals the
  `executionId` of the projected step (`steps` list already loaded in this method, key `executionId`). This is
  the same binding rule as `OutcomeTransitionService.advance` (`pinnedExecution`).
- If the attempt has no envelope or the step has no `executionId`, keep the current behaviour (legacy).
- Do not touch: `CANCEL_ATTEMPT` (still only for non-terminal latest attempts), the step-status `FAILED` branch
  (a step really failed in the current execution keeps its blocker), legacy runs.

### Frontend — `apps/factory-cockpit/src/app/core/mappers/workflow.ts`

1. `mergeCodeEvidenceIntoSteps(steps, evidenceItems)`:
   - first index the current `executionId` of each projected step (`getString(step, 'executionId')`);
   - while building `latestByStep`, **skip** an evidence item when the step has a current `executionId`, the
     evidence has `facts.executionId` (or top-level `executionId`), and the two differ. That evidence belongs to
     a previous execution.
   - Evidence without `executionId` and steps without `executionId` keep the current behaviour (AC5).
   - Do not change the `evidenceStatus` mapping itself (out of scope, see §8).
2. `mapProjectionToSessionDetail`, computation of `status`:
   - `const outcomeManaged = stepExecutions.length > 0`;
   - the `derivedStatus === 'failed'` override applies only when
     `!outcomeManaged || projectedStatus === 'failed'`. Otherwise use `projectedStatus`.
   - `executionState` and `mapSessionDetailToRunSummary` follow automatically (they read `status`).
   - `waitingHuman` (correction `waiting_human`, AC4) keeps priority: unchanged.

Nothing else changes: `timeline.ts`, `step-classification.ts` and the components stay as they are. The step list
already reads the projected (reset) status once the merge stops overriding it. The timeline already shows each
ledger execution with its own status (`timelineSteps` → `executionSteps`), so the FAIL attempt stays visible
(AC2).

### Contract between the sides

No new field. The two sides rely on fields that already exist:

- `projection.steps[].executionId: string` (current execution, written by `persistProgressProjection`,
  `persistProjection` and `OutcomeTransitionService.advance`);
- `projection.stepExecutions[]` (ledger, its presence means "outcome-managed");
- `projection.status` (`running` / `ready` / `waiting_human` / `failed` / `completed`);
- `evidence.items[].facts.executionId` (session-step, code-verification, agent-result);
- `GET .../actions` → `blockers[]` (codes unchanged; only fewer stale `ATTEMPT_FAILED` entries).

Implementation order: backend first (`WorkflowService` + test), then frontend (mapper + tests). The two are
independent and can be merged in one PR.

### Risk level: **medium**

The status mapper drives every run card and session view. Both changes are guarded by the presence of
`executionId` / `stepExecutions`, so legacy runs keep their exact behaviour. The backend change only removes a
blocker in a precise case (outcome-managed + attempt bound to an older execution).
