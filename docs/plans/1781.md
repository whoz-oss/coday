# #1781 — Workstream Build must not publish to npm when builds are failing

Ticket: https://github.com/whoz-oss/coday/issues/1781. It is a GitHub issue with an empty description, no comments and no linked Jira ticket.
Work branch: `work/forge/1781-gate-npm-publish-on-build`. Base and PR target: `workstream/forge/master`.
Type: **bug** (CI / release pipeline).

## 1. Expected outcome

When any npm package of the release set fails to build, `workstream-build.yml` publishes **no** npm package and moves **no** `workstream-<slug>` dist-tag. The job fails loudly, before the first `npm publish`.

- **Observed:** the `publish-npm` job builds each package *inside* `releasePublish`, through `nx-release-publish.dependsOn: ["build"]`, and publishes each one as soon as its own build ends. When one build fails, the others are already on npm, so the set on npm is partial and incoherent.
- **Expected:** all builds run first. Publishing starts only when every build has succeeded. If one fails, nothing is published.
- **Reproduction:** complete, from CI history (see §3). Builds failed and npm still received part of the set.

## 2. Acceptance criteria

Derived by the architect, since the ticket body is empty:

1. In `publish-npm`, every npm package of the release set that has a `build` target is built **before** any package is published.
2. If any of these builds fails, the script exits non-zero and **no** package is published: no tarball reaches npm and no dist-tag moves.
3. If every build succeeds, the publish behaves as today: the same four packages (`coday-client`, `coday-factory-cockpit`, `coday-server`, `coday-web`), the same exact version, the dist-tag `workstream-<slug>`, OIDC provenance, and `workspace:*` replaced in the tarballs.
4. The packages built are the ones that get published. The version stamp happens *before* the build, because each `build` copies `package.json` into `dist`, so the built tarballs carry `0.0.0-workstream-<slug>.<n>`.
5. The master release path (`scripts/release.ts`, `release.yml`) does not change.
6. The existing job gating stays as it is: JVM build or publish failure → `prerelease` skipped → `publish-npm` skipped. This already holds today and must not regress.

## 4. Root cause (single)

The cause is in `scripts/utils/release-steps.ts`, `publishPackages()`, which calls `releasePublish({ … })`, together with the targets in each `project.json`:

- `apps/client/project.json`, `apps/server/project.json` and `apps/factory-cockpit/project.json` declare `"nx-release-publish": { "dependsOn": ["build"] }`.
- `apps/web/project.json` declares `"nx-release-publish": { "dependsOn": [] }`, so it does not depend on any build.

`releasePublish` runs the `nx-release-publish` task graph with Nx's normal task scheduler. Each publish task waits only for **its own** `build`. Nothing links one project's publish to the other projects' builds, and `coday-web` waits for nothing. When the Angular build of `client` fails, `web`, `server` and `factory-cockpit` have already been published, possibly in parallel. Nx then reports the failure and `publishPackages` exits 1, but too late: npm versions are immutable and the dist-tag has already moved for the packages that were published.

The job-level `needs:` in `.github/workflows/workstream-build.yml` cannot prevent this, because the npm builds do not run in any earlier job. They only exist inside the publish call.

## 6. Scoped change (backend / CI side only)

Principle: **build everything, then publish everything.** The build is an explicit, all-or-nothing step placed between the stamp and the publish, inside the same script. The stamp has to come first (see AC4), and the in-memory `releaseGraph` / `projectsVersionData` returned by `stampVersion` are what `releasePublish` needs. For these two reasons the build cannot become a separate workflow step without restamping.

### 6.1 `scripts/utils/build-npm-packages.ts` (new, pure, no `nx` import)

```ts
export const NPM_BUILD_COMMAND =
  'pnpm nx run-many -t build --projects=tag:platform:npm --exclude=tag:desktop-bundle --outputStyle=static'

export type Exec = (command: string) => void   // must throw on non-zero exit

/** Builds every publishable npm package. Throws if ANY build fails, so the caller publishes nothing. */
export function buildNpmPackages(exec: Exec): void {
  console.log(`Building npm packages before any publish: ${NPM_BUILD_COMMAND}`)
  exec(NPM_BUILD_COMMAND)
}
```

- The selector `tag:platform:npm` minus `tag:desktop-bundle` gives `client`, `factory-cockpit` and `server` (`web` has no `build` target and is skipped by `run-many`). `desktop` is excluded because its `nx-release-publish` is a no-op and its build is useless here. Use the tag selector, not a hard-coded list, so that a new `platform:npm` package is built automatically.
- `nx run-many` exits non-zero as soon as any task fails. That is the whole gate.
- `exec` is injected so the spec can test it without spawning anything. The production caller passes `(cmd) => execSync(cmd, { stdio: 'inherit' })`, and `execSync` throws on a non-zero exit.

### 6.2 `scripts/utils/release-steps.ts`

Add an **optional** last parameter to `publishPackages`: `options: { excludeTaskDependencies?: boolean } = {}`, and forward `excludeTaskDependencies: options.excludeTaskDependencies ?? false` to `releasePublish`. The default `false` keeps master (`scripts/release.ts`) byte-for-byte the same in behaviour (AC5). Update the JSDoc.

*Builder check:* confirm that `releasePublish` in the installed nx accepts `excludeTaskDependencies` (look in `node_modules/nx/dist/src/command-line/release/command-object.d.ts`, `PublishOptions`). If it does not, **leave `publishPackages` unchanged**. The gate in 6.3 is still correct, and the only cost is that the `dependsOn: build` of each publish rebuilds the already-built packages, a deterministic second build that is merely slower. Write down which path you took in the PR.

### 6.3 `scripts/workstream-release.ts`

In `main()`, insert step 2 between the current steps 1 and 2:

1. `stampVersion(version, dryRun)` (unchanged).
2. **New:** `buildNpmPackages((cmd) => execSync(cmd, { stdio: 'inherit' }))`. This runs in dry-run too: it publishes nothing, and it validates that the set builds. If it throws, the existing top-level `catch` logs `Workstream release failed:` and exits 1. `publishPackages` is never reached (AC2).
3. `publishPackages(releaseGraph, projectsVersionData, \`workstream-${slug}\`, dryRun, { excludeTaskDependencies: true })`, or without the options object if the check in 6.2 failed.

Update the header comment: the flow is stamp → build all → publish, and a build failure publishes nothing. Do not import `releaseChangelog` (the safety comment stays).

### 6.4 `.github/workflows/workstream-build.yml`

**Comments and step name only**, no change to the job graph:

- Rename the step to `Stamp versions, build and publish npm packages`.
- In the job 6 header, add a paragraph: the npm packages are built all together *before* the first publish, a single build failure aborts with nothing published, and this is the intra-job counterpart of the `needs:` chain.
- Adjust the sentence "If only this job fails, re-running it is safe". It stays true, and it now also covers a build failure, since nothing was published.

### 6.5 `docs/WORKSTREAM_WORKFLOW.md`

In *npm is published last*, add 2 or 3 sentences: inside `publish-npm` the packages are built first, all of them, and published only when every build succeeds. The reason is that `releasePublish` would otherwise publish each package as soon as its own build is done, which produced the partial sets `0.0.0-workstream-forge.310/311`, where `coday-client` was missing.

## 7. Verification criteria

Tests to add, in `scripts/utils/build-npm-packages.spec.ts` (Jest, project `scripts`, no `nx` import):
- `buildNpmPackages` calls `exec` exactly once with `NPM_BUILD_COMMAND`.
- When `exec` throws (failing build), `buildNpmPackages` **rethrows**. This is the regression case: before the change no build gate existed, after it a failing build stops the flow.
- `NPM_BUILD_COMMAND` selects `tag:platform:npm`, excludes `tag:desktop-bundle` and targets `build`. This guards against an accidental narrowing.
- Optional, if cheap: an ordering test on `main()` is **not** required, because `workstream-release.ts` runs `main()` at import time. Keep the logic in the pure module and the wiring trivial.

Existing checks that must stay green:
- `pnpm nx run-many -t lint test -p scripts` (with `workstream-release.spec.ts` and `update-toml-version.spec.ts`).
- A type check of the scripts: `pnpm exec tsc -p scripts/tsconfig.json --noEmit`, or whatever the project uses. Both `release.ts` and `workstream-release.ts` must compile against the new `publishPackages` signature.

Manual checks:
- Locally: `npx tsx scripts/workstream-release.ts --version 0.0.0-workstream-test.1 --slug test --dry-run` prints the build command, builds client, factory-cockpit and server, then runs the dry-run publish. With a deliberately broken client (a local, uncommitted syntax error), the same command exits 1 after the build and **does not** print any publish output.
- After the merge: the next push to `workstream/forge/master` produces a green `publish-npm` job, and the four packages of the new version exist on npm with dist-tag `workstream-forge`.
- YAML: only comments and a step `name:` change. `actionlint` (if available) or GitHub's workflow parse on push must accept the file.

**Risk level: low.** The change adds a gate before an existing call. The master path is untouched thanks to the optional parameter, and the job graph does not change. The worst case of a wrong selector is a missing build, which the `dependsOn: build` fallback still covers when `excludeTaskDependencies` is not used.
