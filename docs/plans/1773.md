# #1773 — Shared and platform AuthSettings return 404 on `/connection`, `/connect`, PUT and DELETE

Ticket: https://github.com/whoz-oss/coday/issues/1773 (GitHub issue, no Jira key, no comments, no linked ticket).
Work branch: `work/forge/1773-fix-authsetting-permissions`. Base and PR target: `workstream/forge/master`.
Type: **bug**.

## 1. Expected outcome

A user who may read an AuthSetting that is shared by a namespace, or defined at platform level, can read their connection state (`GET /{id}/connection`), connect (`POST /{id}/connect`) and disconnect (`DELETE /{id}/credential`) on it. A namespace ADMIN can edit (`PUT /{id}`) and delete (`DELETE /{id}`) the namespace-shared rows. Today all these calls answer 404.

- **Observed**: on prodadm, the Jira setting shows "Connect" while the user is connected. Edit and delete answer 404. The reporter cites two failing URLs (`/api/auth-settings/{id}/connection` and the PUT/DELETE on `/api/auth-settings/{id}`) without giving the ids.
- **Expected**: the connection state is right, and edit and delete work for the roles in section 2.
- **Reproduction steps**: partial (symptoms and endpoints only). They can be fully derived from the code (see section 4), so this is enough to design the fix.

## 2. Acceptance criteria

The access rules after the fix, from the ticket:

| Action on the AuthSetting | NS-shared row: namespace MEMBER | NS-shared row: namespace ADMIN | Platform row: any user | Super-admin |
|---|---|---|---|---|
| `GET /{id}` | 200 | 200 | 200 | 200 |
| `GET /{id}/connection`, `POST /{id}/connect`, `DELETE /{id}/credential` (READ) | allowed | allowed | allowed | allowed |
| `PUT /{id}` (WRITE) | 404 | 200 | 404 | 200 |
| `DELETE /{id}` (DELETE) | 404 | 204 | 404 | 204 |

1. AC1: a namespace MEMBER gets 200 on `GET /{id}` and `GET /{id}/connection` for a namespace-shared AuthSetting.
2. AC2: a namespace ADMIN gets 200 on `PUT /{id}` and 204 on `DELETE /{id}` for a namespace-shared AuthSetting.
3. AC3: a namespace MEMBER still gets 404 on `PUT` and `DELETE` for a namespace-shared AuthSetting.
4. AC4: any authenticated non-admin user gets 200 on `GET /{id}` and `GET /{id}/connection` for a platform AuthSetting, and 404 on `PUT` and `DELETE`.
5. AC5: a user with no relation to the namespace still gets 404 on every endpoint for a namespace-shared AuthSetting.
6. AC6 (derived): the owner of a user-global or user×namespace AuthSetting keeps full access (the ownership branch). Another user gets 404 on someone else's **user-global** AuthSetting (it is not readable as a platform row because `userId IS NOT NULL`).
7. AC7 (derived): `POST /by-ids` now returns platform AuthSettings and namespace-shared ones to members, because `filterVisibleIds` gets `checkPlatform = true` and the namespace traversal.

## 4. Root cause (one, with proof)

`agentos/agentos-service/src/main/kotlin/io/whozoss/agentos/permissions/Neo4jPermissionRepository.kt`:

- `isNamespaceChildEntity()` (end of the file) does not contain `EntityType.AUTH_SETTING`. So `hasTransitivePermission()` returns `false` straight away (`if (!isNamespaceChildEntity(entityType)) return false`), and the namespace traversal `(n:Namespace)<-[:BELONGS_TO]-(e:AuthSetting)` is never tried.
- `PLATFORM_SCOPABLE_ENTITY_TYPES` (companion object) does not contain `EntityType.AUTH_SETTING` either. Even when the transitive branch is reached, the platform rule `isPlatformScoped` (namespaceId and userId both NULL) is never applied to AuthSettings.

The failure path for a non-super-admin: `@PreAuthorize("hasPermission(#id, 'AuthSetting', …)")` → `AgentOsPermissionEvaluator.hasPermission` → `PermissionServiceImpl.evaluatePermission`: no direct edge (AuthSettings never get one), so it checks the transitive permission, which is always false. Then the ownership fallback: `OwnershipResolver` → `AuthSettingService.resolveOwner` = `userId`, which is `null` on shared and platform rows. The result is DENIED, and `@HideOnAccessDenied` turns the 403 into a 404. That hides the real reason.

The data is already right: `Neo4jAuthSettingRepository.save` creates the `BELONGS_TO` edge for namespace-scoped rows (proven by `AbstractAuthSettingPersistenceSpec` "save links a namespace-scoped setting to its Namespace via BELONGS_TO"), and `AuthSettingNode` keeps the `namespaceId` and `userId` properties that `isPlatformScoped` and `filterIdsWhere*` read. Only the registration of the type is missing.

Why the user's own rows work today: the ownership branch (`userId == caller`) authorizes them. Super-admins work through the bypass. That is why the bug only shows on shared and platform rows.

## 6. Scoped change

### Backend (the only side concerned)

`Neo4jPermissionRepository.kt`:
1. Add `EntityType.AUTH_SETTING` to the set in `isNamespaceChildEntity()`.
2. Add `EntityType.AUTH_SETTING` to `PLATFORM_SCOPABLE_ENTITY_TYPES`.
3. Update the three comments that list the covered types (the "Covers:" list of `PLATFORM_SCOPABLE_ENTITY_TYPES`, the comment in the MEMBER branch of `hasTransitivePermission`, and the KDoc of `isNamespaceChildEntity`) so they name AuthSetting.

AuthSetting is **not** added to `OWNER_PRIVATE_ENTITY_TYPES`: namespace members must read the shared rows (AC1).

No change to the controller, the Cypher, the SDK, the OpenAPI spec or the generated client. No change to the frontend.

### Frontend

None in this ticket. The ticket lists the UI work as a follow-up (section 9).

### Contract

Unchanged: same endpoints, same payloads. Only the HTTP status changes for the authorized roles (404 → 200/204).

**Risk level: low.** Two additions to two sets, aligned with seven other entity types that already use the same rule. The behaviour only widens access for roles that the controller guards and the ticket already intend to authorize (the AuthSetting guards were written for this rule).

Known, accepted effect, the same as for Prompt and AiProvider today: a user×namespace overlay also has a BELONGS_TO edge, so after the fix a namespace MEMBER can READ another member's user×namespace AuthSetting by id (the secrets are masked in the DTO), and a namespace ADMIN can WRITE/DELETE it. `/connect` on such a row with `namespaceId` resolves by name in the caller's own layers. Without `namespaceId`, it would authorize the caller with that row's client configuration. This is not a regression of the rules shared by the other overlay types, but it is noted for the follow-up below.

## 8. Deployment notes (from the ticket)

- `PermissionCache` (Caffeine, in memory, TTL 5 minutes) can still hold `false` results for up to 5 minutes after the deployment. A restart clears it. Otherwise wait for the TTL.
- On prodadm, check the scope of the two AuthSettings concerned (`namespaceId`, `userId`). The fix covers namespace-shared and platform rows. If one of them is a user×namespace row belonging to another user, the 404 on PUT/DELETE is expected for a MEMBER.

## 9. Follow-ups to propose as separate tickets

- Frontend (from the ticket): hide Edit and Delete for a plain member on shared rows (`auth-settings-all-scopes` and the form), and offer a "Disconnect" button separate from Delete (`AuthSettingConfigStateService.resetCredential` already exists).
- Decide whether namespace transitivity should exclude user overlays (`e.userId IS NULL` in `hasReadAccessViaNamespace` / `hasAdminAccessViaNamespace`) for every overlay type (AuthSetting, Prompt, AiProvider, IntegrationConfig).
- Consider logging the denial reason behind `@HideOnAccessDenied` at debug level, so this class of bug is quicker to diagnose.
