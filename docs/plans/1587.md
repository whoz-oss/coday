# #1587 Add pptx read capacity

- Ticket: https://github.com/whoz-oss/coday/issues/1587 (enhancement, milestone "Post Convergence", empty description, no comment)
- Work branch: `work/forge/issue-1587-pptx-read`, base `workstream/forge/master`
- Routes: **backend** and **frontend**, independent of each other (see the contract section)

## Context

Agents can already *see* a PowerPoint: `readAsImage` renders one image per slide (#1148). They cannot *read*
it: there is no text tool for `.pptx`, whereas `.docx` has `readDocument` (#1153) and `.xlsx` has
`readSpreadsheet` (#1151). Seeing a slide costs about one image, and gives no exact, quotable or searchable text,
no speaker notes and no text of hidden slides. In the UI, a `.pptx` in the file exchange shows "Preview not
available" (it is in `BINARY_EXTENSIONS`).

The reporter confirmed the scope when asked during this step: **both** a text tool for agents and a preview in
the exchange file viewer.

## Expected outcome

An agent can read a `.pptx` as Markdown text (slide by slide: title, text, tables, speaker notes, embedded
pictures attached), and a user can preview the text of a `.pptx` in the exchange file viewer instead of being
only offered a download.

## Acceptance criteria

The ticket has none: all are derived (D) from the ticket title, the reporter's answer and the sibling tools.

Backend (tool)
1. (D) A read tool `<config>__readPresentation` is provided by the FILE_ACCESS integration, in read-only and
   read-write configs alike (so on both exchange scopes).
2. (D) It returns Markdown with one section per slide, in presentation order: `## Slide i/N` + title, body text
   (bullets with their indentation level), tables as Markdown tables, speaker notes. Hidden slides are included
   and marked `(hidden)`.
3. (D) Pictures placed on the slides that are emitted are attached as images (at most 10 per call, oversized
   ones skipped, never fatal), with a notice of how many were attached / not shown.
4. (D) Output is bounded (~100 000 chars per call); a longer deck is paged with `startSlide`, with a
   `[truncated]` notice that tells the model how to continue.
5. (D) Errors mirror the siblings: legacy `.ppt` and other extensions -> `UNSUPPORTED_FORMAT`; password-protected,
   corrupt or non-presentation package -> `INVALID_INPUT`; size cap, sensitive patterns and path traversal
   enforced; no absolute server path in messages.
6. (D) Every tool description stays within the 1024-character provider cap.

Frontend (preview)
7. (D) Selecting a `.pptx` (<= 20 MB) in the exchange drawer opens a preview that lists the slides in order
   with their title, text and speaker notes, instead of "Preview not available".
8. (D) A corrupt / encrypted / non-pptx file shows the existing "Couldn't load this file" state with "Download
   instead"; download, copy path and back keep working.
9. (D) The preview renders text only through Angular interpolation (never `innerHTML`), and the extraction is
   bounded (only the slide, notes and relationship XML parts are decompressed; extracted text is capped).
10. (D) `.ppt` (legacy) and other binaries keep "Preview not available".

## Contract between frontend and backend

There is **no new API**. The two routes are independent:
- The backend route adds an agent tool inside the file plugin; it exposes nothing over REST.
- The frontend route reads the raw bytes through the **existing** endpoints
  `GET /api/cases/{caseId}/files/download?path=` and `GET /api/namespaces/{namespaceId}/files/download?path=`
  (already used for images and PDFs through `ExchangeStateService.getBlob`), and extracts the text in the browser.
  `.pptx` is already in the upload allow-list (`ExchangeStorageConfigProperties`).

Why not a server-side preview endpoint: POI lives only in the plugin jar (PF4J, not on the service classpath);
putting it on the service classpath, or calling a plugin tool from a controller, would couple the service to the
plugin for a preview. A browser-side text outline needs nothing from the server.

Both sides should produce the same reading order (presentation order from `ppt/presentation.xml` `p:sldIdLst`)
and the same notion of "slide title" (the title/ctrTitle placeholder); exact Markdown equality is not required.

## Scoped change

### Backend

1. **New** `agentos/agentos-file-plugin/src/main/kotlin/io/whozoss/agentos/plugins/file/tools/ReadPresentationTool.kt`
   - `StandardTool<Input>`, name `${configName}__readPresentation` / `FILES__readPresentation`, version `1.0.0`.
   - `Input(filePath: String = "", startSlide: Int? = null)`; JSON schema `filePath` required, `startSlide`
     integer >= 1, `additionalProperties: false`.
   - Constructor mirrors `ReadDocumentTool`: `projectRoot, configName, readMaxSizeBytes, denyPatterns,
     ioTimeoutSeconds (60), imageMaxDimension, imageJpegQuality, imageMaxSourcePixels`, plus
     `maxOutputChars = 100_000`, `maxAttachedImages = 10`, `maxTableColumns = 64`, `maxCellChars = 5000`
     as companion constants (no new config keys: reuse of the document* keys is out of scope).
   - Execution: `runIOWithTimeout`, same `catch` ladder as `ReadDocumentTool` (TIMEOUT, UNSUPPORTED_FORMAT,
     INVALID_INPUT, FileSystemException -> READ_ERROR with relative path, generic READ_ERROR).
   - Read: `BoundaryPathResolver.resolve(createIntent = false)`, size guard, extension switch (`pptx` ok;
     `ppt` -> "Legacy binary '.ppt' is not supported: convert to .pptx first."; else UNSUPPORTED_FORMAT pointing to
     readDocument / readSpreadsheet / readFile). Open with `OPCPackage.open(file, PackageAccess.READ)` then
     `XMLSlideShow(opcPackage)` (revert on failure; direct construction for the PF4J classloader, as in the
     siblings). Map `EncryptedDocumentException`, `NotOfficeXmlFileException`, `POIXMLException`,
     `InvalidFormatException`, `InvalidOperationException` exactly like `ReadDocumentTool` (wording "PowerPoint" /
     ".pptx").
   - Render, per slide from `startSlide` while under budget:
     `## Slide i/N[ (hidden)]: <title>` (title = text of the `TITLE`/`CENTERED_TITLE` placeholder, else none),
     then the shapes in z-order, groups walked recursively: `XSLFTextShape` paragraphs (skip the title shape
     already printed; bullets/indent level -> `- ` with two spaces per level; other paragraphs plain), `XSLFTable`
     -> Markdown table (escape `\` then `|`, newlines -> `<br>`, column/cell caps; per-row budget check as in
     `appendTable`), then `slide.notes` text (body placeholder only, not the slide-number placeholder) as
     `> Notes: ...`. Charts/SmartArt are not text-extracted (POI has no API): silent, the description points to
     readAsImage for visuals. A single oversized text is capped in place (`capToBudget`).
   - Pictures: `XSLFPictureShape.pictureData` of the emitted slides (deduplicated by part), header check against
     `imageMaxSourcePixels`, decode under a JVM-wide `Semaphore(4)`, `ImageProcessor.toJpegContent`, up to the cap;
     notice `[k embedded image(s) attached below. (m of t not shown)]` or `[t ... present but none could be shown.]`.
   - Paging notice: `[truncated] N slides total; call again with startSlide=K to continue.`;
     `startSlide` beyond N -> INVALID_INPUT "out of range"; empty deck -> "(no slide)" success.
   - Description (keep < ~900 chars, asserted < 1024): what it returns, the image cap, paging, `.pptx` only,
     "to SEE the slide layout use readAsImage".
2. `.../plugins/file/FileToolProvider.kt`: add `ReadPresentationTool(rootPath, configName, readMaxSizeBytes,
   denyPatterns, imageMaxDimension=..., imageJpegQuality=..., imageMaxSourcePixels=...)` to `readTools` (after
   `ReadSpreadsheetTool`); update the KDoc list of read tools and the `readMaxSizeMb` / image keys descriptions in
   the config schema to mention readPresentation (text only, no new key).
3. `.../plugins/file/tools/ReadAsImageTool.kt`: description line "For Word documents (.docx) use readDocument."
   becomes "For the text of Word (.docx) or PowerPoint (.pptx) files use readDocument / readPresentation." -
   check the length stays < 1024. No behaviour change.
4. Tests: **new** `src/test/kotlin/io/whozoss/agentos/plugins/file/ReadPresentationToolSpec.kt` (see below) and
   `FileToolProviderSpec.kt`: 9 -> 10 tools, 6 -> 7 read-only, add `TEST__readPresentation` to the name lists
   (incl. the scopeGuidance "read tools untouched" list); the 1024-cap test covers it automatically.
5. Docs: `agentos/docs/file-exchange.md`, add readPresentation where the read tools are listed.

Not touched: `ExchangeToolGrantService`, `ExchangeToolsConfigProperties`, `application.yml`, `KnownSettings`
(no new settings), `ExchangeIntegrationTypes.MUTATING_TOOLS` (read tool).

### Frontend

1. Dependency: add `fflate` (MIT, ~8 kB gzip, no transitive deps) to the root `package.json` (and the pnpm
   catalog if that is how runtime deps are pinned). Load it with a dynamic `import('fflate')` so it is only fetched
   when a `.pptx` is opened. (Alternative if a new dependency is refused: a ~60-line zip central-directory reader
   over `DecompressionStream('deflate-raw')`; harder to unit-test under jsdom.)
2. **New** `libs/agentos-ui/src/lib/services/pptx-outline.utils.ts` (pure, no Angular):
   - `export interface PptxSlide { index: number; title: string | null; paragraphs: { text: string; level: number }[];
     tables: string[][][]; notes: string | null; hidden: boolean }`
   - `export async function extractPptxOutline(bytes: Uint8Array): Promise<PptxSlide[]>`: `unzipSync` with a
     `filter` that only accepts `ppt/presentation.xml`, `ppt/_rels/presentation.xml.rels`, `ppt/slides/slideN.xml`,
     `ppt/slides/_rels/slideN.xml.rels`, `ppt/notesSlides/notesSlideN.xml` and rejects any entry whose declared
     `originalSize` exceeds a cap (e.g. 5 MB per part, 50 MB total) -> throw. Order slides by `p:sldIdLst` resolved
     through the presentation rels; notes through the slide rels (`.../notesSlide`). Parse with `DOMParser`
     (`application/xml`), namespace-aware lookups (`getElementsByTagNameNS` with the `a`/`p` namespaces): title =
     `p:sp` whose `p:ph@type` is `title`/`ctrTitle`; paragraphs = `a:p` of other `p:sp` (level from `a:pPr@lvl`,
     text = concatenated `a:t`, `a:br` -> newline); tables = `a:tbl/a:tr/a:tc`; notes = body placeholder text of the
     notes slide; hidden = `p:sld@show="0"`. Cap total extracted characters (e.g. 200 000) and mark the outline
     truncated. Throw a typed error when the zip is not a presentation (no `ppt/presentation.xml`).
3. `libs/agentos-ui/src/lib/services/exchange-content.utils.ts`:
   - `ContentFormat` gains `'presentation'`; `detectFormat` maps `pptx` -> `'presentation'`.
   - `export function isPresentationFile(name)` (`pptx` only, case-insensitive).
   - `isBlobPreviewFile` includes `isPresentationFile` (so `canViewFile` accepts it under 20 MB and the shell
     fetches the bytes); `pptx` stays in `BINARY_EXTENSIONS` (still never shown as text); `ppt` unchanged.
   - `getFileIcon`: `pptx`/`ppt` -> `'slideshow'`.
   - `ensureTypedBlob` needs no change (non-image, non-pdf blobs pass through).
4. `libs/agentos-ui/src/lib/components/exchange-content-viewer/exchange-content-viewer.component.ts`: a
   `presentation` signal (`PptxSlide[] | null`) + `presentationFailed` signal, filled by an `effect` on
   `blob()` when `format() === 'presentation'` (`blob.arrayBuffer()` -> `extractPptxOutline`), with a generation
   guard so a late result for a previous file is dropped; reset on file change. `canOpenFull` unchanged (no full
   view / new tab for pptx).
5. `.../exchange-content-viewer.component.html`: a `@else if (format() === 'presentation')` branch: spinner while
   parsing, the "Couldn't load this file" empty state with "Download instead" on failure, otherwise a list of
   `<section>` per slide (`Slide i` + title as heading, `(hidden)` badge, paragraphs indented by level, simple
   `<table>`, notes block), a "Preview truncated, download the file for the full content" line when capped, and
   "No slide" when empty. Interpolation only.
6. `.../exchange-content-viewer.component.scss`: styles for the slide list using the design-system tokens already
   used by the markdown block.
7. `exchange-shell.component.ts`: no change expected (the blob path is driven by `isBlobPreviewFile`); only
   adjust the `loadBlob` KDoc ("images, PDFs and presentations").

## Risk level

**Low to medium.** Backend: additive read tool in an isolated plugin, no new dependency, pattern proven by two
siblings; the main risks are the tool-count/description-cap tests and POI memory on large decks (bounded by the
size cap and timeout, as for readDocument). Frontend: additive format branch; risks are the new `fflate`
dependency (license/bundle, mitigated by lazy import), zip-bomb handling in the browser (mitigated by the
entry filter and size caps) and not regressing the image/PDF blob path shared in `isBlobPreviewFile`.
