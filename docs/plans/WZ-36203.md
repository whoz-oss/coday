## Acceptance criteria

Explicit in the ticket:
1. A visible Wizz button in the conversation toggles the mode; off by default and clearly active when enabled.
2. Enabled mode produces one short shake of the conversation panel, not the page, on completion of a new agent response.
3. No repeated effect per streaming fragment, user message, tool event or technical event. Loading history never triggers it.
4. No Wizz-induced scrolling or lasting layout change.
5. `prefers-reduced-motion: reduce` replaces shaking with a brief stationary highlight.
6. Accessible name, native keyboard operation and exposed toggle state; follow existing visuals and translation conventions.
7. Frontend only; no sound, dependency, backend/agent-engine change or persisted preference. Reuse the existing completion event.
8. Add relevant frontend coverage of toggling, completion uniqueness, exclusions/history and reduced motion; provide browser coverage of scroll/layout stability.

Derived design decisions (not literal ticket criteria):
- Apply the user-approved conservative eligibility rule above. Wizz is not a delivery guarantee for every possible agent implementation.
- Reset the toggle to off on a case switch/reinitialisation, including reopening; preserve it during a transport retry of the same case but discard in-flight eligibility. Destroying/remounting also returns to off. No storage or preference API.
- Treat one agent run ending at `AgentFinishedEvent` as one response, even if several AGENT MessageEvents occur during that run. Require at least one non-empty textual AGENT message after live eligibility begins; a tool-only or no-answer finish does not animate. Scope eligibility to the current case and agent run; do not count delegated sub-case lifecycle events as an answer.
- A fresh transient event after enabling mid-run can arm the effect; enabling after the last transient event does not retroactively arm it. Disabling clears eligibility and cancels the current visual effect.

## Minimal scoped implementation — frontend

### 1. `libs/agentos-ui/src/lib/components/case-chat/wizz-response.ts` (new)

A small, frontend-only stateful eligibility helper, with no DOM, persistence, HTTP, timers or dependency injection. Feed it only newly accepted events from the existing SSE handler (after duplicate rejection), plus explicit enabled/reset notifications. Return a completion token or boolean only on an eligible finish.

Keep bounded per-current-run state: live-armed flag, run agent id when known, candidate AGENT actor id and message id. Run boundaries (`AgentSelectedEvent`, `AgentRunningEvent`, a USER message/answer, prior finish) clear eligibility; transient thinking/chunks arm it only while enabled and never emit a completion. Repeated transients within the same run must not erase an existing candidate. An AGENT MessageEvent can record a candidate only after arming; require non-empty text using the existing text-content convention. At `AgentFinishedEvent`, match candidate actor id to finish agentId (and known running agent when available), consume/reset state unconditionally, and emit at most once. No user, tool, status, question, sub-case or technical event emits an effect. ErrorEvent and IDLE/KILLED/ERROR status clear pending eligibility; transport errors and explicit retries also clear it. Keep the existing component event-id dedup as the first line of defense against replayed finishes.

This is deliberately not a generic event service or new stream abstraction. Conservative missing eligibility means no effect, never guessing from timestamps, delays or browser clock. Current FIFO history-before-live ordering is part of the reasoning.

### 2. `libs/agentos-ui/src/lib/components/case-chat/case-chat.component.ts`

Own a local `signal(false)` for the toggle and the small helper instance. Process fresh events without altering current side effects, including before early returns for TextChunkEvent and status. Invoke the visual effect only for the helper's eligible finish, not for each message/chunk or changes to computed timeline/running state. Gate again on enabled state. Use no new subscriptions to global message notifications.

Own the animation lifecycle locally: one temporary CSS animation state on the message-region element, cleaned on animation completion/cancellation, disable, reinitialisation and destruction. Ensure consecutive eligible completions can restart the short effect, including two completions inside one duration (alternate animation names/states rather than forced reflow, polling or layout reads). A stale animation-end callback must not clear a newer effect. Transport resets clear eligibility; case resets also turn Wizz off. Keep late events from a closed/old EventSource from rearming the current case by checking current source identity/caseId at ingestion for this feature. Do not change case-running, focus, exchange refresh or scroll behavior.

### 3. `libs/agentos-ui/src/lib/components/case-chat/case-chat.component.html`

Add a native `button type="button"` labelled `Wizz` in the composer action bar with stable accessible name (e.g. `Wizz: highlight completed agent responses`), `[attr.aria-pressed]`, a clearly visible active state and focus-visible styling. Native Enter/Space behavior needs no custom key handler. Do not disable the toggle while an agent runs. Follow this screen's current English inline labels (the inspected component has no translation service/catalog); Wizz itself is invariant. Do not introduce an i18n framework or hard-code a different UI language.

Bind the ephemeral effect class/state and completion listener only to `.case-chat__messages-region`. Do not add/remove message rows or reparent the scroller to animate it. Header, usage, composer, namespace navigation and exchange drawer remain stationary.

### 4. `libs/agentos-ui/src/lib/components/case-chat/case-chat.component.scss`

A restrained single ~300 ms transform-only horizontal shake (about +/-3 px), identity at both ends; no animation fill retaining displacement. No width, height, margin, padding, position, scrollTop or focus mutations. Keep animation isolated to the message region and prevent any new page overflow without changing existing scroller behavior. Use a non-layout-affecting stationary inset highlight for reduced motion. A CSS media query replaces the entire shake animation, not just its duration, so it also respects preference changes without a new browser listener. Both normal/reduced variants support the restart/cleanup contract. Button styles use existing accent/background/border tokens, a non-color-only active indicator and no size changes between states; preserve narrow-screen action reachability.

### 5. Tests

- `libs/agentos-ui/src/lib/components/case-chat/wizz-response.spec.ts` (new): deterministic event sequences for helper behavior.
- `libs/agentos-ui/src/lib/components/case-chat/case-chat.component.spec.ts`: actual SSE wiring, dedup/lifecycle integration and effect invocation count. Preserve existing cases.

## Tests to write and review focus

No build, test, lint or check is executed in this architecture step; this plan makes no execution-based correctness claim and contains no validation commands.

Required scenarios:
- Default disabled, enable/disable, active appearance, native keyboard toggle, accessible name and aria-pressed. Enabling alone never animates; disable cancels the active effect and pending candidate. No settings API/storage calls.
- Live Thinking -> chunks -> AGENT message -> finish produces exactly one effect, only at finish; multiple chunks/ThinkingEvents/messages in a run still produce one. Repeat a completed finish id across legacy/stable channels and reconnect replay: no repeat.
- USER/Answer, tools, QuestionEvent, statuses, sub-case lifecycle and technical events never independently trigger an effect. Empty answer, mismatched agent, no-message finish, error/kill and boundary reset do not reuse a previous answer. Each subsequent genuine run can trigger again.
- Initial history containing old run/message/finish sequences, even while enabled before history arrives, never animates. Reconnect clears live eligibility before replay, including previously unseen durable events. Fresh transient activity after replay can arm a new candidate. Zero-LLM durable-only completion is silent as approved.
- Toggle on mid-run: no retroactive arming; later fresh transient may arm. Toggle off/on without fresh transient remains silent. Case switch/reopen defaults off; retry same case preserves preference but not eligibility; old source/case frames cannot trigger current chat. Destruction leaves no animation callback/resources.
- Two eligible completions close together restart once for each; stale completion handlers cannot terminate the latest animation.
- Browser normal motion animates only message region; reduced motion computes no transform/shake and shows a brief highlight, including when preference changes. Both return to baseline.
- At mid-history scroll, compare enabled versus disabled identical event sequences: Wizz adds no scrollTop/scrollHeight delta. At bottom, preserve existing magnetic scroll from incoming content rather than suppressing it. Compare final element bounds and page overflow before/after; header, composer, drawer and navigation do not move. Include small viewport and long content. Read focus/selection behavior carefully: Wizz itself must never move focus.

**Risk: medium**, despite low business impact. The sensitive areas are replay classification, handoffs/confirmation runs, dedup across reconnection, existing automatic focus/scroll and CSS overflow. The conservative live gate is intentionally safer than a time-based heuristic.
