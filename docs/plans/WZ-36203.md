## Acceptance criteria

From the ticket (no additional comments):

1. Visible Wizz button in the conversation toggles the effect; off initially; active state unmistakable.
2. When enabled, completion of a new agent answer shakes only the conversation panel briefly, not the whole page.
3. Exactly once per completed answer, never on streaming fragments, user messages, tool calls, technical events, or history loading.
4. Effect does not change scroll position or final layout.
5. `prefers-reduced-motion: reduce` replaces movement with a brief non-moving highlight.
6. Accessible name, keyboard-operable control, exposed enabled/disabled state; existing visual/language conventions.
7. Frontend only; no sound, dependency, backend/engine changes, or preference persistence; reuse an existing completion signal.
8. Automated frontend tests of the above and visual verification of scroll/layout.

Derived implementation decisions (not quoted requirements): reset toggle and pending animation on case change/reopen; disabling cancels the effect immediately; no delayed notification after enabling, navigation, or network recovery; require positive live-event evidence rather than guess at replay boundaries. A run with no visible agent answer does not Wizz. Several intermediate agent messages within one run produce at most one completion cue.

## Recommended architecture and exact event contract

Select **frontend only**. Preserve backend payloads, runtime, generated client, existing subscriptions and SSE state decisions.

The reliable replay-free completion source already exists: GlobalStreamService.caseEvents$ carrying a live AgentFinishedEvent. Correlate it, by **event ID and current case/namespace**, with the same finish in the per-case timeline to establish that this run contained a visible agent answer. The two transports can arrive in either order, so retain a small pending live-finish set and reconcile on either ingestion. No time-window/debounce history heuristic, local/server timestamp comparison, `onopen = history finished`, or separate live EventSource.

Use a component-provided Wizz state service, not CaseStateService's root-scoped list state. It subscribes once, disposed with the chat. Expose readonly enabled state, toggle, and a completion pulse output. Keep DOM animation owned by the component. Suggested internal methods: `setContext(caseId, namespaceId)`, `acceptTimeline(events)`, `toggle()`, `reset()`. Can keep correlation as a pure helper beside the service for deterministic tests.

Eligibility:

1. Only a live global `AgentFinishedEvent` observed while Wizz is enabled and the same conversation is active can be a candidate. Ignore every other global type. Deduplicate candidates before scheduling an effect.
2. Resolve the candidate's exact finish ID in per-case events. Identify that agent run's interval after its matching AgentRunningEvent (or the latest user/start boundary when necessary) and before the finish. Require a non-empty AGENT text MessageEvent belonging to that agent, not merely old text before a previous run. Follow existing turn-metrics boundary conventions; do not change timeline metrics.
3. Once resolved, consume the candidate even when it has no answer. Clear pending candidates on disable/recovery, and clear all correlation/consumed state on context reset or teardown. A repeated finish ID must not re-trigger after toggling: seed already-known finish IDs from current timeline on enable, and preserve consumed IDs for the current context. Cap pending candidates to avoid retaining unmatched global events indefinitely; discard on next run/context boundary or disconnect/recovery rather than replaying old visual work.
4. Handoff/empty/tool-only runs do not Wizz. A displayed, completed non-empty agent response counts even if it reports an iteration limit; the cue signifies answer availability, not task success. Do not infer success from `maxIterationsReached` absence.
5. Global finish can arrive before the local final message: wait for the local exact finish before deciding. Local history alone, including first load and unseen replay after reconnect, never creates a candidate. A global live finish while history is still loading is a real new response; it can resolve once its corresponding local finish arrives, provided the same enabled context is still active.

Known delivery boundary: `/events/mine` covers directly related active cases; a namespace-only reader without a direct case relation may not receive that global event. Prefer no cue over a false replay cue in that case or during global-stream downtime. This is an existing notification coverage limitation, not grounds to change server permissions in this visual story. Record this limitation in the PR/manual results. If product requires guaranteed Wizz for namespace-only cases, request a separate protocol/notification-coverage ticket; do not silently use a timestamp heuristic or claim that scenario was covered.

No new frontend/backend API contract is needed. Existing contracts are GET `/api/cases/{caseId}/events` (history + live, JSON discriminant `type` on `case-event`) and shared GET `/api/cases/events/mine` (live named `AgentFinishedEvent`). Correlation uses `{id, caseId, namespaceId, agentId}` from the same backend event. No requests on toggle; no preference write.

## Verification and risk

**Risk: medium**, concentrated in replay/live correlation, multiple transports, router reuse, and animation/scroll interaction. Visual code is small; chat lifecycle is sensitive.

Automated additions:

- Initially off; native labelled control toggles aria-pressed and active style; enable sends no HTTP/storage operation.
- Live finish + same-run non-empty AGENT message => one pulse; both transport orders; many streaming fragments => no intermediate pulse.
- Duplicate per-case/global finish IDs, repeated signal snapshots, timeline preferences, disable/re-enable => no repeat.
- USER/AnswerEvent, text chunks, tools, thinking/status/errors/questions and empty/tool-only/handoff run => none. Agent message without exact matching finish => none. Multiple intermediate messages => one run-completion cue.
- Initial history, history containing full run sequences, unseen reconnect catch-up, retry/reopen, switching cases, other namespace/case, stale previous-case callback => none. New live eligible response after replay still works.

- No calls to scrollToBottom/scrollTop changes made by the effect; target is messages-region, not host/page/composer. Existing normal magnetic scroll caused by NEW CONTENT remains unchanged; compare with Wizz off, not with an artificially frozen chat.
