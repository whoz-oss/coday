# WZ-36203 — [Coday UI] « Wizz » mode at the end of an agent answer

Jira: https://whoz.atlassian.net/browse/WZ-36203 (User Story, parent epic WZ-34898)
Base branch: `workstream/forge/master` · Work branch: `feature/WZ-36203-wizz-mode`
Routes: **frontend** only · Risk: **low**

## 1. Expected outcome

In the case chat, a « Wizz » toggle button (off by default) makes the conversation panel give one short
MSN-style shake each time a new agent answer is completed, and a motionless highlight instead when the user
prefers reduced motion. Nothing else in the page moves, scrolls or changes layout.

This is not a bug: it is a small, self-contained UI feature (no reproduction steps to look at).

## 2. Acceptance criteria

From the ticket:

1. AC1. The conversation has a « Wizz » button that turns the effect on or off. It is **off by default** and its on state is
   clearly visible.
2. AC2. When it is on, the end of a **new** agent answer triggers a short shake of the **conversation panel only**, not of
   the whole page.
3. AC3. It is triggered **once per completed answer**, never on a streaming chunk, a user message, a tool call or a
   technical event. **Loading the history does not trigger it.**
4. AC4. The effect changes neither the scroll position nor the final layout.
5. AC5. With `prefers-reduced-motion: reduce`, the shake is replaced by a short highlight with no movement.
6. AC6. The button has an accessible label, works from the keyboard and exposes its on/off state. It follows
   the visual and translation conventions of the project.
7. AC7. Frontend only: no sound, no new dependency, no change to the agent engine or the backend. Reuse the existing
   end-of-answer signal. The setting is not persisted in this first version.

Derived by the architect (flagged):

- **D1 (derived).** A "new answer" is an answer to a turn **started from this chat** (message sent, question
  answered, voice message, "Continue"). This is the only deterministic way to tell live events from history: the SSE
  protocol has no boundary between the replayed history and live events (see `TERMINAL_CLOSE_DEBOUNCE_MS` in
  `case-chat.component.ts`). A turn that was already running when the case was opened, or that was started by another
  member of a shared case, therefore does not wizz. This is acceptable for v1 and keeps AC3 safe.
- **D2 (derived).** A turn counts as "an answer" only if at least one agent `MessageEvent` (actor role `AGENT`)
  arrived during it. A turn that ends on a warning only (no agent configured, agent not found), on an interruption
  requested by the user (Interrupt button), or on KILLED / ERROR does not wizz.
- **D3 (derived).** "Once per answer" = once per **turn**, not once per agent. A turn handed over from one agent to another
  (redirect, several `AgentFinishedEvent`s) or draining several queued commands still gives a single wizz, at its
  end (`CaseStatusEvent` `IDLE`).
- **D4 (derived).** Translation conventions: `libs/agentos-ui` has no i18n layer (no `$localize`, no translation
  pipe). All UI strings are plain English literals, so the button follows that: visible text `Wizz`, English
  `title` / `aria-label`.
- **D5 (derived).** The toggle state lives in the chat component (a signal). It is kept when switching from one case to another
  in the same component instance, and lost on page reload (no persistence, AC7).

### The existing end-of-answer signal (to reuse)

In `connectSse()`'s handler (`case-chat.component.ts`):

- **Replay deduplication.** An event whose id is already in `events()` takes the early-return branch at the top and only
  restores `isRunning`. A reconnection therefore never re-runs the live side effects (pinned by the specs
  "does not refresh Files again when a reconnection replays…").
- **Turn end.** `CaseStatusEvent` with `status === 'IDLE'` is the end of the whole turn. It is the branch that already resets
  `streamingText`, after every handoff and every queued command (backend: `CaseRuntime.executeTurn` →
  `updateStatus(finalStatus)` → `CaseServiceImpl.handleStatusChange` emits `CaseStatusEvent`).
  `AgentFinishedEvent` is **not** suitable: it is also emitted on every handoff between agents (see the comment
  "A handoff emits one too" and the spec "keeps the case running … in the gap between two agents"), so it would
  wizz several times per answer.
- **Agent answer.** An agent `MessageEvent` (`msg.actor.role === 'AGENT'`). The component already forwards it to
  `caseState.notifyAgentMessageEvent`.
- **No history/live boundary.** On the first connection, the whole persisted history goes through the "new event" path
  (the dedup set is empty), including `CaseStatusEvent IDLE` frames and agent messages. This is why D1 arms the
  trigger on a local user action and not on the stream alone.

Turns started locally all go through `isRunning.set(true)`: `postMessage()` (covers `submit`, attachments,
`continueAfterLimit`), `onQuestionAnswered()`, and the voice `onSending` callback in `startRecording()`. Their
failure paths set `isRunning` back to `false` (`postMessage` error, `onQuestionAnswered` error, voice
`onSendFailed`).

### Recent history and regression risk

The chat component is touched a lot (running state across handoffs, PENDING gate, stream death, voice, effort).
Areas to leave alone: `runningAfter` and the dedup branch, the terminal-close debounce, the magnetic auto-scroll effect and the
focus effects. The change only **adds** a few calls in existing branches. It changes no condition, no early
return and no existing signal.

## 5. Scoped change (frontend)

### 5.1 New file `libs/agentos-ui/src/lib/components/case-chat/wizz-trigger.ts`

A small, framework-free state machine (pure TS, like `case-chat.utils.ts`), so the trigger rules can be tested
without the component:

```ts
/** Decides when a completed agent answer should wizz the chat. See docs/plans/WZ-36203.md. */
export class WizzTrigger {
  private armed = false
  private answered = false

  /** A turn was started from this chat (message, answer, voice, Continue). */
  arm(): void { this.armed = true; this.answered = false }

  /** The local start failed, the user interrupted, or the chat moved to another case. */
  disarm(): void { this.armed = false; this.answered = false }

  /**
   * Feed every NEW (non-deduplicated) case event. Returns true exactly once, on the IDLE status that ends an
   * armed turn during which at least one agent message arrived. Any IDLE / KILLED / ERROR status disarms.
   */
  onEvent(event: CaseEvent): boolean { … }
}
```

Rules of `onEvent`:

- An agent `MessageEvent` (`actor.role === 'AGENT'`) received while armed sets `answered = true`.
- `CaseStatusEvent` with `IDLE`: returns `armed && answered`, then disarms.
- `CaseStatusEvent` with `KILLED` or `ERROR`: disarms and returns false.
- Everything else (`TextChunkEvent`, user messages, tools, `AgentFinishedEvent`, `RUNNING` / `PENDING`, …): returns false
  and leaves the state as it is.

The trigger must not depend on whether the toggle is on. The component reads the toggle when the trigger
fires, so turning Wizz on in the middle of a turn still wizzes at its end.

### 5.2 `case-chat.component.ts`

1. State:
   - `protected readonly wizzEnabled = signal(false)`: the toggle (AC1, D5). It is **not** reset in `reinitialise()`.
   - `protected readonly wizzEffect = signal<'shake' | 'highlight' | null>(null)`: the effect currently playing.
   - `private readonly wizz = new WizzTrigger()`.
2. `protected toggleWizz(): void`: flips `wizzEnabled`. Turning it off also clears `wizzEffect`.
3. Arm, next to the existing `isRunning.set(true)` of a local action: in `postMessage()`, `onQuestionAnswered()`
   (after its guard) and the voice `onSending` callback. Disarm on their failure paths (`postMessage` error,
   `onQuestionAnswered` error, voice `onSendFailed`), in `interrupt()` (D2), and in `reinitialise()`.
4. In the `connectSse()` handler, **after** the dedup early return and after `this.events.update(...)`, call
   `if (this.wizz.onEvent(event)) this.playWizz()` once for every new event, before the per-type branches (some of
   them `return`). The dedup branch must **not** call it (AC3: a reconnection replay never wizzes).
5. `private playWizz(): void`:
   - does nothing unless `wizzEnabled()`;
   - picks `'highlight'` when `window.matchMedia?.('(prefers-reduced-motion: reduce)').matches`, otherwise `'shake'`
     (guard `matchMedia` with optional chaining: jsdom and the existing specs have none);
   - restarts cleanly if an effect is still playing: set `null`, then set the new value on the next frame
     (`requestAnimationFrame`, or `afterNextRender` with the component injector).
6. `protected onWizzAnimationEnd(): void { this.wizzEffect.set(null) }`, bound to `(animationend)` on the panel.
   It must ignore `animationend` events that bubble up from child animations (agent-activity pulse, voice
   recorder…): check `event.target === event.currentTarget`.

Nothing else changes in the component: no change to `isRunning`, `runningAfter`, the scroll effect or the focus
effects.

### 5.3 `case-chat.component.html`

1. Header, view mode, before the "Share case" button (with the other non-destructive header actions):

   ```html
   <button
     type="button"
     class="case-chat__wizz-toggle"
     [class.case-chat__wizz-toggle--active]="wizzEnabled()"
     [attr.aria-pressed]="wizzEnabled()"
     aria-label="Wizz: shake the conversation when an agent answers"
     [title]="wizzEnabled() ? 'Wizz is on: the conversation shakes when an agent answers' : 'Wizz is off'"
     (click)="toggleWizz()"
   >
     <span class="material-icons" aria-hidden="true">vibration</span>
     <span class="case-chat__wizz-toggle-label">Wizz</span>
   </button>
   ```

   Use a native `<button>`, not `ds-icon-button`: `ds-icon-button` cannot expose `aria-pressed`, and the header
   already uses native buttons (title, edit save and cancel, delete confirmation). A native button is focusable
   and works with Enter and Space (AC6).
2. The conversation panel `<div class="case-chat" …>` gets
   `[class.case-chat--wizz-shake]="wizzEffect() === 'shake'"`,
   `[class.case-chat--wizz-highlight]="wizzEffect() === 'highlight'"` and
   `(animationend)="onWizzAnimationEnd($event)"`. This element holds the messages and the composer only, not the
   header, the usage panel, the drawer or the app shell (AC2: "panel only").

### 5.4 `case-chat.component.scss`

- `.case-chat__wizz-toggle`: same size, padding and colour tokens as the other header buttons. In the
  `--active` state, use the accent colour (`var(--color-accent)`) for the text, icon and border or background,
  so the on state is clearly visible (AC1). Add a visible `:focus-visible` ring.
- `.case-chat--wizz-shake { animation: case-chat-wizz-shake 500ms ease-in-out 1; }`, with `@keyframes` using
  **`transform: translateX(...)` only** (±4px, a few steps, back to `none` at 100%). A transform neither moves the
  layout nor changes the `scrollTop` of the inner `.case-chat__messages` (AC4). Nothing persists after the animation (no
  `forwards` fill mode).
- `.case-chat--wizz-highlight { animation: case-chat-wizz-highlight 600ms ease-out 1; }`, with `@keyframes` on
  `box-shadow: inset 0 0 0 2px var(--color-accent)` fading to `none`. No movement, no layout impact (AC5). An inset
  shadow cannot be clipped by an `overflow: hidden` ancestor.
- As a safety net, add
  `@media (prefers-reduced-motion: reduce) { .case-chat--wizz-shake { animation-name: case-chat-wizz-highlight; } }`,
  in line with the existing conventions (`agent-activity`, `spinner`).

## 7. Tests to write

### `libs/agentos-ui/src/lib/components/case-chat/wizz-trigger.spec.ts` (new, pure unit)

- Not armed: an agent message then IDLE → false (history replay case, AC3).
- Armed: an agent message then IDLE → true, then a second IDLE → false (once per answer).
- Armed: TextChunk, user message, ToolRequest / ToolResponse, AgentRunning, AgentFinished, RUNNING, PENDING
  → always false (AC3).
- Armed, with an AgentFinished between two agents (handoff), two agent messages, then IDLE → exactly one true (D3).
- Armed, IDLE with no agent message (warning-only turn) → false (D2).
- Armed, then KILLED or ERROR → false, and a later IDLE → false.
- `disarm()` before IDLE → false.

### `case-chat.component.spec.ts` (extend, same fake-`EventSource` pattern as the existing specs)

- Off by default: `wizzEnabled()` is false, and a local send, an agent message and IDLE leave `wizzEffect()` null (AC1).
- `toggleWizz()` flips the state twice (on, then off).
- On: `submit()` a message, emit an agent `MessageEvent` then `CaseStatusEvent IDLE` → `wizzEffect()` is `'shake'`
  (AC2). This test would fail before the change.
- On: **history replay** (connect, emit a past user message, an agent message and IDLE **without** a local send) →
  `wizzEffect()` stays null (AC3).
- On: a reconnection replays the same agent message and IDLE ids after a wizz → no new effect (dedup branch).
- On: only `TextChunkEvent`s and tool events, no IDLE → null (AC3).
- On: `matchMedia` mocked to `matches: true` for `(prefers-reduced-motion: reduce)` → `'highlight'` (AC5).
- On: send, then `interrupt()`, then IDLE → null (D2).
- `onWizzAnimationEnd` with `target === currentTarget` clears the effect. With a child target, it does not.
- `reinitialise()` keeps `wizzEnabled()` and disarms the trigger (D5).

The existing specs must keep passing unchanged (the component is created without `matchMedia`).

### Reviewer attention (neighbouring behaviours)

- The `onEvent` call must stay **after** the dedup early return and **before** the per-type branches that
  `return` (TextChunk, CaseUpdated, CaseStatus, AgentFinished, ToolResponse, Question).
- No change to `isRunning` transitions, `runningAfter`, the terminal-close debounce, or the magnetic auto-scroll and focus
  effects.
- The keyframes use `transform` (shake) and `box-shadow` (highlight) only: no `margin`, `left`, `width` or `height`,
  and no `animation-fill-mode: forwards`.
- `animationend` from child animations must not cut the effect short.
- The toggle is a native button with `aria-pressed` and a visible focus ring.
