## Expected outcome

An accessible Wizz toggle, initially off and not persisted, produces one short conversation-panel shake when a new agent answer finishes, or a motionless highlight under reduced motion, without affecting scroll or final layout.

This is a feature, not a bug; reproduction steps and a bug root cause are not applicable.

## Acceptance criteria

From the ticket (no comments, attachments or linked tickets were returned):

1. A visible Wizz toggle in the conversation is off by default and clearly indicates its enabled state.
2. Enabled mode shakes only the conversation panel briefly when a new agent answer finishes.
3. Exactly one effect per completed answer; none per streaming fragment, user message, tool call or technical event. History loading must never trigger it.
4. No effect on scroll position or final layout.
5. `prefers-reduced-motion: reduce` substitutes a brief highlight without motion.
6. Accessible name, native keyboard operation, exposed on/off state, existing visual and translation conventions.
7. Frontend only, no sound, new dependency, agent-engine change or backend change. Reuse an existing completion signal. Do not persist the setting.
8. Add frontend tests for activation, single completion, excluded events/history and reduced motion; visually check scroll/layout.

User clarification in this session: frontend only remains mandatory; use the workstream branch naming convention. No reduction to locally initiated turns was approved.

Architect-derived operational rules (not additional ticket claims):

- D1: Eligibility is based on the existing live-only SSE option, never on a local send, browser/server timestamp comparisons, a quiet-time debounce, or a guessed history boundary.
- D2: One answer means one agent execution that produced at least one nonblank AGENT MessageEvent and reached AgentFinishedEvent. Intermediate text messages within that execution do not animate; a finish without an answer does not animate. A handoff without an answer does not animate; two agents that each actually answer are two completions, not one case-IDLE animation.
- D3: New answers from other members' turns and from turns already running at opening are eligible when their answer and completion arrive on the live observer. No requirement to observe a local send or AgentRunningEvent first.
- D4: Turning off cancels the observer and visual effect immediately. Switching case resets Wizz to off (no persistent preference); switching back requires explicit activation. No catch-up animations for completions missed while disabled or disconnected.
- D5: QuestionEvent alone is not a completed answer message; tools, warnings and technical finishes cannot trigger on their own. A finish following ErrorEvent/AgentSelectedEvent clears an unmatched candidate rather than attributing an earlier message to a later execution.

## Scoped implementation, file by file

### Frontend: new `libs/agentos-ui/src/lib/components/case-chat/wizz-completion-observer.ts`

Component-scoped, narrowly named observer: owns only the optional live EventSource and response-completion eligibility. Keep it framework-light with an injectable EventSource factory/callback for tests; no new package, shared global event bus or runtime state store.

- `start(basePath, caseId, onAnswerCompleted)` opens exactly one EventSource at `${basePath}/api/cases/${caseId}/events?includePreviousEvents=false`; stop any preceding instance first. No connection while Wizz is off.
- Listen only to `case-event`, decode payload by `type`, validate matching caseId and required message/actor fields defensively. Invalid payload must not break the observer or main chat.
- Track distinct live event ids within this activation, independent of the main chat's replay dedup. A history frame from the main connection must never enter this observer.
- Track the pending nonblank AGENT message actor id for the current agent execution. AgentRunningEvent/AgentSelectedEvent start a new execution and clear stale candidates. User/Answer events clear stale candidates. ErrorEvent and terminal case statuses clear candidates. Tools/chunks never create candidates.
- On AgentFinishedEvent, consume the matching actor/agent candidate once and invoke callback once; then clear it even when there is no candidate. Do not require a local action or observed run-start, so mid-run opening works when the final message arrives live. Blank/tool-only finishes do nothing. Preserve the last candidate per execution rather than animate for each intermediate MessageEvent.
- On transport error clear pending candidates. Native reconnection reuses the URL with `includePreviousEvents=false`; never replay missed completions. Preserve handled ids for the same activation; reopening after disable starts a fresh live-only subscription.
- `stop()` closes source, removes handlers and clears state. A generation/source identity guard rejects callbacks from a source already closed on disable, navigation or destroy.
- Do not write the timeline, change running state, call HTTP mutation endpoints or emit file/status refresh notifications.

Trade-off: one additional same-origin SSE connection only while explicitly enabled. Do not open a per-case background observer or change the main connection. This is the smallest reliable frontend-only use of the existing live-vs-history distinction; duplicating every event into application state is unnecessary. Browser connection-budget validation below is mandatory; if it regresses normal chat in the supported deployment, stop and revisit the frontend subscription design, not the backend or acceptance criteria.

### Frontend: `case-chat.component.ts`

- Add local `wizzEnabled = signal(false)`, observer lifecycle, panel ref and animation ownership. Toggle starts/stops observer for the current case; no changes in postMessage, voice, question answering, runningAfter or main SSE ingestion.
- Completion callback checks current activation/case and enabled state and schedules the effect after rendering the answer. Cross-connection arrival order must not affect timeline correctness; Wizz never inserts an event into the main stream.
- Use a single owned Web Animation on the panel element (native Element.animate, no dependency). At every completion, cancel the preceding owned animation before starting a new short effect. No repeated DOM reflow tricks or uncancelled animationend listeners.
- Query matchMedia at playback: reduced motion selects inset-shadow highlight, otherwise small translateX keyframes ending at identity. The MediaQueryList listener belongs ONLY to the current playing effect, never the enabled session. Remove it on finish, cancel, replacement, disable, navigation and destroy. A preference change may replace a currently running shake with a motionless highlight, but must never start an effect after completion or cancellation. Identity-guard old animation callbacks so they cannot clear a replacement. Guard absent animation/media APIs in tests and teardown; no effect failure can interrupt chat. See the correction addendum below for the required regression and cleanup ordering.
- Disabling, case reinitialisation and destruction cancel pending render callbacks/animation and stop observer. Reset toggle on case switch. Never manipulate scroll or focus for Wizz.
