# WZ-36203 — Opt-in Wizz on completed agent answers

## Outcome and delivery context

Give the reader an initially disabled, accessible Wizz toggle that produces one short conversation-panel-only cue for each newly completed agent answer, replacing movement with a stationary highlight under reduced motion and leaving scroll and final layout unchanged.

## Acceptance criteria

Ticket criteria (not inferred):

1. A visible Wizz button in the conversation toggles the effect; off initially, clearly marked when on.
2. When on, completion of a new agent answer briefly shakes the conversation panel, never the whole page.
3. One cue per finished answer; none for text chunks, user messages, tools, technical events, or history load.
4. The effect itself changes neither scroll position nor final element layout.
5. prefers-reduced-motion replaces shaking with a brief stationary highlight.
6. Accessible label, native keyboard operation, exposed on/off state, and project visual/language conventions.
7. Frontend only: no sound, dependency, backend/agent-engine modification, or persistence; reuse the existing finish signal.
8. Add relevant frontend coverage for toggle, unique completion, excluded events/history and reduced motion, with visual scroll/layout validation specified for implementation review.

Derived design criteria (explicitly inferred):

- Reset to off when changing/reopening a case or destroying the view; never carry pending cues across cases. Retry may preserve the enabled choice but must discard pending correlation from the old connection.
- A finish without a non-empty agent MessageEvent in its run is not an answer. Technical finishes, handoffs with no answer, tool-only runs and QuestionEvent-only pauses do not cue. A visible summary at an iteration limit or an in-channel confirmation message does count when that run finishes; the ticket does not require successful task execution.
- Toggling on does not retroactively cue an already finished answer. Toggling off cancels pending/active effects. Missed completions during disconnection are not replayed as delayed Wizz cues.
- At most one extra live-only SSE connection per enabled chat; zero while off. No writes or stored preferences are introduced.

## Architecture decision and scoped implementation

Choose **frontend only**. No new backend contract or route is needed. Do not guess live provenance from timestamps, an onopen event, debounce, isRunning, or seeing a TextChunkEvent: none separates persisted history safely for every answer path.

Use the existing live-only option as a small, opt-in provenance side channel. Keep the normal history-bearing chat stream intact. This costs one extra connection only while enabled, deliberately trading a bounded connection cost for correct history exclusion without a backend change. Do not generalize all SSE ownership or refactor the chat's HTTP calls in this ticket.

### Completion correlation algorithm / internal frontend contract

- While enabled, connect only the displayed case with includePreviousEvents=false. Record only matching-case AgentFinishedEvent IDs as live provenance; never insert side-channel events into chat history or invoke existing chat side effects from them.
- Reconcile each live finish against the same finish ID in the ordered normal chat events. Both arrival orders must work; do not discard a live finish merely because normal replay/display has not yet reached it. This ensures the answer is displayed before its cue.
- For that finish, inspect the run segment since the previous AgentFinishedEvent, AgentRunningEvent or user MessageEvent boundary. Require at least one nonblank AGENT MessageEvent whose actor.id matches finish.agentId; use its last matching answer. Never borrow an earlier run's answer. Handle repeated agent runs and agent handoffs explicitly. Do not require llmUsage.
- If present in normal events but no matching answer, consume the finish without cue. If eligible and still enabled/current generation, consume before emitting exactly one completion notification. Duplicate finishes/reconnect replay and timeline recomputation cannot re-cue.
- Clear pending provenance and cancel animation on disable/retry/reset; keep consumed identities across off/on and same-case retry, so delayed duplicate delivery cannot animate twice. Reset all identities on case change/reopen and destruction. Late callbacks from old subscriptions are ignored via generation guard.
- Turning on opens a fresh live subscription; old default-stream finishes alone never qualify. A response finishing after activation may qualify even if its run started earlier. Do not require a new AgentRunningEvent on the side channel.
- Normal history recovery is not a cue recovery mechanism: an answer finished while disconnected is displayed but does not Wizz after replay. This intentionally favours no false historical cues.
- For consecutive legitimate finishes during an animation, serialize the short cues rather than dropping one or restarting indefinitely. Cancel queued effects when disabled or the case changes. No UI focus movement or new scroll calls; keep Wizz state independent of timeline/streaming computations.

## Risk and boundaries for review

**Risk: medium**, despite a small visual feature. Main risks are replay/live confusion, cross-stream ordering, stale callbacks, connection budget, and transform/scroll interactions. Review the existing handoff, terminal-close debounce, file refresh and usage pairing beside the new hooks; none should be rewritten.

The side channel is best-effort while disconnected, and adds one HTTP/1.1 socket per enabled chat. The recent #1616/#1618 connection-budget work makes prompt teardown important. Keep off by default and never open hidden per-case streams speculatively. Do not silently broaden this ticket into transport redesign. Suggested separate follow-up (not created here): shared per-case multiplexing or an explicit replay/live boundary enabling side effects on one chat connection, including hidden-tab and HTTP/1.1 budget handling. Persistence of Wizz, sounds, global notifications, nested delegation-panel effects and translation-framework adoption are out of scope.

No application source was modified, and no build, test, lint or application check was run in this architecture step. This is a scoped design verdict, not an implementation correctness verdict.
