# WZ-36203 — Wizz on completed agent answers

## Expected outcome

An accessible, initially disabled Wizz toggle makes only the conversation panel briefly shake once when a new agent answer finishes, with a motionless highlight for reduced-motion users and no Wizz-induced scroll or final layout change.

No application code is changed by the architecture step. This plan supersedes neither another run's branch nor its implementation without review.

Ticket criteria:

1. A conversation button labelled Wizz toggles the effect, off by default, with a clearly visible active state.
2. Enabled mode gives a short shake of the conversation panel, not the page, at the end of a new agent answer.
3. Exactly one trigger per completed answer; never from chunks, user messages, tools, technical events or history loading.
4. The effect changes neither scroll position nor final layout.
5. `prefers-reduced-motion: reduce` replaces movement with a short highlight.
6. Keyboard-operable, accessible name and exposed toggle state; existing visual and translation conventions.
7. Frontend only; no sound, new dependency, engine/backend change or persisted preference. Reuse an existing completion signal.
8. Automated frontend coverage for toggling, completion, exclusions, history and reduced motion, plus visual scroll/layout verification.

Derived design decisions (not additional reporter requirements):

- D1: one answer means one agent execution that produced at least one persisted AGENT MessageEvent and then an AgentFinishedEvent. Multiple intermediate messages in that execution cause only one effect. A handoff with no answer produces none; two agents each finishing an actual answer may each produce one effect. Do not redefine the criterion as one per whole case IDLE transition.
- D2: toggle is component-local, reset to false on a case switch and lost on destruction/reload. No user-preference API or localStorage.
- D3: events first observed while disabled are consumed, not played retroactively after enabling. Clearing/disabling, switching cases and destroying cancel pending visual work.
- D4: no replay recovery of effects missed while disconnected. A cosmetic notification must not be reconstructed from history.

## Minimal implementation, by file and side

### Frontend — new `libs/agentos-ui/src/lib/components/case-chat/wizz-completion.ts`

A small framework-free correlator, independently unit-tested. It does not own HTTP/SSE, preferences, the DOM or scroll.

Inputs: an explicitly live AgentFinishedEvent from the global stream and the current ordered per-case event collection (or incremental equivalent). Output: newly eligible completion ids. Keep state per displayed case generation and clear it on switch/destroy.

Rules:

1. Only a matching current case and namespace is eligible. Reject other cases/subcases and missing identifiers defensively.
2. Deduplicate global completion ids for the generation **even when disabled**. Only retain a candidate for playback if enabled at live receipt; no historical backlog on enabling.
3. Reconcile on BOTH sources. The global completion may arrive before or after its per-case counterpart; never assume transport ordering. Require the same finished id in the per-case collection before deciding answer eligibility.
4. At that finish, inspect the execution segment since the preceding AgentRunningEvent (or previous AgentFinishedEvent/user-turn boundary). Require a nonempty persisted AGENT message belonging to that finishing agent (`actor.id === agentId`); a user message/tool-only/empty segment is not an answer. Existing ordered timeline helpers are a model; keep this logic independent of technical/tool display toggles and usage fields.
5. Consume the candidate once its segment is known, whether it qualifies or not; emit at most once per finished id. Never trigger from MessageEvent, TextChunkEvent or CaseStatusEvent alone.
6. Pending candidates must not leak across case switches, stream failure/retry, disabling or destruction. Clear pending candidates on these lifecycle boundaries; do not replay missed completions after reconnect. Retain dedup knowledge for an unchanged case while cancelling pending work. No long-lived global cache.

Do not introduce timer-based guesses about replay completion or arm only on a local send. If an observed production sequence contradicts the actor/execution association, add a fixture and resolve the association before implementation completion; do not weaken the history guard.

### Frontend — `.../case-chat.component.ts`

- Inject GlobalStreamService. Subscribe locally with takeUntilDestroyed; do not call a separate transport or restart the app-wide stream.
- Add `wizzEnabled = signal(false)` and transient animation state. The component owns only view state and the correlator instance, not a new app-wide state service.
- Feed matching global completions to the correlator, and reconcile after new per-case events have been appended. Keep the existing duplicate-event early return and all running, streaming, exchange-refresh, terminal-close and focus behavior intact.
- Use current event collection when a global event arrives so an already-rendered per-case finish is handled. A per-case finish already present at the time of live receipt must still be eligible.
- Trigger a bounded CSS animation on `.case-chat` only. A CSS class with a finite animation and an animationend cleanup is sufficient. Restart on a distinct completion during playback by cancelling prior scheduled restart and removing/reapplying the class across rendered frames; never accumulate indefinite animation jobs.
- Clear state on disable/reinitialise/destroy; cancel RAF/timers and guard stale callbacks by case generation. Ignore bubbled child animationend events (`target !== currentTarget`). Clear only the matching Wizz animation, not child activity animations.
- Visual signals must not be dependencies of existing scroll effects; do not call scrollToBottom, modify scrollTop, rebuild timeline entries or move focus as part of Wizz.

### Frontend — `.../case-chat.component.html`

## Verification and completion gates

Pure/unit sequence matrix:

- Disabled by default; enabled/disabled transitions and no retroactive cue for a completion first seen disabled.
- Historical AGENT message + per-case finish, even after enabling => no trigger without a global live completion.
- Live global finish plus matching per-case answer/finish => one trigger, in both transport arrival orders.
- Repeated global ids, repeated per-case replay, unrelated namespace/case/subcase => none extra.
- Many chunks/user messages/tool requests/responses/statuses => no trigger. Pure tool-only or no-answer execution => none even with live finish.
- Multiple AGENT messages in one execution => one trigger. Handoff without an answer => none for that segment; next answering agent => one. Separate completed answers => one each.
- Case switching, disable, destroy, retry/transport failure clear pending visual work. Late candidate from an old case must not animate the new one. Reconnect history never generates a fresh cue.
- Confirm completion still works for a live collaborator turn and for a case opened mid-execution when the existing global stream delivers its finish; no local post prerequisite.
- Child animationend does not clear Wizz; own end clears it. Closely spaced distinct answers restart safely; no stale frame restarts after disabling.

Browser checks (Playwright, plus visual review):

- Role/name/aria-pressed assertions, Tab focus, Enter and Space toggling, active state discernible, compact mobile viewport reachable.
- Normal motion: only `.case-chat` animates. Header, drawer, shell and final bounds are unchanged.
- `page.emulateMedia({ reducedMotion: 'reduce' })`: non-moving highlight keyframe, no transform throughout, cleanup at end. Repeat after preference change while enabled.
- Seed sufficient history; scroll above bottom to break magnet; record messages.scrollTop and layout sizes before cue, during and after. Compare with identical completion with Wizz disabled to separate existing content auto-scroll from the effect. Also test at-bottom magnetic scrolling remains unchanged.
- No permanent classes, transforms, outer scrollbars or layout shifts after effect; no audio and no extra EventSource/API calls.

Existing suites to remain green: case-chat.component.spec.ts, case-chat.utils.spec.ts, turn-metrics.spec.ts, global-stream.service.spec.ts, composer-scroll.spec.ts; especially replay dedup, PENDING, agent handoffs, terminal close/reopen, attachments, voice, focus and scroll.
