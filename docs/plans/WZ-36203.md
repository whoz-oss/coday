# WZ-36203 — Conversation Wizz implementation plan

## Expected outcome

An accessible, default-off Wizz toggle gives one brief visual effect on the conversation messages panel when a newly observed live agent response finishes, never on history replay, without effect-induced scrolling or final layout changes; reduced motion uses a stationary highlight.

Ticket: https://whoz.atlassian.net/browse/WZ-36203
Type: User Story (feature, not a bug). Reproduction/root-cause analysis is not applicable.

## Ticket evidence and acceptance criteria

The ticket has no comments, attachments, linked tickets or subtasks. Its explicit scope is frontend only, no sound, dependency, persistence, engine or backend changes.

Explicit acceptance criteria:
1. A visible `Wizz` conversation toggle is off by default, can be switched on/off, and clearly shows its active state.
2. When enabled, a newly completed agent response causes a short shake of the conversation panel only, never the whole page.
3. Exactly one trigger per completed response: not per streaming chunk, user message, tool call or technical event. Loading history never triggers it.
4. The effect does not alter scrolling or final layout.
5. `prefers-reduced-motion: reduce` replaces shaking with a brief highlight without movement.
6. Accessible label, native keyboard interaction and exposed toggle state; follow local visual and language conventions.
7. Add frontend coverage of toggle, completion uniqueness, intermediate/history exclusions and reduced motion, plus browser verification of scroll/layout.

Derived implementation criteria (not additional reporter requirements):
- Scope the effect to `.case-chat__messages-region`, leaving header, composer, sidebar and exchange drawer stationary.
- Reset opt-in and pending effect state on case switch/component teardown. No local/session storage or user preference/API writes.
- A finish without a new non-empty AGENT message is not a response completion. Match message actor ID to the finishing agent ID, not display name.
- Discard uncertain completions across transport errors/retry/reopen. Prefer skipping an unobserved completion to animating replay; resume after new transient activity. This is a deliberate frontend-only limitation, not a claim that SSE exposes a history/live boundary.

## Recommended minimal design

Keep this a presentation feature owned by CaseChatComponent, with a small colocated, framework-independent completion tracker. No app-wide state service, event bus, generalized animation framework or SSE refactor.

### Completion eligibility

Call the tracker only for newly accepted, current-case events after the existing duplicate-ID guard. It returns a single boolean/pulse request on AgentFinishedEvent, not from computed timeline state.

1. Start unarmed on mount/new case, enable and every connection boundary. Enabling does not inspect or animate the current timeline. Disabling clears pending candidates and cancels an active effect.
2. Arm only after observing a new ThinkingEvent or non-empty TextChunkEvent while enabled on the current uninterrupted connection. Neither one triggers an animation. These transient events cannot come from persisted history under the current protocol; FIFO history-first delivery makes them evidence that subsequent accepted frames are live/buffered-live.
3. Track the latest new non-empty MessageEvent with actor.role `AGENT` after that evidence. A user MessageEvent/AnswerEvent or a new AgentRunningEvent/AgentSelectedEvent resets the candidate/evidence for the next agent/turn. Never let a message from an earlier run or agent qualify a later finish. Thinking/chunks within the same run may update evidence without triggering effects. Tools themselves never qualify as an answer or trigger an effect.
4. At AgentFinishedEvent, require an armed live candidate with actor.id equal to agentId, current caseId, and new completion id. Consume/reset eligibility regardless of match, then issue at most one pulse. Multiple intermediate AGENT messages before one finish still produce one pulse; repeated finish events cannot re-trigger because of the component's existing dedup guard and consumed candidate. A handoff/tool-only finish without a matching response produces none. An iteration-limit finish with an actual new answer can qualify; it is feedback that text completed, not a success indicator.
5. Clear pending eligibility on ErrorEvent, terminal/IDLE case status, QuestionEvent, transport error, reconnect `open`, explicit retry, case reinitialisation and teardown. Preserve unrelated chat handling and file refresh semantics. Use an EventSource instance/generation guard so late callbacks from an old connection cannot arm or pulse the newly selected case. Attach `open` handling without relying on it as a history/live marker.

Conservative edge: a client connecting after the last transient frame, or a producer emitting no transient activity, gets no Wizz for that already-in-flight response. Do not silently substitute client/server timestamp comparisons or timing heuristics. Universal notification of completions not observed live would require a separate protocol/product ticket; it is not a backend change in WZ-36203.

### Toggle and visual effect

Add a small native `button type="button"` labelled `Wizz` in the existing conversation header, next to non-destructive actions. Bind `aria-pressed` and a visible active treatment using design tokens (not colour alone: e.g. a check mark, aria-hidden). Native button provides Tab/Enter/Space semantics, focus-visible ring and stable accessible name. Do not use a host-only aria attribute on ds-icon-button that misses the internal native button. Keep mobile actions reachable.

Bind a scoped pulse class to `.case-chat__messages-region`. Use a short approximately 300 ms, small horizontal transform shake returning to identity, without changing width/height/margins/borders/scrollTop. Under `prefers-reduced-motion: reduce`, replace the animation name with a stationary inset-box-shadow/highlight animation; there must be no translation, rotation or scaling at any phase. Keep the same finite duration and cleanup for both variants. Do not animate the page/body/host/drawer or re-create the scroller/messages in order to restart an animation.

Use one cleanup/restart path: clear class, schedule class re-add on the next rendered frame when restarting, cancel any pending frame and finite-duration cleanup timer when disabling, switching case or destroying. Guard animationend by target and animation name so child animations cannot clear it. A timer fallback avoids leaving a stale class when animations do not dispatch animationend. Cancel/restart (do not queue) if distinct completions occur during an effect; event eligibility remains once per completion. Do not focus/scroll as part of Wizz. Existing content-driven auto-scroll remains unchanged.

## Verification and regression risk

Risk: **medium**. Visual blast radius is local, but replay, handoff, connection lifecycle and scroll are sensitive. No application code has been changed or tests executed in this architecture-only step; the following is the implementation verification gate, not a claim of test success.

Unit sequence matrix:
- Disabled by default; toggle/enable alone does nothing; disable cancels active/pending effect; case switch resets opt-in.
- Enabled: Running -> Thinking/chunks -> matching AGENT text -> Finished yields exactly one pulse, only at Finished. Multiple chunks and multiple intermediate messages yield no earlier pulse.
- New second turn gives one additional pulse. Repeated finish id, duplicate AGENT frame or an additional finish with no candidate gives none.
- Initial history Running -> AGENT -> Finished -> IDLE with no transient frames gives zero, even when Wizz is enabled during delayed replay. Replay after error/retry likewise gives zero; subsequent live activity works again.
- Thinking -> Finished with no answer, user text, tool request/response, status/technical events, question, agent mismatch, prior-run message and handoff-only finish give zero.
- Non-streaming AGENT answer following observed Thinking qualifies. Connection after all transients is intentionally suppressed. Pure technical frames never independently trigger Wizz.
- Interrupted/error run, late old-source callbacks, case switch, reopen and destroy cannot leak a pending pulse. Existing duplicate branch must still restore running state where appropriate.
- Fake timers/frame callbacks verify finite cleanup, rapid distinct completions and no stale callback after disable/destroy. Child animationend cannot prematurely clear the panel effect.

Browser (new Playwright spec, mocked APIs and controllable fake EventSource; no real mutations/LLM):
- Button accessible name `Wizz`, aria-pressed false/true, visible active mark, native Enter/Space and visible keyboard focus.
- Normal mode runs a single local shake, reduced-motion mode a stationary highlight (assert computed animation name and transform at sampled phases, not just source CSS). Switching the OS media preference while mounted is respected via CSS.
- Only messages region moves; header/composer/sidebar/drawer remain fixed; final bounding boxes match initial values. Test both default and small viewport and open exchange drawer.
- With a long conversation scrolled away from the bottom, capture scrollTop and scroll dimensions immediately before/after the pulse and ensure unchanged within pixel tolerance. At bottom, compare Wizz on/off for the same content: ordinary magnetic scroll is allowed, no extra effect-induced change. Highlight never changes geometry. Verify no focus change attributable to toggle/pulse beyond native button interaction and existing composer behaviour.
