# WZ-36203 — opt-in Wizz on completed agent answers

## Outcome and ticket framing

Add an initially disabled, accessible Wizz toggle to the conversation: while enabled, one newly completed agent answer produces a brief conversation-panel-only shake, replaced by a stationary highlight for reduced motion, without changing scroll or final layout.

Source: https://whoz.atlassian.net/browse/WZ-36203 — **User Story**, not a bug. There is no defect root cause or reproduction requirement. Description, comments, attachments and links were read: no comments, attachments, issue links or duplicates were supplied. Parent **WZ-34898**, “Forge > Delivery Workflows • November 2026”, describes delivery workflows, not additional Wizz behaviour. The launch instruction explicitly requests this Factory execution despite the older backlog/no-run planning paragraph. No scheduling fields are to be edited.

### Acceptance criteria from the description

1. A conversation button labelled **Wizz** toggles the mode; default off, clearly visible active state.
2. When active, the end of a new agent answer causes a short shake of the conversation panel only, never the whole page.
3. Exactly one trigger per completed answer; none for streaming chunks, user messages, tools, technical events or history loading.
4. The effect itself changes neither scroll position nor final element layout.
5. `prefers-reduced-motion: reduce` replaces motion with a brief stationary highlight.
6. Accessible label, native keyboard operation and exposed on/off state; follow local visual and translation conventions.
7. Frontend only; reuse the existing completion signal; no sound, dependency, persistence, backend or agent-engine change.
8. Add frontend coverage for toggling, unique completion, negative events/history and reduced motion; inspect scroll/layout visually at implementation review.

### Derived implementation decisions (not extra reporter requirements)

- Setting belongs to the displayed conversation instance and resets off on case switch, reopen/reinitialisation and component destruction. No local storage, user preference or server write.
- A completed answer means a non-empty durable AGENT MessageEvent followed by its AgentFinishedEvent in that agent run. A run with only tools or no answer is not an answer. Multiple durable messages in one run still cause one cue at the finish, not one cue per message. A limit-summary answer still counts if present; the flag is not a success discriminator. A QuestionEvent alone does not count. An in-channel confirmation phrased as an AGENT message does count when its run finishes. This follows the visible message model, not tool-name heuristics.
- Once a new finish has been considered, disabling/re-enabling must not replay it. Effects queued for the old conversation/activation are cancelled.
- This is an ephemeral visual affordance, not a durable notification: no catch-up after an auxiliary stream outage, and no attempt to fabricate a cue for events before the live subscription exists. Ordinary conversation history and operation must work even if the cue channel fails.

## Architecture and scoped file changes

**Chosen route: frontend only.** The API-client custom adapter is browser code, not backend work. No API/schema/payload or Kotlin change is needed.

A separate opt-in **live-only** subscription is the smallest reliable frontend-only way to distinguish new completions without changing the existing history stream. It costs **one extra per-case SSE connection per enabled chat**, zero while off. It must close promptly on disable, terminal case, case switch and destroy. Browser HTTP/1 connection limits remain a risk; do not open one for every background case or add a new global fan-out. Replacing the history protocol would be a separate initiative.

### 1. `libs/agentos-api-client/src/custom/case-event-sse.service.ts` (frontend transport)

Extend `connect` with optional options, e.g. `connect(caseId, { includePreviousEvents?: boolean })`. Keep the existing URL/default behaviour unchanged when options are omitted; explicit false appends `?includePreviousEvents=false`. Keep stable `case-event` discrimination, native reconnect and unsubscribe cleanup. Describe that false has no replay/catch-up; do not change generated services/models or regenerate the client.

### 2. `libs/agentos-ui/src/lib/components/case-chat/case-chat-wizz-state.service.ts` (new component-scoped frontend state)

Own enabled state, activation generation, auxiliary adapter subscription, pending finish IDs and consumed finish IDs. Provide this service only on CaseChatComponent. No application-wide preferences or new HTTP mutations.

On enable, open the live-only stream for the current case; ignore non-finish frames for triggering. Filter finish payload by exact current case ID. On each finish record the finish ID for correlation; deduplicate auxiliary duplicates. Reconcile against a **pure** completed-answer mapping from the main ordered events, keyed by finish ID. It must work whichever stream arrives first: a live finish may wait for the main timeline to ingest that same finish, and a main finish may already be present when the live stream reports it. Never join on “latest message”, timestamps, a name or isRunning. A main/history finish without auxiliary live provenance is never eligible.

Build a small pure helper in this file (or `case-chat-wizz.utils.ts` if clearer) that walks main events in order. Reset the candidate on AgentRunningEvent, a new USER message/AnswerEvent, agent selection changes and every finish; retain only non-empty AGENT messages with actor.id matching the finishing agentId in that run. A matching finish with no candidate consumes the finish with no cue. Reset/invalidate on terminal/error boundaries so a later empty finish cannot borrow an old answer. Do not couple eligibility to token usage or visibility of technical logs. Do not mutate or append to the conversation's domain events from this service.

Emit one presentation trigger only after both provenance and a correlated displayed answer exist, marking the finish consumed before emitting. Retain consumed IDs for the displayed-case lifetime across disable/enable; drop pending IDs on disable or stream error. Ignore callbacks from a previous activation using a generation guard; clear everything on case reset. Main stream replay may complete a genuinely live pending finish, but cannot independently create one. Cap pending work (e.g. latest 100 pending finishes) so a broken main feed cannot accumulate indefinitely; consumed IDs are bounded by the loaded case event set. Bind subscriptions to destruction.

### 3. `libs/agentos-ui/src/lib/components/case-chat/case-chat.component.ts` (frontend presentation integration)

Inject the scoped state service. Feed current case/reset lifecycle and the main events signal to reconciliation; state changes must not be inserted into timeline events. Keep existing SSE handler, dedup, running state, exchange refresh and scroll logic intact. React to eligible triggers with a one-shot class/animation restart on the existing messages-region element after rendering. Cancel any pending animation/frame work when disabled, case changes or component is destroyed. For rapid distinct completions, restart the short effect without losing event dedup; never replace the scroll container DOM node or force a reflow of the conversation as a restart mechanism.

Keep an explicit generation check in delayed render callbacks. Reset off in reinitialise; terminal state closes the auxiliary subscription. Auxiliary failure must not set the conversation's streamUnavailable or disable its composer.

### 4. `libs/agentos-ui/src/lib/components/case-chat/case-chat.component.html` (frontend UI)

Add a native `button type="button"` with visible **Wizz**, stable accessible name (e.g. “Wizz on completed agent replies”), `[attr.aria-pressed]`, active styling and focus-visible ring. Native Enter/Space and tab order require no keydown workaround. Place it in the conversation actions without hiding it during an ordinary run. Bind the cue class/end cleanup to `.case-chat__messages-region` so header, composer, drawers and page remain stationary. Preserve the `#messagesContainer` identity and existing floating scroll button.

### 5. `libs/agentos-ui/src/lib/components/case-chat/case-chat.component.scss` (frontend styles)

Use existing design-system mixins/tokens for the toggle, readable active/inactive distinction beyond colour alone (e.g. pressed border/background plus On/Off text), and keyboard focus. Add one short transform-only shake (about 300ms, small alternating horizontal translation, identity at both endpoints, one iteration). Reduced-motion media rule must **replace**, not merely disable, it with a brief inset-shadow/background highlight, no transforms. No border-width, padding, margin, height, scrollTop, scrollIntoView or layout-affecting animation; no selector on body/root/drawer. Class removal must handle the reduced-motion animation name too. Keep page horizontal overflow unchanged and do not create a new scrollbar during the effect.

### Backend side / existing contract (read only)

No backend implementation route. Existing request is `GET {Configuration.basePath}/api/cases/{caseId}/events?includePreviousEvents=false` (same Case READ permission as the normal conversation stream). Frames: `event: case-event`, `id: <stable UUID>`, JSON CaseEvent; the eligible lifecycle payload is `{ type: 'AgentFinishedEvent', id, caseId, namespaceId, timestamp, agentId, agentName, ... }`. Answer data stays in the main stream's `MessageEvent` with `actor.role === 'AGENT'`, `actor.id`, and non-empty content. No new field or network contract; no reliance on global membership notifications.

## Test scenarios to write and review

1. Default off; click, Enter and Space toggle state without network mutation; on/off label, aria-pressed and focus stay coherent. Only enabled mode owns the auxiliary connection.
2. Main history containing full running/message/finish sequences causes zero effects, even while an enabled auxiliary connection opens. Main replay on reconnection also causes none on its own.
3. New AGENT message + matching live finish + main finish produces one cue in **both inter-stream arrival orders**. Multiple chunks/messages produce none until finish; distinct later answers each produce a cue; duplicate finish IDs and main replay do not repeat it.
4. Ignore USER/AnswerEvent, tool request/response, thinking, status, selection, error, warn and delegation lifecycle as triggers. Finish with no non-empty matching answer produces none; a previous run's answer and another agent's message cannot be reused. Limit-summary and in-channel confirmation semantics above are explicit fixtures.
5. A completion received before disable cannot be replayed on re-enable. Old-case/old-generation callbacks and delayed render callbacks cannot shake the new case. Reset/reopen returns off; terminal/destroy/disable close the extra connection and cancel pending work.
6. Auxiliary connection error/outage never changes normal chat running/status/composer/history. Restored live subscription never requests history; missed cues are not replayed. Namespace-only reader uses the same case stream and works without a global-stream event.
7. Rendered normal mode animates messages region only and returns to identity; rapid consecutive completions restart cleanly. Reduced-motion emulation shows highlight with **no transform at any sampled point**. Toggling the OS preference while active must not reintroduce motion.
8. With long history and user scrolled up, record message scrollTop and scrollHeight before cue after new content has settled, during and after it: the cue alone must not change either. At bottom, normal content auto-scroll remains as before. Header/composer/sidebar/drawer/document boxes and final panel geometry stay unchanged; no horizontal overflow; check narrow and short windows as well as desktop. Visual review confirms a small, short cue rather than whole-page shake.
