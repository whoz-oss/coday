# WZ-36203 — Wizz implementation plan

## Expected outcome and scope

An accessible, default-off Wizz conversation toggle produces one brief panel-local effect when a newly observed live agent response finishes, never on history replay, without changing scroll position or final layout, and substitutes a stationary highlight for reduced motion.

## Acceptance criteria

Explicit in ticket:
1. Visible `Wizz` toggle in the conversation, disabled by default, clearly showing its active state.
2. When active, a newly finished agent answer triggers a short shake of the conversation panel only, never the page.
3. Exactly one effect per completed answer, not per streaming fragment, user message, tool call or technical event. Loading history never triggers it.
4. No effect-induced scrolling or change to final layout.
5. `prefers-reduced-motion: reduce` uses a brief highlight without movement.
6. Accessible label, native keyboard usability and exposed on/off state; follow project visual and translation conventions.
7. Frontend only; reuse existing completion signal; no sound, persistence, dependency, backend or agent-engine change.
8. Frontend tests for toggle, unique completion, intermediate/history exclusions and reduced motion; visual verification of scroll/layout stability.

Derived implementation criteria (not additional reporter requirements):
- Affect `.case-chat__messages-region`, leaving header, composer, sidebars and exchange drawer stationary.
- Reset opt-in on case switch/reopen and teardown. Disable cancels pending/active effects; enabling alone never animates existing content.
- Require a new non-empty AGENT text message matching the finishing `agentId` by `actor.id`; never use display names for correlation.
- Conservatively skip completions whose live activity was not observed on an uninterrupted connection. No timestamp or timeout heuristic to identify live events.

## Minimal design

Keep the feature presentation-local to CaseChatComponent with a small colocated pure completion tracker. No new global state service, event bus, network request or SSE architecture refactor.

### Completion eligibility

Feed tracker only accepted current-case/current-source events AFTER the existing duplicate-ID guard. Suggested local interface: `reset(): void`, `accept(event: CaseEvent): boolean`; component owns enabled state and invokes reset on toggle/lifecycle boundaries. `true` means one pulse request, only ever returned for AgentFinishedEvent.

1. Start unarmed on mount, enable, case change and every connection boundary. Toggle off cancels active animation and resets tracker. No inspection of existing timeline.
2. A fresh ThinkingEvent or non-empty TextChunkEvent while enabled arms live evidence but never triggers. These are not replayed from persistence; history-first FIFO ensures subsequent newly accepted frames follow that evidence. Do not arm on Running/Selected/status alone: they are durable.
3. After evidence, remember the latest new non-empty AGENT text message. USER MessageEvent, AnswerEvent, new AgentRunningEvent or AgentSelectedEvent clears previous evidence/candidate so another agent or turn cannot inherit it. Multiple Thinking/chunk frames within one run do not themselves produce pulses; intermediate AGENT messages remain candidates, never triggers.
4. On AgentFinishedEvent, require live evidence and a matching current-case candidate with actor.id === agentId. Consume eligibility regardless of match; return at most one pulse. Existing event-ID dedup plus consumption rejects repeated finishes and multiple message/chunk fragments. Finish without answer produces none. Iteration-limit finish with new answer still qualifies: feedback means text finished, not task succeeded. An in-channel confirmation text followed by finish is an agent response; typed QuestionEvent without such response is not.
5. Reset eligibility on ErrorEvent, QuestionEvent, IDLE/KILLED/ERROR status, transport error, new connection/open, retry, reinitialise and destroy. Guard stale EventSource callbacks with source identity/generation and caseId before they can affect Wizz. Preserve unrelated chat side effects and duplicate running restoration.

Known conservative edge: history reads may already include a message/finish that also appears in the buffered live queue; server dedup can place it before transient evidence. Likewise connecting after all transient activity or enabling after its last frame yields no Wizz for that in-flight answer. This is intentional replay safety, not a claim of universal completion delivery. Subsequent fully observed live turns work. No replay marker, clock comparison, idle-delay or alternate live-only stream is introduced. If universal notification of unobserved completions is required later, propose a separate protocol/product ticket for explicit history/live provenance, not a backend change here.

### Toggle and visual effect

Add native `button type="button"` labelled Wizz beside non-destructive header actions. Bind `aria-pressed`, visible active treatment plus check/indicator (not colour alone), focus-visible styling and stable accessible name. Native Tab/Enter/Space semantics; do not put ARIA only on a custom-component host whose internal button misses it. Keep small-viewport actions reachable without redesigning header.

Apply a finite, approximately 300 ms small horizontal transform shake to `.case-chat__messages-region`, returning to identity. No width/height/margin/border/focus/scroll changes or DOM recreation. Under `prefers-reduced-motion: reduce`, replace with stationary inset shadow/highlight keyframes with no transform at any phase. CSS media query responds to preference changes while mounted. Header/composer/drawers must not move.

Use one restart/cleanup path: reset pulse class, re-add after a rendered frame when restarting, cancel pending frame and cleanup timer on disable/case change/destroy. Filter animationend by target/name so child animations cannot end it; finite timer fallback avoids a stuck class. Distinct rapid completions restart rather than queue effects. Keep pulse/enabled signals separate from timeline/scroll dependencies; normal content-driven magnetic scrolling is unchanged.

## Verification and regression risk

Risk: **medium**. Local visual scope, but sensitive ingestion/replay/handoff and scrolling behaviour. Architecture-only step: no application code changed; no build, test run or visual validation claimed. Implementation gate:

Unit sequence matrix:
- Default disabled; enable alone no pulse; disable cancels; case switch/reopen returns off.
- Running -> Thinking/chunks -> matching AGENT text -> Finished: exactly one pulse at finish only. Multiple chunks/intermediate messages remain zero until finish. Second turn gives one additional pulse.
- Duplicate message/finish IDs and second finish with no candidate cannot retrigger. Preserve existing duplicate-branch running restoration and file-refresh dedup.
- Initial/delayed history Running -> AGENT -> Finished -> IDLE without transient evidence produces zero, including toggle-on during replay; reconnect/retry replay likewise zero. Fresh live turn after replay works.
- Thinking -> Finished without answer, user messages, tools, technical events, typed QuestionEvent, actor mismatch, stale prior-run text and handoff-only finish give zero.
- Non-streaming text after observed Thinking qualifies. Interrupted/error run and old-source callbacks after switch/destroy do not leak a pulse.
- Fake timers/frame scheduling prove bounded cleanup/restart, disable/destroy cancellation and child animationend exclusion.

Browser tests with fake EventSource and API routes (no real mutations/LLM):
- Actual native button name, false/true aria-pressed, visible active indicator, keyboard Tab/Enter/Space and focus ring.
- Normal mode local shake; reduced mode stationary highlight. Assert actual computed animation/transform during sampled phases, not only CSS source. Change media preference while mounted.
- Long conversation scrolled away from bottom: capture scrollTop and scroll dimensions before/after finish; unchanged within pixel tolerance. At bottom compare Wizz on/off with identical content so ordinary magnetic scrolling is not mistaken for effect-induced movement.
- Compare bounding boxes after animation; only messages region moves during normal animation; header/composer/sidebar/drawer stationary. Check open drawer, light/dark themes and desktop/narrow/short viewports.
- Manual visual inspection of amplitude, duration, layout and focus in both motion modes.

Keep existing case-chat attachment/voice/question, handoff/running restoration, terminal replay/debounce, retry/deletion probes, exchange refresh and turn metrics tests green; retain composer-scroll browser coverage.
