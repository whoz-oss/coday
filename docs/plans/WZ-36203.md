## Acceptance criteria

Explicit ticket criteria:

1. A conversation button labelled Wizz toggles the mode; initially off; active state clearly visible.
2. While active, a completed new agent response produces a short shake of the conversation panel only, not the page.
3. One effect per completed response, never per streaming fragment, user message, tool operation or technical event; historical loading produces none.
4. The effect changes neither scroll position nor final layout.
5. `prefers-reduced-motion: reduce` replaces shaking with brief non-moving emphasis.
6. Accessible label, keyboard operation and exposed on/off state; follow local styling and translation conventions.
7. Frontend only: no sound, dependency, persistence, backend or agent-engine change. Reuse the existing completion signal.
8. Add relevant frontend tests and visually verify stable scrolling/layout.

Derived implementation criteria (not verbatim ticket requirements):

- For v1, eligible means live activity observed, then a new agent message, then its matching completion, on one uninterrupted connection. Prefer a missed decorative effect to history/reconnect false positives. This limitation is also recorded in prior plan PRs #1682/#1683; it is not a new backend guarantee.
- Reset observation on disconnect/retry, case change/reopen and teardown. Reset the opt-in to off on case reinitialisation; never use user preferences or browser storage.
- Disabling cancels an active effect and pending eligibility; re-enabling does not animate an already completed answer.
- A tool-only run or handoff with no agent message does not qualify. Multiple messages within one agent run produce one effect at its finish, consistent with the existing turn model. Each subsequent qualifying agent run may produce its own effect.

## Minimal scoped change, by file and side

**Route: frontend only.** No backend implementation, API contract change, server configuration or generated client changes.

1. **New `libs/agentos-ui/src/lib/components/case-chat/wizz-response-tracker.ts`** — small pure per-component state machine, no Angular/DOM/HTTP. Feed only newly accepted events after the existing dedup return. Track live-activity observation and pending agent-message identity; return a qualifying completed response identity or null. Keep no second global event history.
   - Start/reset disarmed. A new ThinkingEvent or nonempty TextChunkEvent arms live observation; it never triggers an effect itself.
   - After that, a newly accepted nonempty AGENT MessageEvent records `{messageId, actorId}` for this run. User messages and a new agent selected/running boundary clear stale candidates; require fresh activity for each run. Tool/technical events do not create candidates or trigger effects.
   - A matching AgentFinishedEvent (`agentId === actorId`, same case) consumes the candidate and clears run observation before returning an identity. A finish without candidate or a mismatching finish produces no effect and clears observation. Do not compare display names or timestamps as identity.
   - Status IDLE/KILLED/ERROR and transport lifecycle reset observation. Existing SSE dedup handles duplicate event ids before this tracker; consuming the candidate also prevents a second differently-id'd finish from replaying an answer.
   - Do not scan persisted arrays to recover eligibility after reconnect: responses completed while disconnected intentionally do not Wizz. An unstreamed response with no observed ThinkingEvent also intentionally does not Wizz in v1.
2. **`case-chat.component.ts`** — local default-false signal, toggle, tracker instance, one presentation trigger and bounded cleanup. Integrate tracker at the existing new-event ingestion boundary without changing existing per-type branches, running state or exchange refreshes. Trigger only while enabled. Reset tracking and cancel visuals on disable, stream errors (including automatic reconnect), connect/retry, terminal close, reinitialise and destroy. Guard Wizz handling against stale EventSource callbacks/case identities without refactoring the transport. Never put this side effect in a computed/effect over `events()`.
3. **`case-chat.component.html`** — native `type="button"` with visible `Wizz`, stable accessible name (e.g. `Wizz mode`), `[attr.aria-pressed]`, title/help and visibly distinct enabled state in the composer actions. Native Enter/Space behaviour; visible keyboard focus. Bind only the messages-region effect class/trigger and its cleanup event, not the page/host, header, composer or drawer.
4. **`case-chat.component.scss`** — small local token-based button styles; approximately 300 ms low-amplitude transform-only shake with identity at start/end. Animate the fixed-size messages region, not its scroll content. No dimension/margin/padding/border-width changes, no DOM remount, no scrolling/focus calls. CSS `@media (prefers-reduced-motion: reduce)` replaces shake with same-duration background/inset-highlight keyframes containing no transform. Use one finite animation and clear the class on its own animationend (ignore child bubbling), with bounded cleanup fallback if needed. Cancel/restart the presentation for a new qualifying response arriving mid-effect; do not queue delayed effects or force synchronous layout reads.
5. **New `.../case-chat/wizz-response-tracker.spec.ts`** — table-driven pure tracker coverage below.
6. **`case-chat.component.spec.ts`** — ingestion, opt-in and cleanup tests using existing EventSource mocks, plus a rendered focused fixture to verify actual button ARIA/state/placement (existing non-rendered tests alone are insufficient).
7. **New `apps/client-e2e/src/case-wizz.spec.ts`** — narrowly mock API/SSE using composer-scroll precedent; expose fake per-case event source emission. Real DOM geometry/keyboard/reduced-motion tests. Keep helpers local unless an existing shared helper already fits; do not refactor unrelated tests.

## Existing wire contract (read-only dependency)

`GET /api/cases/{caseId}/events`, default history included; SSE `event: case-event`, JSON discriminant `type`. Common fields: `id`, `caseId`, `namespaceId`, `timestamp`, `metadata`. Eligible sequence: transient ThinkingEvent / TextChunkEvent (`chunk`) → MessageEvent (`actor: {id, role: 'AGENT'}`, nonempty content) → AgentFinishedEvent (`agentId`). All in the currently displayed case and one uninterrupted connection. Use stable event ids for dedup and actor/agent ids for matching. Keep channel compatibility and existing endpoint/query parameters unchanged. No cross-side implementation coordination is needed.

## Verification criteria

Automated tracker/component tests:

- Off by default; toggle on/off; no API/storage writes; disabled mode never triggers. Enabling alone/history already present does nothing.
- Many chunks/thinking frames → matching agent message → finish produces exactly one effect, at finish only. Two separate runs, including same-agent successive runs, each produce one.
- Pure persisted replay containing selected/running/message/finish creates none, including replay with new-to-this-component ids. Duplicate replay after reconnect creates none.
- User message, Question/Answer, tool-only run, status, warning/error, selected/running and delegate/subcase events alone never trigger. Mismatched agent/case, empty message and finish without new message never qualify.
- New run boundaries cannot inherit the previous candidate. Multiple messages in one run yield one finish effect. Duplicate or extra finishes do not retrigger.
- Disconnect between activity/message/finish, retry, switch/reopen and destruction clear eligibility and pending presentation; late old-source callbacks do not affect the new chat. New observed live activity after reconnect can qualify again.
- Button is a native button with accessible label and `aria-pressed` toggling false/true; visible pressed/focus states. Disable cancels active effect; no retrospective effect when enabled again.
- Animation cleanup and rapid consecutive completion restart leave no stale class/timer; nested animationend does not cancel the region effect.

Browser tests and visual checks:

- Keyboard Tab/Space/Enter operates the button without sending a message; Wizz active is clear in light/dark themes and narrow widths.
- With many messages, scroll upward, emit completion, verify the effect does not change scrollTop or scroll dimensions; after settling, panel/header/composer/drawer/page bounding boxes match the pre-effect values. At bottom, compare against Wizz-off normal message auto-scroll: new content may scroll normally, but the effect adds no displacement.
- Under `page.emulateMedia({ reducedMotion: 'reduce' })`, computed animation is highlight-only, transform remains none throughout, highlight is visible briefly then gone. Normal mode moves only messages region and returns to identity; no horizontal page scrollbar.
- Preserve selection, composer focus behaviour, magnetic scroll and scroll-to-bottom anchor, streamed text clearing, exchange refresh dedup, usage figures, technical-log toggles, terminal/reopen and handoff behaviour.

## Risk and exclusions

**Risk: medium**, concentrated in replay/live distinction, lifecycle cleanup and existing scrolling, not in backend state. The transient gate is intentionally conservative; there is no explicit protocol replay boundary or run id. Do not replace it with age thresholds, debounce guesses or a second SSE stream (connection-budget regression).

Out of scope: sound, preferences persistence, backend/motor changes, prototype thread UI, global notifications, shared design-system refactoring, global i18n adoption or existing SSE cleanup. If product later requires guaranteed feedback for every nonstreaming or disconnected response, propose a separate ticket for explicit replay/live and run-correlation protocol metadata rather than weakening this decorative feature's history safety.
