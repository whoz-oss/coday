# WZ-36045 — Retry a failed workflow step

Jira: https://whoz.atlassian.net/browse/WZ-36045 (User Story, epic WZ-36044 "FP - Forge - Feb 2027")
Base branch: `workstream/forge/master` — work branch: `work/forge/WZ-36045-retry-failed-step`
Sides: **backend** (factory-service, Kotlin) and **frontend** (factory-cockpit, Angular).

## 1. Expected outcome

When an **agent** step of a Factory run has failed, the operator can click **Retry** in the Cockpit, optionally add
information, and Factory reruns **that same step in the same run and the same AgentOS case** as a new attempt N+1.
The new attempt gets the original brief, the previous attempt's result and the operator text. The rest of the run then
continues normally. The run does not restart from the beginning.

## 2. Acceptance criteria

From the ticket:
1. A failed step offers a Retry action.
2. Selecting Retry reruns that step and does not restart the workflow.
3. The retry receives the original context enriched with the previous attempt's result.
4. The status and result of the new attempt are visible in Factory.

Decided with the requester (benjamin.valdes, design discussion of this step):
5. *(derived)* Before retrying, the operator can add **optional** free text (0–4000 characters).
6. *(derived)* The retry runs in the **same AgentOS case / worktree** as the failed attempt, so the agent keeps its
   conversation history.
7. *(derived)* Scope is **agent steps only**. Code and human steps do not offer Retry in this ticket.
8. *(derived)* Runs with **outcome transitions** (`projection.stepExecutions`) do not offer Retry: their failure routing
   is automatic.
9. *(derived)* **Cancelled** runs stay closed. Only a step (and a run) in `failed` can be retried.
10. *(derived, answers the open question "previous result unavailable")*: the retry still runs. The brief keeps the
    original context and says explicitly that the previous result could not be retrieved, plus the failure code/message
    when the evidence has one.
11. *(derived)* The command is fenced on the revision, idempotent (`Idempotency-Key`), and audited (actor, text,
    predecessor and successor attempt ids).
12. *(derived)* Dependent steps that were blocked **only because of this failure** go back to `pending`. Steps blocked by
    another real failure stay blocked.

Open question "visual reference": no dedicated design. The UI reuses the existing "Complete and resume" card
(NEEDS_RESEARCH) in `action-bar`.

## 4. Analysis of the current code (root cause of "Retry does nothing useful")

Today the Retry button can never work for a failed step:

- `factory/factory-service/src/main/kotlin/io/whozoss/factory/workflow/service/WorkflowService.kt`
  - `workflowActions(...)`, branch `WorkflowStatuses.FAILED ->`, emits `retry` for **every** failed step (agent, code
    or human), even when the run is sealed. It is fenced on the **projection-row** revision (`revision`) instead of the
    instance revision.
  - `openRetry(...)` rejects anything that is not `blocked` (`"Only a blocked step can be retried."` →
    `INTERACTION_STALE`). So the cockpit call for a failed step always fails.
  - Even for a blocked step, `openRetry` only opens a `retry` human interaction, and approving it
    (`replyInteractionTransactional`, `requestedStatus = "completed"`) **marks the step completed** without rerunning it.
- `WorkflowModels.kt`: `FAILED` is terminal (`TRANSITIONS[FAILED] = ∅`), and `assertNotSealed` rejects any mutation
  of a run whose status is `completed|failed|cancelled` (Phase 10 seal).
- `apps/factory-cockpit/.../action-bar/action-bar.component.ts` `requestRetry` → `FactoryStore.retry` →
  `FactoryApiService.openRetry` → `POST /retries`.

What already exists and must be reused:
- `WorkflowService.resumeResearch(...)`: idempotency, revision fence, re-arming the step to `ready`, resetting
  dependents to `pending` (`rootStepId == stepId && cause == dependency_non_success`), projection publication, durable
  submission `sessionRunSubmissionService.submit(..., "resume-research:<successorId>")`.
- `capability/NeedsResearchRouter.resume(...)`: registers attempt N+1 through `DurableAgentAttemptService.registerRetry`
  with the **same `caseId` / `rootCaseId` / `parentCaseId` / environment**, its own capability
  (`issueSuccessorCapability`), a brief rewritten with the successor ids (`successorBrief`) and a re-pinned envelope
  (`successorEnvelope`).
- `CapabilityExecutionService.resolveAgentViaAdapter` then follows `findLatestForStep` (the successor), replays its
  **frozen** brief/envelope and reuses its case. No change is needed there.

Recent history: `WorkflowService.kt` changed often (outcome transitions 0623ff39, #1710, #1701, #1684). Regression risk
areas: actions/blockers read model, the seal, the outcome-transition ledger, and worktree occupancy.

## 5. Design decision: governed exception to the seal

A failed run stays sealed for **every** mutation except **one** command: the human-triggered "retry failed agent step".
The exception is written in code and KDoc (update the `assertNotSealed` KDoc and `WorkflowStatuses.TERMINAL` KDoc):

- Only run status `failed` can be reopened, never `completed` or `cancelled`.
- An authenticated actor is required, the command is fenced on the instance revision, idempotent, and audited by a
  dedicated evidence item.
- The step state machine is **not** changed (`TRANSITIONS[FAILED]` stays empty). Like `resumeResearch`, the retry
  rewrites the step to `ready` through an explicit governed command, not through the generic transition policy.
- Excluded: steps that are not agent steps, runs with `stepExecutions`, parent-Run fragments (`instance.runId` /
  `relations.runId`), see §8.

## 6. Contract (backend ⇄ frontend)

### 6.1 Allowed action (changed)
`GET /api/factory/workflows/{id}/actions` → `allowedActions[]` item, **unchanged shape**:
```json
{ "type": "retry", "stepId": "<stepId>", "expectedRevision": <INSTANCE revision>, "label": "Retry failed step '<stepId>'" }
```
Emitted only when **all** these are true: step projection status `failed`, step responsibility kind `agent`, instance
run status not `completed` / `cancelled`, no `stepExecutions` in the projection, not a parent-Run fragment, and the
latest durable attempt of the step is terminal. The `ATTEMPT_FAILED` blocker stays as is.

### 6.2 New command
`POST /api/factory/workflows/{workflowId}/steps/{stepId}/failed-step-retries`
Headers: `Idempotency-Key` (required, 1–128 chars), `X-Namespace-Id` (as the other commands).
Body (no other field accepted):
```json
{ "namespaceId": "<ns>", "expectedRevision": 12, "additionalContext": "optional, 0..4000 chars" }
```
`additionalContext` may be absent, `null` or blank: it is then treated as empty.
Response `201` (or `200` with `"idempotent": true` on replay):
```json
{ "data": { "workflowId": "…", "stepId": "…", "attemptId": "<successor>", "previousAttemptId": "…",
            "attemptNumber": 2, "revision": 13, "idempotent": false, "submissionId": "…", "queued": true } }
```
Errors (existing codes, `{ error: { code, message } }`):
- `REVISION_CONFLICT` 409: stale `expectedRevision` or lost compare-and-set.
- `IDEMPOTENCY_KEY_COLLISION` 409: same key, different payload (`IdempotencyKeyCollisionException`).
- `INTERACTION_STALE`: step not `failed`, latest attempt not terminal, or no durable predecessor/frozen context.
- `ACTION_NOT_ALLOWED`: not an agent step, `stepExecutions` run, parent-Run fragment.
- `WORKFLOW_SEALED`: run `completed` or `cancelled`.
- `INVALID_REQUEST`: unknown field, context over 4000 characters, missing key, or repository root not resolvable.

## 7. Scoped change per file

### Backend (implement first)

1. `factory/factory-service/src/main/kotlin/io/whozoss/factory/workflow/service/WorkflowService.kt`
   - New `@Transactional fun retryFailedStep(scope, namespaceId, workflowId, stepId, expectedRevision, additionalContext: String?, actorId, idempotencyKey): WorkflowHttpResult`.
     Same structure as `resumeResearch`:
     a. idempotency lookup with scoped key `failed-step-retry:${scope.workstreamId}:$namespaceId:$workflowId:$stepId:$key`
        and a JSON request hash (workflowId, namespaceId, stepId, expectedRevision, normalized context, actorId);
     b. validate context length ≤ 4000 (after `trim()`, empty allowed);
     c. `activeInstance`; run status must be `failed`, otherwise the existing `assertNotSealed` path applies (so
        `completed` / `cancelled` → `WORKFLOW_SEALED`). For a non-terminal run, still require that the step is
        `failed`;
     d. revision fence on `instance.revision`; guards from §6.2 (agent kind, no `stepExecutions`, not a fragment);
     e. predecessor = `durableAgentAttemptService.findLatestForStep`: it must exist, be `status.terminal` and not
        `SUPERSEDED`, and have `brief` + `contextEnvelope` (otherwise `INTERACTION_STALE`, same rule as research);
     f. previous result: `agentStepResultService?.acceptedResult(..., predecessor.attemptId)` (summary, findings,
        artifacts), else the last `agent-result` evidence of that attempt (`facts.code` / `facts.message` / `reason`),
        else "unavailable";
     g. `needsResearchRouter.retryFailed(...)` (below) → successorId;
     h. **extract** the existing "re-arm step + reset dependents + CAS instance + upsert step states + publish
        projection + resolve repo root + submit" block of `resumeResearch` into a private helper
        `rearmStepAndSubmit(scope, namespaceId, workflowId, instance, definition, stepId, expectedRevision, actorId, operation)`
        and call it from both (`operation = "resume-research:$id"` / `"retry-failed-step:$id"`). The behaviour of
        `resumeResearch` must stay identical. Its existing tests are the guard;
     i. save the idempotent response, SSE publish, return 201.
   - `workflowActions(...)`, `FAILED` branch: emit `retry` only under the §6.1 conditions, with
     `expectedRevision = instanceRevision`. Resolve the step kind from `resolveDefinition` (guard with `runCatching`, no
     retry offered if it fails) or from the projected `responsibility.kind`. Keep the final `stepExecutions` filter.
   - KDoc of `assertNotSealed`: document the single governed exception.
   - Do **not** touch `openRetry` / `replyInteraction` (legacy BLOCKED flow). Propose its removal in a separate ticket.
2. `factory/factory-service/src/main/kotlin/io/whozoss/factory/capability/NeedsResearchRouter.kt`
   - New `fun retryFailed(scope, namespaceId, workflowId, step, predecessor: DurableAgentAttempt, previousResult: FailedAttemptSummary, additionalContext: String, actorId): String`.
     It mirrors `resume`:
     - append audited evidence `kind = "failed-step-retry"`, `outcome = "accepted"`, `source = {kind: "factory-failed-step-retry", actorId}`,
       facts `{attemptId, successorAttemptId, previousFailureCode, previousResultId?, additionalContext}`,
       `idempotencyKey = "failed-step-retry:$successorId"`;
     - bounded `resumptionContext` JSON `{reason: "FAILED_STEP_RETRY", previousAttemptId, previousResultId, failureCode, summary (shrunk first), additionalContext, retryEvidenceId}` ≤ `StepQuestionLimits.RESUMPTION_CONTEXT_BYTES`;
     - brief = `successorBrief(predecessor, successorId, retrySupplement(...))` with the section below. The operator
       text is fenced by `<<<` and `>>>`:
       ```
       ## Retry of a failed attempt
       A previous attempt of this step failed and an engineer asked to retry it in the same case.
       Previous result: <summary / failure code+message, ≤1000 chars> | "The previous result could not be retrieved."
       [Information supplied by the engineer:
       <<<
       …
       >>>]
       Fix the cause of the failure and complete the same step. Submit your result with the identifiers above;
       do not reuse identifiers of the previous attempt.
       ```
     - `registerRetry` with the predecessor's `caseId`, `rootCaseId`, `parentCaseId`, `environmentRef`,
       `expectedEnvironmentRevision`, `expectedAmendmentSeq`, its own capability (`issueSuccessorCapability`) and
       `successorEnvelope`.
   - Small data class `FailedAttemptSummary(resultId: String?, failureCode: String?, summary: String?, findings: List<*>)`, in the same file.
   - Update the class KDoc: the router owns the *governed successor attempts* (research and failed-step retry). Renaming
     the class is out of scope.
   - **Worktree occupancy**: a failed attempt without an accepted result keeps its occupation (fail-closed, see
     `releaseAgentWorktreeIfResultAccepted`). In that case the successor would be deferred with
     `AGENT_WORKTREE_OCCUPIED`. Parent-Run fragments are excluded (§5). For a standalone adopted workspace, when the
     predecessor carries a full occupancy handle, `retryFailed` releases it with
     `WorktreeExecutionOccupancyService.releaseOwned` (owner- and generation-fenced) **before** registering the
     successor, and records `releasedOccupancy=true` in the retry evidence. The explicit human decision stands in for
     the accepted result. Inject `WorktreeExecutionOccupancyService?` as an optional constructor dependency. ⚠ Review
     point for the PR.

## 8. Out of scope (separate tickets proposed)

- Retry of failed **code** steps (rerun a verification in the same worktree).
- Retry inside **parent-Run fragments** (needs a Run-level policy and fenced worktree occupancy transfer).

- Renaming `NeedsResearchRouter` to a neutral successor-attempt name.

## 9. Verification criteria

New backend tests: `factory/factory-service/src/test/kotlin/io/whozoss/factory/workflow/WorkflowFailedStepRetryTest.kt`.
Use a mockk setup copied from `WorkflowResearchResumptionTest`, with a DAG where A failed, B and C are blocked by A, E
is blocked by another failed step F, and D is independent. Test cases:
- Fails before / passes after: `workflowActions` offers `retry` for a failed agent step with `expectedRevision` =
  **instance** revision, and `retryFailedStep` returns 201 with a successor. Today `openRetry` throws
  `INTERACTION_STALE`.
- A becomes `ready`, B and C become `pending`, E and F are unchanged, the run becomes `pending`, the revision is +1, and
  one durable submission `retry-failed-step:<id>` is queued.
- A run with status `failed` is accepted. `completed` and `cancelled` → `WORKFLOW_SEALED`, no mutation.
- No `retry` action and `ACTION_NOT_ALLOWED` for: code step, human step, `stepExecutions` run, fragment.
- Stale revision / lost CAS → `REVISION_CONFLICT`, nothing stored. Replay with the same key returns 200 idempotent
  without a second router call. Same key with another payload → collision.
- Context: absent and blank are accepted, 4000 is accepted, 4001 is rejected.
- The predecessor attempt and its evidence are never rewritten (no `finalize`, no evidence append except the router's
  audit).
- Latest attempt not terminal, or without frozen brief/envelope → `INTERACTION_STALE`.

`NeedsResearchRouter` unit test (add to the existing router test or create one):
- the successor keeps `caseId`, `rootCaseId`, `parentCaseId` and `environmentRef`, gets `attemptNumber` N+1, its own
  capability, and a brief with the successor ids;
- the brief contains the previous summary and the fenced operator text;
- without a previous result, the brief contains "could not be retrieved";
- the occupancy handle is released (owner-fenced) only when present.

- `factory.store.spec.ts`: stable key on retry, conflict and collision feedback.

Existing tests that must stay green: `WorkflowResearchResumptionTest` (guards the extracted helper),

## 10. Risk level

**Medium.** It is an explicit exception to the Phase 10 seal and it touches the actions read model. The worktree
occupancy release on retry is the most sensitive point. Mitigations: a single fenced and audited command, reuse of the
proven research-resumption machinery, narrow eligibility (agent, failed, non-fragment, non-outcome), and no change to
the step state machine or the execution adapter.

   then `retryFailedStep` and the `workflowActions` change, then the controller, then the tests.
