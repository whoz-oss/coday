# #1759 — Add rewind feature (AgentOS case chat)

Ticket: https://github.com/whoz-oss/coday/issues/1759 (GitHub issue. The description is empty, there are no comments and no linked Jira ticket.)
Work branch: `work/forge/issue-1759-rewind`. Base and PR target: `workstream/forge/master`.

## 1. Expected outcome

In the AgentOS case chat, a user can rewind an idle case to one of their own messages. That message and every later event are removed from the conversation. The case goes back to the state it was in just before the message, and the message text is put back in the composer so the user can edit it and send it again.

Type: feature (user story). The reporter (vincent.palita) confirmed the scope below during the design step. #174 / PR #210 delivered the same feature for the legacy Coday thread UI (`libs/ai-thread`, `apps/web-ng`). That code no longer exists, so this ticket brings the feature to AgentOS.

## 2. Acceptance criteria

Confirmed with the reporter, since the ticket body is empty:

1. A USER message bubble in the case chat offers a **Rewind** action. Agent messages, question answers and other timeline items do not offer it.
2. Rewind asks for confirmation first. It is a destructive action.
3. On confirmation, the message and every event after it are soft-deleted (`removed = true`). They disappear from the chat and from the history that later agent runs read.
4. After the rewind, the composer contains the text of the rewound message and nothing is sent. No agent runs on its own.
5. Rewind is refused while the case is `RUNNING` or `PENDING` (HTTP 409). The button is hidden or disabled in that state.
6. It needs WRITE on the case. Without it the server answers 403/404.

Derived by the architect:

7. Rewind is also refused (409) on a terminal case (`KILLED`, `ERROR`). The user reopens it first. This keeps the reopen and rewind lifecycles separate.
8. An event id that is not an active USER `MessageEvent` of this case is rejected: 404 if it is unknown or belongs to another case, 400 if it is not a user message.
9. After a rewind, the persisted history ends with a fresh `CaseStatusEvent(IDLE)`. A reconnecting client then replays a consistent state, with no stale RUNNING or KILLED status from the removed part.
10. The next message after a rewind is handled with the shortened history, both by a live runtime and by a rehydrated one.

Out of scope (confirmed): sub-cases created by delegations after the rewind point are left as they are. Exchange files are not touched. `UsageRecord`s are kept, so the cost already spent stays counted. There is no rewind to an agent message, no automatic re-send, no undo, and no live refresh of *other* connected viewers of a shared case (they see the change on their next reconnect or reload). See section 8.

## 5. Design

### Why the runtime must be involved
Soft-deleting the events in Neo4j is not enough. A live `CaseRuntime` (kept in `activeRuntimes` while a viewer is connected, or during the idle grace period) runs agents against its **in-memory** `InMemoryCaseEventList`, not the database. Without in-memory truncation, the next message would still send the removed turn to the LLM. Evicting the runtime instead is not acceptable either: the SSE subscribers of the shared case would stay attached to an orphaned flow. So the runtime gets a small truncation operation, and the service runs persistence first and memory second.

### Contract (frontend ⇄ backend)

```
POST /api/cases/{caseId}/rewind
Content-Type: application/json
{ "eventId": "<uuid of the USER MessageEvent to rewind to>" }

200 OK -> CaseDto (same shape as reopen; status IDLE)
400    -> eventId is not a USER MessageEvent
403/404-> no WRITE on the case / case unknown (HideOnAccessDenied semantics as other case endpoints)
404    -> eventId unknown, removed, or belonging to another case
409    -> case RUNNING, PENDING, KILLED or ERROR
```

- SDK request DTO: `RewindCaseRequest(eventId: UUID)` in `io.whozoss.agentos.sdk.api.case`.
- Generated Angular client: `CaseControllerService.rewindCase(caseId: string, rewindCaseRequest: RewindCaseRequest): Observable<Case>`. The operationId comes out as `rewindCase` because the method name already contains "Case".
- SSE side effect: the endpoint emits **one** live `CaseStatusEvent(IDLE)` (persisted too). Removed events are not announced. The requesting client reloads the history itself (see the frontend section).

### Backend — scoped change per file

1. `agentos-sdk/.../api/case/RewindCaseRequest.kt` (new): `data class RewindCaseRequest(val eventId: UUID)`.
2. `agentos-sdk/.../api/case/CaseApi.kt`: add `rewindCase(caseId: UUID, request: RewindCaseRequest): CaseDto` with an `@Operation` description that restates the contract above.
3. `caseEvent/CaseEventRepository.kt` + `Neo4jCaseEventRepository.kt` + test double `src/test/.../caseEvent/InMemoryCaseEventRepository.kt`: add `deleteFrom(caseId: UUID, eventId: UUID): Int`. It reads `findActiveByCaseId(caseId)`, locates the index of `eventId` in that ordered list, and soft-deletes the sublist from that index to the end with `saveAll(mapper.withRemoved(it, true))` inside `@Transactional`, like `deleteByParent`. It returns the count, or 0 when the id is not in the list. Deriving the cut from the ordered list, and not from a timestamp comparison, keeps the cut identical to what `findByParent` replays (`timestamp, id`).
4. `caseEvent/CaseEventService.kt` + `CaseEventServiceImpl.kt`: delegate `deleteFrom`.
5. `caseEvent/CaseEventList.kt` + `InMemoryCaseEventList.kt`: add `removeFrom(eventId: UUID): Int`. Under the write lock, find the index of the event in `events`, drop the tail from that index, and remove the dropped ids from `eventsById`. It returns the number removed, or 0 when the event is absent.
6. `caseFlow/CaseRuntime.kt`: add `fun rewindFrom(eventId: UUID): Int = eventList.removeFrom(eventId)`. Plain delegation: the status guard is the service's job, and the operation holds no lock and does no I/O. Also clear `commandQueue` and `pendingQuestionResumptions` there, so no queued command from the removed turn survives.
7. `caseFlow/CaseService.kt` + `CaseServiceImpl.kt`: add `rewindCase(caseId: UUID, eventId: UUID): Case`:
   - `findById(caseId)` returns 404 when the case is missing.
   - The status guard: `RUNNING`, `PENDING`, `KILLED` and `ERROR` give a `ConflictException`. The same goes when `activeRuntimes[caseId]?.isRunning() == true` or `hasRunningExecutions(listOf(caseId))` (an admitted gated launch).
   - The target event is loaded with `caseEventService.findById(eventId)`: missing, removed, or `caseId` mismatch gives a `ResourceNotFoundException`; not a `MessageEvent` with `actor.role == USER` gives a `BadRequestException`.
   - `caseEventService.deleteFrom(caseId, eventId)` persists the soft delete.
   - `activeRuntimes[caseId]?.rewindFrom(eventId)` updates memory. No rehydration happens when there is no live runtime: the next `getCaseRuntime` rehydrates from the already shortened persistence.
   - `handleStatusChange(caseId, CaseStatus.IDLE, postProcess = false)` persists and emits the fresh IDLE status. This meets AC9.
   - Return `findById(caseId)`.
   - Log at info: case id, event id, number of events removed.
8. `caseFlow/CaseController.kt`: add `@PostMapping("/{caseId}/rewind", consumes = [JSON])`, `@PreAuthorize("hasPermission(#caseId, 'Case', 'WRITE')")`, `@ResponseStatus(OK)`. It delegates to the service and returns `withCallerMeta(currentUserId)`, like `reopenCase`.
9. `agentos/openapi/agentos-openapi.yaml` and `libs/agentos-api-client/src/lib/**`: regenerate with `pnpm nx run agentos-service:regenerate`. Never edit them by hand.

Known race, accepted: the guard and the write are not atomic with a concurrent `addMessage`. The UI hides Rewind while a message is in flight. A message posted in the few milliseconds between the guard and the truncation could lose events. A comment in `rewindCase` documents this. The fix (a claim/release flag on the runtime) is out of scope.

### Frontend — scoped change per file

1. `libs/agentos-ui/.../case-chat/case-chat.component.ts`:
   - `protected readonly rewindTarget = signal<CaseMessageEvent | null>(null)` drives the confirmation dialog.
   - `protected canRewind(): boolean` returns `!isRunning() && !composerClosed() && !isTerminal() && canAttach() && !attachments.isUploading() && !voice.isBusy() && !submitting`.
   - `protected askRewind(event)` sets `rewindTarget` when `canRewind()`.
   - `protected rewind()` reads the target and its text (`extractText`), clears `rewindTarget`, and POSTs `${basePath}/api/cases/${caseId}/rewind` with `{ eventId: target.id }` through `this.http`, as `reopen()` does. Keep the component's direct-HTTP pattern here and do not add a state-service method for this one call. Guard against a case switch: capture `caseId` at call time and ignore the answer if it changed. On success, `caseState.updateCaseStatus(caseId, 'IDLE')`, `reinitialise()` (which clears and replays the shortened history), then `inputValue.set(text)` and focus the composer. On error, `console.error` and leave the chat unchanged.
2. `libs/agentos-ui/.../case-chat/case-chat.component.html`:
   - In `.case-chat__bubble-wrapper`, only for `item.event.actor.role === 'USER'` (plain and voice bubbles alike), add a `ds-icon-button` (icon `history` or `undo`, `title="Rewind to this message"`, `variant="default"`, class `case-chat__bubble-rewind`) next to the copy button, rendered when `canRewind()`. Question answers are rendered elsewhere and do not get it.
   - Add a second `ds-confirm-dialog` bound to `rewindTarget() !== null`. Title "Rewind to this message?". Message: "This message and everything after it will be removed from the conversation. Its text goes back in the composer so you can edit and resend it. Files, sub-cases and costs already spent are kept." Confirm label "Rewind", cancel label "Cancel". `(confirmed)="rewind()"`, `(cancelled)="rewindTarget.set(null)"`.
3. `libs/agentos-ui/.../case-chat/case-chat.component.scss`: position `.case-chat__bubble-rewind` like `.case-chat__bubble-copy` (shown on bubble hover and on focus, keyboard reachable). Use existing tokens only.

No change in `apps/client`, the Express server or the proxy: `/api/cases/**` is already proxied to AgentOS.

## 6. Verification criteria

Backend tests to add (Kotest):
- `InMemoryCaseEventListUnitSpec`: `removeFrom` drops the target and every later event, keeps the earlier ones, cleans `getById`, returns the count, and returns 0 with nothing changed for an unknown id. Add a same-timestamp case: events inserted before the target at an equal timestamp are kept.
- `AbstractCaseEventPersistenceSpec` (runs for embedded and Testcontainers Neo4j): `deleteFrom` soft-deletes the tail only, `findByParent` returns the head, another case is untouched, and an unknown id returns 0.
- `CaseServiceImplSpec`:
  - Rewind on an IDLE case with a live runtime: persistence is shortened, `runtime` history (through a following `addMessage` and the events the fake agent receives) no longer contains the removed turn, and the last persisted event is `CaseStatusEvent(IDLE)`.
  - Rewind with no live runtime: the next `getCaseRuntime` rehydrates the shortened history.
  - 409 on RUNNING, PENDING, KILLED and ERROR.
  - 404 for an unknown event, a removed event, or an event of another case. 400 for an agent `MessageEvent` and for a non-message event.
- `CaseControllerSpec`: `rewindCase` delegates and maps through `withCallerMeta`. `CaseControllerMvcIntegrationSpec`: `POST /api/cases/{id}/rewind` returns 200 with `status = IDLE` on a seeded case, and 409 on a KILLED case.

Frontend tests to add (Jest, `case-chat.component.spec.ts`, instance style):
- `rewind()` POSTs `/api/cases/c-1/rewind` with `{ eventId }`, then reinitialises (events cleared, SSE reconnected) and leaves the message text in `inputValue`.
- On HTTP error, the events and the input are unchanged.
- `askRewind` does nothing while `isRunning`, on a terminal case, or when `canWriteCase` is false.
- A case switch during the request does not refill the composer of the new case.

Existing suites that must stay green: `pnpm nx run-many -t lint test -p agentos-ui`, the AgentOS Gradle tests (`CaseServiceImplSpec`, `CaseRuntime*Spec`, `CaseEventSseController*Spec`, persistence specs), and `agentos/agentos-service/check-openapi-spec.sh` (the spec must be regenerated and committed).

Neighbouring behaviours to check by hand (`pnpm nx run web:local`): reopen after kill still works; the iteration-limit "Continue" notice disappears after rewinding before it; turn metrics, tool groups and delegation cards render correctly on the shortened timeline; a reload after rewind shows the same shortened history; the case title and summary are unchanged.

**Risk level: medium.** The change touches the runtime's in-memory history and the persisted event store of live cases. The status guard keeps the window small, the soft delete is reversible by hand in the database, and every change is additive (no existing endpoint or event type changes).

## 7. Chosen routes

**frontend** and **backend**. The change spans the AgentOS service (endpoint, service, persistence, runtime, SDK contract, regenerated client) and the Angular case chat (action, confirmation, composer refill). The routes run in either order:
- If **backend** runs first, it delivers the endpoint, the regenerated spec and the client. The frontend can use the generated `CaseControllerService.rewindCase` or a raw `http.post`, which matches the existing pattern of `reopen()`.
- If **frontend** runs first, it codes against the contract in section 5 with a raw `http.post` (no generated client needed) and mocks HTTP in the specs. It must not touch `libs/agentos-api-client`, which the backend route regenerates.
