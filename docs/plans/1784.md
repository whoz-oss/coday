# #1784 — The "New case" button makes no sense when already on home

Ticket: https://github.com/whoz-oss/coday/issues/1784. It is a GitHub issue with a title only: empty body, no comments, no linked ticket, so there is no Jira ticket to transition.
Work branch: `work/forge/1784-hide-new-case-on-home`. Base and PR target: `workstream/forge/master` (forge workstream).
Type: **improvement / UX bug** (frontend only).

## 1. Expected outcome

On the home composer (no case open, no sub-case being created), the "New case" buttons of the shell are shown **disabled**, because the user is already on a new case. Everywhere else they stay active.

- **Observed:** on `/agentos/home?ns=<id>` (no `case`, no `parentCase` query param), the primary "New case" button of the desktop sidebar (expanded and compact rail) and the "+" button of the mobile top bar are active. Clicking them calls `CaseShellComponent.onCreateRequested()`, which navigates to the same URL `/agentos/home?ns=<id>`: nothing happens. The most prominent call to action of the sidebar offers an action that does nothing.
- **Expected:** on that screen the buttons are disabled (not clickable, dimmed by the existing `.btn-primary:disabled` style) and their tooltip says why. As soon as a case is open (`?case=`) or a sub-case composer is shown (`?parentCase=`), they are active again and behave as today.
- **Reproduction:** complete from the title and the code (see §4). Open the app on a namespace with no case selected and click "New case".

**Design choice: disable rather than hide.** Hiding the button would make the sidebar top bar jump on every navigation between home and a case: in the wide layout the filter input would take the button's space, and in the narrow layout a whole row would disappear. A disabled button keeps the layout stable and still shows the user where the action lives. This is the architect's choice, since the ticket does not say which. If the reporter prefers hiding, the change stays in the same three templates (swap `[disabled]` for an `@if`).

## 2. Acceptance criteria

Derived by the architect, since the ticket body is empty:

1. On the home composer (`activeCaseId` null **and** no `parentCase` query param), these buttons are `disabled`:
   - the expanded sidebar "New case" button (`.shell-sidebar__new-case-btn`),
   - the compact rail "New case" icon button,
   - the mobile top bar "+" button (`.shell-topbar-mobile__new-btn`).
2. Their `title` (tooltip) becomes `Already on a new case` while they are disabled, and stays `New case` otherwise.
3. With a case open (`?case=<id>`), the buttons are enabled and still navigate to the home composer of the namespace (current behaviour).
4. In the sub-case composer (`?parentCase=<id>`, no `case`), the buttons are enabled: clicking them still leaves the sub-case composer for a top-level new case (current behaviour, which makes sense there).
5. The state follows navigation live: opening a case, deleting the active case (the shell navigates home), switching namespace and the browser back button all update the disabled state with no reload.
6. Nothing else changes: the case drawer's per-row "Create sub-case" buttons, the empty-list text, the home composer itself and the routes.

## 4. Root cause (single)

`libs/agentos-ui/src/lib/components/case-shell/case-shell.component.ts`, `onCreateRequested()` (and `onMobileCreateCase()`, which delegates to it), does:

```ts
this.router.navigate(['/agentos/home'], { queryParams: { ns: this.namespaceId() } })
```

The three buttons that emit `createRequested` are rendered unconditionally and always enabled:

- `shell-sidebar/shell-sidebar.component.html`, "Row 2: New case + Search" (expanded) and "New case button" (compact rail),
- `shell-topbar-mobile/shell-topbar-mobile.component.html`, "New case button".

When the current URL is already `/agentos/home?ns=<id>`, this navigation targets the same URL. The Angular router ignores a same-URL navigation by default (`onSameUrlNavigation: 'ignore'`, and the repo never overrides it), and `CaseHomeComponent` is already displayed. The click is therefore a silent no-op. No presentational component knows whether the shell is on the home composer, because `CaseShellComponent` only passes `activeCaseId` to the sidebar, which never uses it to gate the button, and does not read the `parentCase` query param at all.

## 6. Scoped change (frontend only)

Principle: the **shell** (smart) decides, the presentational bars only render one boolean input. This follows the existing split, where all state and navigation live in `CaseShellComponent` and the bars receive inputs.

### 6.1 `case-shell.component.ts`

- Next to `_activeCaseIdRaw` / `activeCaseId`, add a query param signal for the sub-case composer, written the same way:
  ```ts
  private readonly _parentCaseIdRaw = toSignal(this.route.queryParams.pipe(map((p) => (p['parentCase'] as string) ?? null)))
  protected readonly parentCaseId = computed(() => this._parentCaseIdRaw() ?? null)
  ```
- Add, in the "UI state" or "Cases" section, with a one-line JSDoc:
  ```ts
  /** True on the home composer of a top-level case: "New case" would navigate to the screen already shown. */
  protected readonly isOnNewCaseComposer = computed(() => !this.activeCaseId() && !this.parentCaseId())
  ```
- Leave `onCreateRequested()` and `onMobileCreateCase()` unchanged. A disabled button emits nothing, so a guard is not needed (and `onMobileCreateCase` must keep closing the drawer).

### 6.2 `case-shell.component.html`

- `<agentos-shell-sidebar …>`: add `[newCaseDisabled]="isOnNewCaseComposer()"`.
- `<agentos-shell-topbar-mobile …>`: add `[newCaseDisabled]="isOnNewCaseComposer()"`.

### 6.3 `shell-sidebar/shell-sidebar.component.ts` and `.html`

- TS: in the "Cases" input block, `readonly newCaseDisabled = input(false)` with the JSDoc `/** Disables the New case buttons: the shell already shows the new case composer. */`.
- HTML, on **both** New case buttons (expanded `.shell-sidebar__new-case-btn` and the compact rail `btn btn-primary btn-icon`):
  - `[disabled]="newCaseDisabled()"`,
  - replace the static `title="New case"` by `[title]="newCaseDisabled() ? 'Already on a new case' : 'New case'"`.
  - Keep `dsBlueprint`, the classes, the SVG and the label as they are.

### 6.4 `shell-topbar-mobile/shell-topbar-mobile.component.ts` and `.html`

- TS: `readonly newCaseDisabled = input(false)` (same JSDoc) in a small "Cases" block above the outputs.
- HTML, on `.shell-topbar-mobile__new-btn`: the same `[disabled]` and `[title]` bindings. The default `false` keeps any other host of these components unchanged.
