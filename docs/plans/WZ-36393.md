# WZ-36393 — Automatic step polling (max 30 min) and deterministic CI-check step with return to Architect

Jira: https://whoz.atlassian.net/browse/WZ-36393 (User Story, parent epic WZ-36044 "FP - Forge - Feb 2027")
Work branch: `work/forge/WZ-36393-ci-check-step-retry` → base `workstream/forge/master`
Sides: **backend** (factory-service, main part) + **frontend** (factory-cockpit, small). Backend first.

Scope decision (confirmed by the requester during framing): **full scope in this ticket** — non-terminal
`IN_PROGRESS` for code steps **and** agent steps, plus `outcomeTransitions.fail.return` allowed on the CI-check code step.

## 1. Expected outcome

A workflow step (the new deterministic `github-pr-checks` code step, or an agent step that submits `IN_PROGRESS`)
can report "external condition still pending"; Factory then parks the step in a new non-terminal status
`waiting_external`, frees the worker slot, and re-runs the step through a delayed outbox continuation every ~60 s,
for at most 30 min per step execution. A green CI finishes the step with PASS, a red CI finishes it with FAIL with the
failed checks and log excerpts captured, which triggers `outcomeTransitions.fail.return` (e.g. to `architect-design`),
and a CI still pending after 30 min fails the step with `POLL_TIMEOUT_EXCEEDED` (blocks, no return, no budget consumed).

## 2. Acceptance criteria

From the ticket:

- **AC1** A step (code or agent) can return a non-terminal IN_PROGRESS when the external process is neither succeeded
  nor failed. Code: the CI-check capability returns a pending outcome. Agent: the worker submits `status: IN_PROGRESS`.
- **AC2** Factory re-schedules the step through the outbox at regular intervals (default 60 s) without holding a worker
  thread, for up to 30 min (1800 s).
- **AC3** A deterministic CI-check executor polls GitHub PR checks without any LLM call while CI is pending.
- **AC4** After 30 min still pending, polling stops and the step fails with the explicit code `POLL_TIMEOUT_EXCEEDED`.
- **AC5** IN_PROGRESS polls never consume the `outcomeTransitions.fail.maxCycles` budget.
- **AC6** CI green → step PASS; CI red → failure details/logs captured and `fail.return` to the configured target.

Derived by Archay (flagged **[derived]**):

- **AC7 [derived]** The 30-min window is measured per **step execution** (`firstPollStartedAt` = first claim of the
  current `executionId`). A correction replay (new execution) gets a fresh window and a fresh poll counter.
- **AC8 [derived]** Only a *real CI verdict* (`verdict = failed`) of the `github-pr-checks` step is eligible for
  `fail.return`. Timeout, missing configuration, draft PR, missing PR, auth errors and any other refusal **block**
  (`return` not taken, budget not consumed). The return budget (`maxCycles`, default 2) and exhaustion → human wait
  are unchanged.
- **AC9 [derived]** `fail.return` is accepted by the definition validator on a code step **only** when
  `responsibility.name == "github-pr-checks"`; every other code/human step keeps `return_requires_agent_result`.
- **AC10 [derived]** Transient GitHub errors (network, 5xx, 429) are treated as "still pending" (next poll), not as
  failures; they still count against the 30-min window.
- **AC11 [derived]** The CI verdict is bound to the PR head SHA. If the local worktree HEAD is known and differs from the
  PR head SHA, the check is pending (`CI_HEAD_NOT_PUSHED`) — a stale green CI of an older commit never passes the step.
- **AC12 [derived]** A draft PR is refused (`CI_PR_IS_DRAFT`, blocks): `validate.yml` skips every job on drafts, so the
  checks would be "skipped" and could be misread as green. The CI step must be placed after the step that marks the PR
  ready for review.
- **AC13 [derived]** An agent step may submit IN_PROGRESS only on a non-decision PASS-less turn: `selectedRoutes` is
  rejected with IN_PROGRESS; an optional `retryAfterSeconds` (30–300, default 60) tunes the next poll.
- **AC14 [derived]** The run (and the run card) shows the run as active while a step is `waiting_external`; it is never
  shown failed or waiting for a human.
- **AC15 [derived]** Legacy definitions and runs (no `github-pr-checks` step, no IN_PROGRESS submission) behave exactly
  as today.

## 4. Analysis of the current code

### 4.1 Why the need cannot be met today

- `SessionRunService.classify` (`factory/factory-service/src/main/kotlin/io/whozoss/factory/workflow/service/SessionRunService.kt`)
  maps every capability outcome to a terminal status (COMPLETED/FAILED/NEEDS_RESEARCH/WAITING_HUMAN). There is no
  "pending, poll me later" outcome.
- Continuations are only woken by events (`enqueueContinuation` with `nextAttemptAt = null`) or by the adoption
  backoff (`adoptionDeferred`). There is no delayed wake that a running session can request while its own continuation
  is claimed: `acknowledgeContinuation` (`SpringDataNeo4jOutboxRepository`) re-pends a `wakeRequested` continuation
  with `nextAttemptAt = null` (immediately due).
- `AgentStepResultStatus` (`agentattempt/domain/AgentStepResultModels.kt`) only has PASS / FAIL / NEEDS_RESEARCH;
  `AgentStepResultValidation.STATUSES` and the worker OpenAPI enum match.
- `OutcomeReplayPlan.error` (`workflow/domain/OutcomeTransitions.kt`) rejects any `return` on a non-agent step
  (`return_requires_agent_result`), and `OutcomeTransitionService.advance` only considers an accepted agent FAIL
  (`latest.failureCode == "FACTORY_STEP_RESULT_FAILED"`).
- No code capability talks to GitHub: `CapabilityResolver.resolveCode` handles `prepare-work-branch`, the frontend
  registry and the repository whitelist (`factory/verification.json`) only.

### 4.2 What already fits

- Releasing the worker slot is free: a session that ends in a non-terminal state returns from `runSession`, the worker
  acknowledges its continuation, and the bounded pool slot (WZ-36378) is freed.
- `findDueContinuations` already honours `nextAttemptAt`: a pending continuation with a future `nextAttemptAt` is
  not claimed before it is due.
- `OutcomeTransitionService.record` accepts any known non-terminal status and never touches correction counters, so a
  `waiting_external` execution does not consume `maxCycles` (AC5) as long as nothing records FAILED for it.
- The NEEDS_RESEARCH pattern already shows how to finalize an attempt as `INDETERMINATE` with a dedicated
  `failureCode` (terminal but neither success nor failure) and re-arm a successor attempt N+1 with a fresh capability
  and a rewritten frozen brief on the same AgentOS case.
- `recordCode` / `recordStepEvidence` already attach `executionId` to evidence, which is what an execution-scoped
  CI verdict needs.

### 4.3 Regression risk areas

- Outbox CAS queries (claim / ack / release / defer / enqueue): a wrong `nextAttemptAt` either loses a wake or
  busy-loops. Covered by integration tests on the real Neo4j queries.
- Sequencer loop and session status (`SessionSequencer.terminalStatus`, `persistProgressProjection`): a new status must
  never be sealed as FAILED nor as COMPLETED.
- Exhaustive `when` over `AgentStepResultStatus` / `CapabilityOutcome` (compile errors are the safety net), and the
  places that special-case `AGENT_NEEDS_RESEARCH` (`BridgeRecoveryWorker`, `WorkflowService.workflowActions`,
  `CapabilityExecutionService.reserveAgentAttempt`/`terminalAgentExecution`, cockpit `timeline.ts`).
- Outcome router eligibility: a code step trigger must never fire on timeout/refusal.
- Cockpit status mappers (WZ-36374 area): `waiting_external` must not fall into the `failed` / `pending` buckets.

### 5.3 Delayed continuation wake (outbox)

`agentattempt/persistence/SpringDataNeo4jOutboxRepository.kt` — new property `wakeNotBefore` (nullable Instant, add to
`OutboxEventNode`):

- New query `requestDelayedWake(id, organizationId, eventId, workstreamId, payload, now, notBefore)`: MERGE the
  continuation node (same ON CREATE as `enqueueContinuation`), bump `casVersion`, then:
  - `claimed` → `wakeRequested = true`, `wakePayload = coalesce(wakePayload, payload)`,
    `wakeNotBefore = CASE WHEN wakeRequested already true AND wakeNotBefore IS NULL THEN null ELSE min(existing wakeNotBefore, notBefore) END`
    (an earlier immediate wake always wins);
  - `pending` → `nextAttemptAt = CASE WHEN nextAttemptAt IS NULL OR nextAttemptAt > notBefore THEN notBefore ELSE nextAttemptAt END`
    only when `retryDeadline IS NULL` (never touch the adoption-backoff state); 
  - `dispatched` / `dead` → `status = 'pending'`, `payload`, `attempts = 0`, `nextAttemptAt = notBefore`,
    `retryDeadline = null`, `diagnostic = 'EXTERNAL_POLL_SCHEDULED'`.
- `acknowledgeContinuation`, `releaseContinuation`, `deferClaimedContinuation`: where they consume `wakeRequested`, set
  `nextAttemptAt = e.wakeNotBefore` (instead of `null`), and `REMOVE e.wakeNotBefore` in every branch.
- `enqueueContinuation`: a *fresh* event wake (`fresh = true`) clears the delay — `wakeNotBefore = null` when the
  continuation is claimed, `nextAttemptAt = null` when pending (an accepted worker result must never wait 60 s).

`agentattempt/service/OutboxDrainService.kt`: new
`@Transactional(propagation = REQUIRES_NEW) fun scheduleWake(scope, namespaceId, workflowId, repoRoot: Path, ticket: String?, notBefore: Instant)`
building the same payload as `adoptionDeferred` (`namespaceId`, `workflowId`, `repoRoot`, `ticket`) and calling
`requestDelayedWake` on the deterministic `continuationId`. Update the class KDoc. `OutboxDrainWorker` needs **no**
change (it already parses `repoRoot`/`ticket` from the payload and refills slots on each tick).

### 5.5 Deterministic CI-check capability (no LLM)

  `Ok`, `Transient(reason)` (IO error, 5xx, 429, 408), `Refused(code, message)` (401/403/404/other 4xx).
- `PullRequestChecksCapability` (`@Component`, optional `GitHubChecksClient`):
  `fun check(stepId: String, repoRoot: Path): CapabilityOutcome` with the rules:
  1. token missing → `CodeRefused(code = "CI_GITHUB_NOT_CONFIGURED")`;
  2. repository = `origin` URL parsed from the worktree git config (`.git` dir or `gitdir:` file → `config`,
     `[remote "origin"] url`, `github.com[:/]owner/repo(.git)`), else `properties.repository`, else
     `CodeRefused("CI_REPOSITORY_UNRESOLVED")`;
  3. branch = attached branch read from `HEAD` (same parsing as `CapabilityResolver.observedGitBranch`), detached →
     `CodeRefused("CI_BRANCH_UNRESOLVED")`;
  4. no open PR → `CodeRefused("CI_PR_NOT_FOUND")`; draft PR → `CodeRefused("CI_PR_IS_DRAFT")` (AC12);
  5. local HEAD (read as in `observedGitHead`) known and ≠ PR `head.sha` → `ExternalPending(reason = "CI_HEAD_NOT_PUSHED")` (AC11);
  6. check runs + combined statuses of the PR head SHA: any check run `status != completed` or status context
     `pending`, or **no check and no status at all** → `ExternalPending(reason = "CI_CHECKS_PENDING", facts = counts)`;
  7. all completed: failed = check-run conclusion in `{failure, timed_out, cancelled, action_required, startup_failure, stale}`

  8. failures → fetch the log tail of up to `maxFailedJobsWithLogs` failed check runs whose `app.slug == "github-actions"`
     (check-run id = job id); other failures keep `name/conclusion/url/output.summary` only. Redact with the same
     regexes as `SessionRunService.safeDiagnostic` (TOKEN/SECRET/PASSWORD/API_KEY/PRIVATE_KEY, bearer) →
     `CiChecksCompleted(passed = false, failedChecks = [{name, conclusion, url, summary, logExcerpt, logTruncated}])`;
  9. any `Transient` → `ExternalPending(reason = "CI_GITHUB_TRANSIENT: …")` (AC10); any `Refused` → `CodeRefused(code = "CI_GITHUB_REFUSED")`.
  No process is spawned and no LLM is called (AC3).

### 5.7 Sequencer: park, poll, time out

`SessionRunService.kt` (new optional constructor params at the end: `pollingProperties: ExternalPollingProperties = ExternalPollingProperties()`,
`clock: Clock = Clock.systemUTC()`; use `clock` for every poll timestamp):

- `SessionProgress`: new `polls = HashMap<String, Map<String, Any?>>()` persisted in the step payload under `"poll"`
  (`fromStates` / `payload` / `reloadAuthoritativeProgress`, cleared when the `executionId` changes — AC7).
  Shape: `{executionId, source, firstPollStartedAt, lastPollAt, nextPollAt, deadlineAt, pollCount, intervalSeconds, reason}`.
- `executeStep`: right after `resolveAndRecord`, before oracles:
  - `ExternalPending` / `AgentInProgress` → `interval = clamp(retryAfterSeconds ?: defaultIntervalSeconds)`;
    `first = existing poll.firstPollStartedAt ?: startedAt of this execution`; `deadline = first + maxWaitSeconds`.
    If `now >= deadline` → `recordPollTimeout` (below) and return FAILED. Else persist the poll state, `setStatus(WAITING_EXTERNAL)`,
    `transition(WAITING_EXTERNAL)`, `outcomeTransitionService.record(..., WAITING_EXTERNAL, attemptId, evidenceId)`,
    `recordStepEvidence(WAITING_EXTERNAL)` and return `WAITING_EXTERNAL`. No oracle runs, no FAILED is recorded (AC5).
- `classify`: `CiChecksCompleted -> if (passed) COMPLETED else FAILED`; `ExternalPending`, `AgentInProgress -> WAITING_EXTERNAL`.
- Main loop (before `readySteps`): for each `WAITING_EXTERNAL` step of the current execution: `now >= deadlineAt` →
  `recordPollTimeout`, `continue`; `now >= nextPollAt` → it is the candidate step (claimed like a READY step).
  `claimStep` accepts `WAITING_EXTERNAL` in both branches (`fromStatuses` and the execution-fenced path). The
  `executeStep` return value `WAITING_EXTERNAL` does **not** end the loop (independent branches keep running).
- `recordPollTimeout(step)`: in one `newTransaction`: evidence `session-step` FAILED with facts
  `{code: "POLL_TIMEOUT_EXCEEDED", executed: true, pollCount, firstPollStartedAt, deadlineAt, lastReason, executionId}`,
  `transition(FAILED)`, `setStatus(FAILED)`. It is a technical failure: the router never takes `return` on it (AC4/AC8).
- After the loop: if the evaluated session status is `WAITING_EXTERNAL`, call
  `outboxDrainService?.scheduleWake(scope, ns, wf, effectiveRepoRoot, effectiveTicket, min(nextPollAt))` (idempotent,
  single place; also covers synchronous `runSession` callers). `persistProgressProjection` status: add
  `any WAITING_EXTERNAL && none RUNNING -> WAITING_EXTERNAL` after the WAITING_HUMAN branch; projected steps carry
  `poll` (copy, `remove` when absent).
- `OutcomeTransitionService.advance`: add `WAITING_EXTERNAL` to the `CORRECTION_SCOPE_ACTIVE` guard set.

## 7. Contract between backend and frontend

```
projection.status            : … | "waiting_external"        (non-terminal; cockpit → RunStatus "running")
projection.steps[].status    : … | "waiting_external"
projection.steps[].poll      : { executionId, source: "ci-checks"|"agent", firstPollStartedAt, lastPollAt,
                                 nextPollAt, deadlineAt, pollCount, intervalSeconds, reason }   (ISO-8601 UTC)
projection.stepExecutions[]  : status may be "waiting_external"
evidence kind "ci-checks"    : outcome pass|fail|pending; facts { stepId, executionId, verdict, reason?, prNumber,
                                 prUrl, headSha, branch, checks[{name,status,conclusion,url}],
                                 failedChecks[{name,conclusion,url,summary,logExcerpt,logTruncated}] }
evidence kind "session-step" : failed with facts.code "POLL_TIMEOUT_EXCEEDED" on timeout
attempts                     : status "indeterminate", failureCode "AGENT_IN_PROGRESS" for agent polls
worker submission (agent)    : result.status "IN_PROGRESS", optional result.retryAfterSeconds (30–300)
definition                   : code step responsibility.name "github-pr-checks" may declare
                               outcomeTransitions.fail { action: "return", target, maxCycles? }
```

Implementation order: 5.1 → 5.2 → 5.3 → 5.4/5.5 → 5.7 (code path, tests) → 5.6 (agent path) → 5.8 → 5.9 → 5.10 →
frontend 6. Both sides go in this one PR.

## 10. Risk level

**High.** The change adds a new non-terminal step status across the sequencer, the outbox CAS queries, the worker result
schema, the outcome router and the cockpit mappers, and an outbound GitHub integration with a secret. Mitigations: the
new status is only reachable through the new capability or an explicit IN_PROGRESS submission (legacy runs keep their
exact behaviour), the router trigger is restricted to a real red CI verdict bound to the current execution, the 30-min
cap is enforced server-side, and every outbox query change is covered by integration tests on the real Neo4j queries.
