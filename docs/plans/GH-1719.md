# GH-1719 — Case files: folder-scoped download, folder create/delete, uploads into a folder

- Ticket: https://github.com/whoz-oss/coday/issues/1719 (GitHub issue, label `bug`; no Jira issue exists under this key)
- Base branch: `workstream/forge/master` — work branch: `bugfix/GH-1719-case-files-folder-actions`
- Routes: **backend** and **frontend** (the contract below lets either run first)
- Risk: **medium** (new destructive operation: recursive folder delete; streamed archive over possibly large trees)

## 1. Expected outcome

In the Files drawer, a user can create and delete folders, upload into the folder being browsed, and download
the folder being browsed (or the whole scope from the root) as one ZIP, with no browser multi-download prompt.

Observed vs expected (bug):

| # | Observed | Expected |
|---|----------|----------|
| 1 | Inside a subfolder the button reads "Download all case files" and downloads the whole case | Scoped to the current folder, label "Download all files in this folder" |
| 2 | N successive downloads, 300 ms apart; the browser blocks all but the first | One ZIP download |
| 3 | No way to create a folder | "New folder" action |
| 4 | No way to delete a folder | Delete with a confirmation naming the number of files |
| 5 | A file uploaded while browsing a folder lands at the scope root | It lands in the browsed folder |

Reproduction steps: **complete** for 1–4; **partial** for 5 (the ticket says "via the agent"; the code shows the
loss happens on the UI upload path, see root cause 5 — agent `editFiles` writes honour their path already).

## 2. Acceptance criteria

From the ticket:
- AC1 The download-all button is scoped to the current folder, with a matching label.
- AC2 Download-all produces one complete download (a ZIP), with no browser multi-download prompt.
- AC3 The UI allows creating folders (nested: created inside the folder being browsed).
- AC4 The UI allows deleting folders, with a confirmation step stating what happens to the files it contains.
- AC5 Files uploaded into a folder via the UI are stored in that folder.

Derived (flagged):
- AC6 *(derived)* Both drawer sections (case and namespace) get the same behaviour; namespace write actions stay gated on
  Namespace `WRITE`, case ones on Case `WRITE`; read-only users see no create/delete/upload affordance.
- AC7 *(derived)* Deleting a folder that contains a reserved entry (a Git worktree's `.git`, i.e. the case `repo/`
  folder or any ancestor of it) is refused; the scope root can never be deleted.
- AC8 *(derived)* At the scope root the label stays "Download all case files" / "Download all namespace files";
  the archive skips reserved entries exactly as the manifest does.

## 4. Code analysis and root causes

Backend (`agentos/agentos-service/src/main/kotlin/io/whozoss/agentos/exchange/`):
- `ExchangeController.kt` — standalone controller; case writes go through `withFileMutation` (owner-case access,
  workspace usability), namespace writes through `exchangeStorageService.namespaceRoot`. `mapStorageErrors` maps
  storage exceptions without leaking absolute paths. Upload: `uploadTo(...)` uses `uploadRelativePath(file)` =
  the multipart filename only.
- `ExchangeStorageService.kt` — `resolveWithin` (traversal, symlink, reserved-entry guard), `writeNew` (CREATE_NEW),
  `delete` (`Files.delete`, single entry), `listManifest` (walk, depth 20, reserved subtrees skipped), `listDirectory`.
- SDK contract `agentos/agentos-sdk/.../exchange/ExchangeApi.kt` — must NOT gain abstract methods (external Feign
  consumers); browse was added outside it on purpose. Follow the same rule.
- Tests: `src/test/.../exchange/ExchangeStorageServiceSpec.kt`, `ExchangeControllerMvcIntegrationSpec.kt`.

Frontend (`libs/agentos-ui/src/lib/`):
- `components/exchange-drawer/exchange-drawer.component.{ts,html}` — presentational; outputs `uploadRequested`,
  `downloadAllRequested`, `deleteRequested`; header buttons per section.
- `components/exchange-shell/exchange-shell.component.{ts,html}` — smart container; delete confirmation via
  `ds-confirm-dialog`; `onDownloadAll`, `onUpload`.
- `services/exchange-state.service.ts` — `downloadAll` (manifest + N `downloadFrom` with 300 ms stagger),
  `uploadFile`, `deleteFile`, `casePath` / `namespacePath`, `caseBrowsePath()` / `namespaceBrowsePath()`.
- Generated client `libs/agentos-api-client/src/lib/` (never hand-edited); hand-written layer `src/custom/`, exported
  from `src/index.ts` (see `libs/agentos-api-client/GUIDELINES.md`).
- Tests: `services/exchange-state.service.spec.ts`, `components/exchange-shell/exchange-shell.component.spec.ts`,
  `components/exchange-drawer/exchange-drawer.component.spec.ts`.

Root causes (one per problem):
1. `exchange-state.service.ts` `downloadAll(scope)` fetches the **recursive manifest of the whole scope** and ignores
   `casePath`/`namespacePath`; the drawer template hard-codes the title `"Download all case files"`.
2. Same method downloads files one by one (`for … await downloadFrom` with a 300 ms timer): each one is an anchor
   click on an object URL, which browsers treat as automatic multiple downloads and block after the first.
   No archive endpoint exists server-side.
3. / 4. No create-directory or delete-directory endpoint exists (`ExchangeStorageService.delete` is a single
   `Files.delete`, which throws `DirectoryNotEmptyException` → 400 on a folder), and the drawer renders no action.
5. `ExchangeController.uploadTo` stores the file at `uploadRelativePath(file)` = multipart filename only, and
   `ExchangeStateService.uploadFile` sends no directory: whatever folder is browsed, the file lands at the root.

## 5. Contract between backend and frontend

All new routes are additive, live on `ExchangeController` only (not on `ExchangeApi`), and exist for both scopes:
`{base}` = `/api/cases/{caseId}` (gate Case) or `/api/namespaces/{namespaceId}` (gate Namespace). Paths are relative
to the scope root, forward slashes, no leading slash. Errors reuse `mapStorageErrors` (generic messages, no server path).

| Method & path | Gate | Params | Success | Errors |
|---|---|---|---|---|
| `POST {base}/files` (multipart `file`) | WRITE | **new** optional query param `directory` (default `""` = root) | 200 `ExchangeFileEntry`, `path = directory/filename` | 400 bad path / extension (checked on the leaf), 409 exists |
| `POST {base}/files/directory` | WRITE | query `path` (required) | 200 `ExchangeDirectoryEntry` (`directory=true`) | 400 blank/invalid/reserved, 409 already exists (file or folder) |
| `DELETE {base}/files/directory` | WRITE | query `path` (required, non-blank) | 200 `ExchangeDeleteResponse` | 400 blank/invalid/not a directory, 404 missing, 409 subtree holds a reserved entry (nothing deleted) |
| `GET {base}/files/archive` | READ, `@HideOnAccessDenied` | query `path` (optional, `""` = root) | 200 `application/zip`, `Content-Disposition: attachment; filename="<name>.zip"` (`<name>` = last segment of `path`, or `case-files` / `namespace-files` at root); entry names relative to `path` | 404 missing folder or denied, 400 not a directory |

OperationIds (follow the controller's naming; the spec generator appends `Exchange`): `uploadCaseFile` /
`uploadNamespaceFile` (extended), `createCaseDirectory` / `createNamespaceDirectory`, `deleteCaseDirectory` /
`deleteNamespaceDirectory`, `downloadCaseArchive` / `downloadNamespaceArchive`.

The frontend must not depend on the regenerated client (routes run in either order): it calls the four operations
through a hand-written `ExchangeFolderApiService` in `libs/agentos-api-client/src/custom/`, built on `HttpClient`
with the same `BASE_PATH`/`Configuration` as the generated services.

## 6. Scoped change per side

### Backend route

`ExchangeStorageService.kt`
- `createDirectory(root, relativePath): ExchangeDirectoryEntry` — `Files.createDirectories(root)`, `resolveWithin`,
  throw `FileExistsException` if the target exists, else `Files.createDirectories(target)`; return its entry.
- `deleteDirectory(root, relativePath)` — `resolveWithin` (blank refused → root can never be deleted); missing →
  `NoSuchFileException`; not a directory → `NotDirectoryException`; first walk the subtree without following links
  and throw a new `ReservedEntryConflictException` (mapped to 409) if any entry name is reserved; then delete
  bottom-up with `walkFileTree` (links are deleted as links, never followed).
- `writeArchive(root, relativePath, out: OutputStream)` — resolve the directory (empty = root; never-written root
  → empty archive), reuse the `listManifest` walk (depth cap, reserved subtrees skipped, symlinks not followed)
  restricted to that directory, and stream each file into a `ZipOutputStream` with `Files.copy` (no whole-file
  buffering). Entry names relative to the archived directory.
- `writeNew` unchanged (already creates parent directories).

`ExchangeController.kt`
- Upload: add `@RequestParam(required = false, defaultValue = "") directory: String` to both upload methods; the
  stored path is `listOf(directory.trim('/'), filename).filter(isNotEmpty).joinToString("/")`; the extension
  allow-list stays checked on the leaf (`isUploadAllowed` already does).
- Add the six directory/archive handlers per the contract; case writes through `withFileMutation`, reads through
  `resolvedCase(...).requireUsable()`; archive returns `ResponseEntity<StreamingResponseBody>` with the disposition
  built like `downloadResponse` (reuse `dispositionFilename`).
- `mapStorageErrors`: map `ReservedEntryConflictException` → `ConflictException("Folder contains protected entries")`,
  `NotDirectoryException` → 400 "Not a directory" (before the generic `IOException` branch).

Other backend files
- New `ReservedEntryConflictException.kt` next to `FileExistsException`.
- Regenerate `agentos/openapi/agentos-openapi.yaml` and the generated client (`agentos-service:regenerate`), commit both.
- `agentos/docs/file-exchange.md`: add the routes to the REST table and the `directory` upload param; replace the
  sentence saying Download all uses the manifest with the archive behaviour.

### Frontend route

`libs/agentos-api-client/src/custom/exchange-folder-api.service.ts` (new) + export in `src/index.ts`
- `uploadFile(scope, id, directory, file)`, `createDirectory(scope, id, path)`, `deleteDirectory(scope, id, path)`,
  `downloadArchive(scope, id, path): Observable<Blob>` (`responseType: 'blob'`), per the contract.

`libs/agentos-ui/src/lib/services/exchange-state.service.ts`
- `uploadFile(scope, file, directory = current browse path of the scope)` → custom service with `directory`.
  Composer attachments keep calling it with the root (pass `''` explicitly from `ComposerAttachmentsService` so the
  mention text stays true).
- `downloadAll(scope)` → `downloadFolder(scope, path = current browse path)`: one `downloadArchive` call, one
  `saveBlob` with `<last segment or case-files|namespace-files>.zip`; captured scope id kept (existing guarantee).
  Drop the manifest + stagger loop.
- `createFolder(scope, name)`: path = `currentPath/name`; refresh the scope on success; map 409 → "A file or folder
  with this name already exists.", 400 → server message.
- `deleteFolder(scope, path)`: refresh on success; 409 → "This folder contains protected files and cannot be deleted."
- `folderFileCount(scope, path): Observable<number>` — count of `fileManifest(scope)` entries under `path + '/'`
  (reuses the cached recursive manifest), for the confirmation text.

`exchange-drawer.component.{ts,html,scss}`
- Download button title: breadcrumb non-empty → "Download all files in this folder", else unchanged scope label.
- New header button `create_new_folder` (only when `canWrite…`) → emits `createFolderRequested(scope)`.
- Per-folder-row delete icon button (only when `canWrite…`, not on filter results) → `deleteFolderRequested({scope, path})`;
  the folder row stays a navigation button, the delete button is a sibling inside the `li`.

`exchange-shell.component.{ts,html}`
- Name prompt: a small inline form or dialog for the folder name (reject empty, `/`, `\`, `.`/`..`) → `state.createFolder`.
- Folder delete: reuse the existing `ds-confirm-dialog` with a folder variant: title "Delete folder", message
  `Delete "<name>" and its N files? This action cannot be undone.` (N from `folderFileCount`; "Delete empty folder
  "<name>"?" when 0; generic text if the count fails). Clear the selection if the previewed file was inside it.
  Pending folder delete is dropped on context change like the file one.
- `onDownloadAll` → `state.downloadFolder`; error message on failure.
