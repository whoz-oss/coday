# WZ-36377 — Run status filter on the Factory dashboard (Workstreams page)

Ticket: https://whoz.atlassian.net/browse/WZ-36377 (User Story, no comments, no attachments, no linked tickets).
Work branch: `work/forge/WZ-36377-run-status-filter`. Base and PR target: `workstream/forge/master`.
Side: **frontend only** (`apps/factory-cockpit`). No backend, API or store change.

## 1. Expected outcome

On the Factory Cockpit Workstreams page, a user can pick one run status (All, Running, Waiting, Waiting for human, Blocked, Failed, Completed, and Destroyed when the "Destroyed runs" toggle is on). Each option shows how many runs it matches. The workstream cards then show only the matching runs, workstreams with no matching run are hidden, and the global KPIs stay unchanged. The filter is computed in the browser from the runs already loaded by `FactoryStore`.

## 2. Acceptance criteria

From the ticket:

1. A status filter control sits in the filter bar of the Workstreams page (`workstreams-page.component.html`). It is a `mat-chip-listbox`, the control the Run History page already uses for its status filter.
2. Options: All, Running (`running`), Waiting (`pending`, the card's default "waiting" chip), Waiting for human (`waiting_human`), Blocked (`blocked`), Failed (`failed`), Completed (`succeeded`). Destroyed (`r.status === 'destroyed'`) appears only while `store.showDestroyed()` is true.
3. Each option shows the number of matching runs, in the format of the History chips (`Label · N`).
4. With a filter active, each `sf-workstream-card` gets only the matching runs, and workstreams with 0 matching runs are not rendered. When nothing matches in the selected workstream(s), the page shows the empty state "No run matches the selected status filter."
5. The global KPIs (`store.costs()`) are not affected by the filter. Unit tests in `workstreams-page.component.spec.ts` cover the filtering.

Derived by the architect (flagged):

6. *(derived)* The filter takes a **single** value, like the History page. The ticket's "status(es)" wording allows multi-select, but single-select matches the existing UI and keeps the counts easy to read. Multi-select can be a follow-up.
7. *(derived)* A run's effective status is exactly what its card displays (see `run-card.component.html`): `destroyed` when `run.status === 'destroyed'`, otherwise `run.run?.cardState`, and `pending` when `cardState` is absent (the card's `@default` "waiting" chip). The chip a user sees and the filter bucket can therefore never disagree.
8. *(derived)* Counts cover the runs currently visible on the page before the status filter is applied: the namespace selection and the Destroyed toggle apply, the status filter does not. They are computed from `store.workstreams()`. "All" equals the total of visible runs.
9. *(derived)* If "Destroyed" is selected and the user then switches the Destroyed toggle off, the filter falls back to "All". There is no stale empty page and no hidden selected chip.
10. *(derived)* The workstream card header (run count and cost) reflects the runs it displays, i.e. the filtered runs. It is a direct consequence of passing a filtered `WorkstreamView`, and the KPIs at the top of the page stay global.
11. *(derived)* The filter state is local to the page component (a signal). It is not persisted in the URL or the store and is reset when the user leaves the page. Keeping it in the URL is out of scope.

## 5. Scoped change — frontend

### 5.1 New file `apps/factory-cockpit/src/app/features/workstreams/run-status-filter.ts`
A small pure module (no Angular), so the logic can be unit-tested and the component stays thin:

```ts
import { FactoryRun, RunCardState } from '../../core/models'

export type RunStatusKey = RunCardState | 'destroyed'
export type RunStatusFilter = 'all' | RunStatusKey

/** Display order and labels of the filter chips (English UI, #1710). */
export const RUN_STATUS_OPTIONS: ReadonlyArray<{ value: RunStatusKey; label: string }> = [
  { value: 'running', label: 'Running' },
  { value: 'pending', label: 'Waiting' },
  { value: 'waiting_human', label: 'Waiting for human' },
  { value: 'blocked', label: 'Blocked' },
  { value: 'failed', label: 'Failed' },
  { value: 'succeeded', label: 'Completed' },
  { value: 'destroyed', label: 'Destroyed' },
]

/** Same precedence as the run card chip: destroyed first, then cardState, default pending. */
export function runStatusKey(run: FactoryRun): RunStatusKey {
  if (run.status === 'destroyed') return 'destroyed'
  return run.run?.cardState ?? 'pending'
}
```

Builder may adjust the names. Two things are mandatory: `runStatusKey` is the single source of truth for the bucket, and it mirrors `run-card.component.html`.

### 5.2 `workstreams-page.component.ts`
- Import `MatChipsModule` and add it to `imports`. Import `computed` and `signal`.
- `protected readonly status = signal<RunStatusFilter>('all')`.
- `protected readonly activeStatus = computed<RunStatusFilter>(() => this.status() === 'destroyed' && !this.store.showDestroyed() ? 'all' : this.status())` (AC9, no `effect`).
- `protected readonly statusOptions = computed(() => RUN_STATUS_OPTIONS.filter((o) => o.value !== 'destroyed' || this.store.showDestroyed()))`.
- `protected readonly statusCounts = computed(() => …)`: one pass over `store.workstreams().flatMap((ws) => ws.runs)`. It returns `{ all: number } & Record<RunStatusKey, number>`, with every key initialised to 0.
- `protected readonly filteredWorkstreams = computed<WorkstreamView[]>(() => …)`:
  - when `activeStatus() === 'all'`, return `this.store.workstreams()` **unchanged (same reference)**, which keeps the #1705 stability;
  - otherwise, map each workstream to `{ ...ws, runs: ws.runs.filter((r) => runStatusKey(r) === active) }` and drop the ones with an empty `runs`.
- `protected selectStatus(value: RunStatusFilter | null | undefined): void { this.status.set(value ?? 'all') }`. `mat-chip-listbox` emits `undefined` when the selected chip is clicked again, which then means "All", the same behaviour as History.
- Leave `onAction` and `confirmRemove` unchanged.

### 5.3 `workstreams-page.component.html`
- After `</header>` and before the namespace-required notice, add a filter bar:
  ```html
  <div class="filters">
    <mat-chip-listbox aria-label="Filter runs by status" data-workstreams-status-filter
      [value]="activeStatus()" (change)="selectStatus($event.value)">
      <mat-chip-option value="all">All · {{ statusCounts().all }}</mat-chip-option>
      @for (option of statusOptions(); track option.value) {
        <mat-chip-option [value]="option.value">{{ option.label }} · {{ statusCounts()[option.value] }}</mat-chip-option>
      }
    </mat-chip-listbox>
  </div>
  ```
  Use the same `·` separator (U+00B7) as History.
- Leave the KPI section unchanged (still `store.costs()`).
- In the cards section, iterate `filteredWorkstreams()` instead of `store.workstreams()`. In `@empty`, add as the **first** branch: `@if (activeStatus() !== 'all' && store.workstreams().length > 0) { <p class="empty sf-panel sf-muted" data-workstreams-status-empty>No run matches the selected status filter.</p> }`, followed by the existing `@else if` chain (mapping missing, overview error, neutral message), which stays unchanged.

## 7. Verification criteria

Tests to add in `workstreams-page.component.spec.ts`. They reuse `createStore` / `createRun` / `createWorkstream`, with runs whose `run.cardState` is set (and one with `cardState` undefined, which must count as Waiting). The status is driven either by clicking the `mat-chip-option` in `[data-workstreams-status-filter]` or through a protected accessor cast, like the History spec:
1. The chip bar renders All plus the 6 statuses with the right counts. There is no Destroyed chip while `showDestroyed` is false. A run without `cardState` is counted as Waiting.
2. With `showDestroyed.set(true)` and a destroyed run in a workstream, the Destroyed chip appears with its count, and selecting it renders only that run.
3. Selecting `failed` renders only failed runs (`sf-run-card` count and `data-run-id`). A workstream with no failed run is not rendered (`sf-workstream-card` count) and the KPI values are unchanged.
4. When nothing matches (runs exist, none `blocked`), selecting `blocked` shows "No run matches the selected status filter." and no workstream card, and the neutral "No workflows in the selected namespaces." message is **not** shown.
5. With "All" selected, `filteredWorkstreams()` returns the same array reference as `store.workstreams()`.
6. With Destroyed selected, setting `showDestroyed` back to false makes `activeStatus()` fall back to `all`, and every run is rendered again.
7. Optional: a small `run-status-filter.spec.ts` for `runStatusKey` (destroyed wins over `cardState`, undefined gives `pending`).

Existing tests that must stay green:
- `pnpm nx run-many -t lint test -p factory-cockpit` (the project name is to be confirmed with `pnpm nx show projects`), and in particular `workstreams-page.component.spec.ts` (empty state, KPIs, lifecycle actions), `workstream-card.component.spec.ts`, `run-card.component.spec.ts`, `history-page.component.spec.ts` and `factory.store.spec.ts`.
- `pnpm nx run factory-cockpit:build` (template type-check of the `statusCounts()[option.value]` indexing).

Neighbouring behaviours to check by hand (`pnpm web:serve:dev`, `/workstreams`): switching the namespace keeps the selected status and the counts update; the Destroyed toggle shows and hides the Destroyed chip; the run actions (Stop, Remove with confirmation, Restore, Ask supervisor) still work on filtered cards; SSE refreshes move a run between buckets live (for example running → failed) without the page flickering.

**Risk level: low.** The change is additive and limited to one page component and its spec. It does not touch the store, the mappers or any API. The only subtle point is keeping the references stable when the filter is "All", which the plan states explicitly.
