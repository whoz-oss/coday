# GH-1751 — The Architect generates a workflow during the run, the user chooses how to launch, and a generated workflow can be saved as a reusable definition

- Ticket: https://github.com/whoz-oss/coday/issues/1751 (GitHub issue, label `enhancement`, so it is a user story, not a bug)
- Work branch: `work/forge/1751-architect-custom-workflow` (base `workstream/forge/master` @ `44e4740`)
- Routes: **backend** + **frontend**
- Risk: **high**. The change touches the session sequencer, the result channel and the way a run finds its definition.

## 1. Expected outcome

When a steering agent is asked to launch work and no workflow is named, it first asks the user which of three paths to take: use an existing workflow, design one together before starting, or let the Architect build one. On the third path, a bootstrap run starts with one Archay step. That step sends a set of continuation steps through `FACTORY_WORKER__submitStepResult`.

Factory checks those steps at once and rejects bad ones with errors the agent can act on. It adds the accepted steps to **that run only** and runs them in the same session, worktree and `rootCaseId`. Later, a run built this way can be saved as a new, versioned definition that cannot be changed once registered.

## 2. Acceptance criteria

AC1–AC6 come from the ticket. I made them precise where the code requires it. The items marked **(derived)** are mine.

1. **AC1 Launch choice.** If no workflow type is given, the `factory-workstream` skill asks the user with `queryUser`: one question, three options.
   - (1) Use an existing workflow: list the registered definitions.
   - (2) Create one first: hand over to `factory-workflow-authoring`, then start the new definition.
   - (3) Let the Architect build it: start `architect-custom-flow` with the ticket.
   - The agent never picks a path without asking.
2. **AC2 Sending the continuation.** `POST /api/factory/agent-step-results` accepts an optional field `result.continuation = { steps: [...] }`. Each step uses the canonical `WorkflowStepDefinition` JSON. The field is accepted only on `PASS`, and only for a step whose definition declares `expansion`.
3. **AC3 Immediate check.** A bad continuation gets `400 RESULT_SCHEMA_INVALID` with `details.violations[]`. Each violation has a `path`, a `code` and a `message`, and never repeats the submitted values.
   - The capability is **not** used up. The Architect can fix the steps and send them again in the same turn.
   - What is checked: the graph has no cycle; every step contract is valid; no step id clashes with the base steps; every `dependsOn` is valid; the routing and join rules hold; every agent is enabled in the namespace.
   - **(derived)** If Factory cannot read the namespace agent list, it accepts the continuation and records `agentsVerified=false`. This is how `WorkspacePrecheckService` already behaves: an agent that cannot be checked is reported as unverified, never assumed missing.
4. **AC4 Adding steps to the run.** An accepted continuation is saved in two places: the `WorkflowInstanceRecord` (its instance and projection) and the `WorkflowProjectionRecord`.
   - The first continuation steps depend on the Architect step.
   - Factory records an audit evidence item of kind `workflow-expansion`.
   - The new steps show in Cockpit through the normal projection and SSE.
   - They run in the same session, worktree and `rootCaseId`.
   - **The definition catalog does not change**: there is no `saveDefinition` call.
   - **(derived)** Adding the steps is idempotent and survives a crash. Replaying the same accepted result never adds the steps twice. If the process stops after the step is finalized but before the steps are added, the next sequencer pass adds them.
5. **AC5 Bootstrap definition.** `architect-custom-flow@1.0.0` ships in `factory/factory-service/src/main/resources/sessions/`. It is loaded at startup like the other bundled definitions. It has a single agent step, `architect-plan` (agent `Archay`), and that step declares `expansion`.
6. **AC6 Saving as a reusable definition.** For a run that has added steps, Factory returns a **draft** of the full definition: the base steps plus the added ones, with `expansion` removed.
   - Cockpit opens this draft in the existing workflow composer.
   - The user picks the type, version and title, and makes the step text generic.
   - The user registers it through the existing `POST /api/factory/workflow-definitions` (`If-None-Match: *`), which never overwrites a definition.
   - An authoring agent can do the same with `FACTORY_AUTHORING`.
   - Factory never registers a definition on its own.
7. **(derived) Limits of this first version.** Each limit is rejected with its own violation code, so nothing is dropped silently.
   - A definition has at most one step that declares `expansion`. That step must be an `agent` step with no dependents and no `decision`.
   - A continuation step cannot declare `expansion` (no nested expansion) or `outcomeTransitions`. The reason: `OutcomeTransitionService.initialize` refuses a run that already has step states (`OUTCOME_LEGACY_RUN_REQUIRES_NEW_RUN`, file `workflow/service/OutcomeTransitionService.kt`).
   - A run that is a fragment of a parent Run (`runId` is set) cannot add steps.
   - A continuation has 1 to 50 steps.

## 5. Design

### 5.1 Principle

The catalog stays unchanged. An expansion is **data that belongs to the run** and is stored with it:

- The base definition stays pinned by `(workflowType, definitionVersion, definitionHash)`.
- The run carries an `expansion` record.
- The definition a run actually follows is always computed by **one** resolver: base plus expansion, validated again, with its hash checked.
- Every place that looks up the definition today goes through this resolver. It replaces three copies of the same lookup. Correctness requires it, so it is not an extra refactor.

### 5.2 Definition contract: a new optional step field

```json
"expansion": { "mode": "append" }
```

- Only `mode: "append"` is accepted.
- It is allowed on exactly one `agent` step that has no dependents and no `decision`.
- When the field is absent, it is left out of the normalized output. The hashes of existing definitions do not change.

### 5.3 Result contract: a new optional business field

```json
"continuation": { "steps": [ { "id": "...", "name": "...", "responsibility": {"kind":"agent","name":"Frontend"}, "dependsOn": [], "entry": [], "mission": "...", "exit": [] } ] }
```

- Allowed only on PASS, with 1 to 50 steps.
- Each step uses the canonical step schema. `decision` and `join` are allowed and follow the usual topology rules on the merged definition.
- An empty `dependsOn` means "after the expanding step". Factory rewrites it to `[<expanderStepId>]`.
- `dependsOn` may name only the expanding step or other continuation steps.
- The field is part of the canonical result hash. A replay with different content is a `RESULT_SEMANTIC_COLLISION`, as it is today.
- The expanding step must send a continuation with its PASS. A PASS without one is rejected with `CONTINUATION_REQUIRED`. NEEDS_RESEARCH and FAIL follow the existing flows.

Violation codes (`details.violations[].code`). Paths look like `result.continuation.steps[i]...`.

| Code | Meaning |
|---|---|
| `INVALID_CONTINUATION` | The shape is wrong: not an object, `steps` is not an array, or the field is sent with a status other than PASS. |
| `CONTINUATION_NOT_ALLOWED` | The step has no `expansion`, or the run is a fragment of a parent Run. |
| `CONTINUATION_REQUIRED` | The expanding step sent PASS without a continuation. |
| `STEP_ID_COLLISION` | A continuation step id already exists in the base definition. |
| `INVALID_DEPENDENCY` | A dependency points to a base step other than the expanding step. |
| `UNSUPPORTED_IN_CONTINUATION` | A step declares `expansion` or `outcomeTransitions`. |
| `MAX_ITEMS` | More than 50 continuation steps. |
| `AGENT_NOT_AVAILABLE` | An agent step names an agent that is not enabled in the namespace. |
| `<WorkflowDefinitionErrorCodes>` | Errors passed on from the validation of the merged definition (`DEPENDENCY_CYCLE`, `MISSING_DEPENDENCY`, `INVALID_RESPONSIBILITY`, `INVALID_VALUE` with its reason, ...). The path is mapped back to the continuation index. |

### 5.4 How an accepted expansion is stored (on the run only)

The accepted expansion is written to `instance.instance["expansion"]` and copied to `projection["expansion"]`:

```json
{ "sourceStepId": "architect-plan", "attemptId": "...", "resultId": "...", "resultHash": "sha256:...",
  "steps": [ /* normalized continuation steps, first steps rewired */ ],
  "stepIds": ["..."], "effectiveDefinitionHash": "<sha256 of the merged normalized definition>",
  "agentsVerified": true, "expandedAt": "ISO-8601" }
```

In addition:

- The added steps are appended to `projection.steps` with status `pending`. They get the same JSON shape as `persistProjection`, including the contract and routing JSON.
- A `workflow_step_states` entry is created for each, with status `pending`. The normal evaluation then moves them to `ready`.
- A `WorkflowEvidenceItem` of kind `workflow-expansion` is recorded with outcome `pass` and idempotency key `workflow-expansion:<workflowId>:<resultId>`.
- An SSE hint is published.

All these writes happen in a single `newTransaction`. The instance update is a compare-and-swap on its revision.

### 5.5 Execution flow

1. The Architect step runs with its explicit brief plus a new `## Workflow expansion` section, produced by `expansionInstruction(step)`. This section explains the continuation rules, the auto-wiring of the first steps and the forbidden fields, and lists the step ids already in use.
2. When the result is sent, `AgentStepResultService.submit` calls `WorkflowExpansionService.validateContinuation(...)` right after `validateRouting` and before anything is saved. If there are violations, it throws `ResultSchemaInvalidException(details = violations)`, and the capability is not used up.
3. In `SessionRunService.executeStep`, after `terminal == COMPLETED` and before `finalizeStep`: if the step declares `expansion`, Factory calls `expansionService.graft(...)` inside `newTransaction`. If adding the steps fails, the step is marked FAILED, the same way a failed `acceptRouting` is handled today (`recordStepFailure`).
4. After the steps are added, `runSessionLocked` reloads `steps` from the resolver, recomputes `guard`, and continues the loop.
   - The added steps then run one after the other.
   - `prepareAgentWorkspace`, `rootCaseId` and the worktree binding work as they are.
   - Agent availability for the added steps was checked when the result was sent. The startup precheck is not run again.
5. Crash safety: at the start of each loop pass, `expansionService.reconcile(...)` adds the steps if three things are true: the expanding step is COMPLETED, it has an accepted continuation, and no expansion is recorded yet.
   - It is idempotent on `resultId`.
   - A different `resultId` raises `EXPANSION_IMMUTABLE`.

### Contract between frontend and backend

1. **Read (existing route, new field).** `GET /api/factory/workflows/{id}?namespaceId=` returns `projection.expansion` for a run that has added steps. The field is absent otherwise. Shape: `{ sourceStepId, attemptId, resultId, resultHash, stepIds: string[], effectiveDefinitionHash, agentsVerified: boolean, expandedAt }`. The frontend uses only whether it is present, plus `stepIds` for display. The added steps are ordinary entries in `projection.steps`.
2. **New read.**

```
GET /api/factory/workflows/{workflowId}/expanded-definition?namespaceId=<id>
200 { "data": {
  "workflowId": "...",
  "source": { "workflowType": "architect-custom-flow", "version": "1.0.0", "definitionHash": "<hex>" },
  "expansion": { "sourceStepId", "attemptId", "resultId", "resultHash", "stepIds", "effectiveDefinitionHash" },
  "definition": { "schemaVersion": "1", "workflowType": "architect-custom-flow-derived", "version": "1.0.0",
                  "title": "<run title>", "steps": [ /* base + added steps, canonical, 'expansion' removed */ ] } } }
404 WORKFLOW_NOT_FOUND | 409 WORKFLOW_NOT_EXPANDED
```

3. The returned `definition` passes `WorkflowDefinitionValidator` as it is.
4. **Registration does not change.** It stays `POST /api/factory/workflow-definitions` with `If-None-Match: *`. No write endpoint is added, and the server never registers a definition on its own.

## 7. Verification criteria

### New backend tests (`factory-service`)

- `workflow/domain/WorkflowContinuationValidatorTest`:
  - A valid continuation is merged and its first steps are rewired.
  - Each of these is rejected: id clash, cycle, unknown dependency, dependency on a base step other than the expanding step, nested `expansion`, `outcomeTransitions`, more than 50 steps, invalid contract, unavailable agent.

  - `continuation` is accepted on PASS only.

- NEEDS_RESEARCH on the expanding step: no steps are added, and the existing research flow applies.
- A fragment of a parent Run refuses a continuation.
- The workstream `allowedWorkflowTypes` restriction may need `architect-custom-flow`. The skill documents this. Nothing changes it automatically.

## 8. Out of scope (separate tickets proposed)

- Continuations with `outcomeTransitions`. This needs the outcome ledger to be initialized after steps are added.
- Nested or repeated expansions, and expansion inside fragments of a parent Run.
- A Cockpit marker for added steps, and a diff view between the base definition and the expanded one.
- Automatic generic rewriting of the step text when saving (an LLM-assisted rewrite).
- Replacing the other duplicated definition lookup, in `RunService.buildFragmentOutcome`. This is not needed because fragments cannot add steps.
- Closing PR #1752, which uses a branch name outside the workstream convention.

## 9. Routes and order independence

- **backend**: everything in §6 Backend, including the skills and the OpenAPI files.
- **frontend**: everything in §6 Frontend.

The two routes run one after the other, in either order, so each side must work against the contract in §6 on its own. The frontend can mock `projection.expansion` and `GET .../expanded-definition` in its tests. The backend does not depend on the frontend.
