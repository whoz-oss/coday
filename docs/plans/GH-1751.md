# GH-1751 — On-the-fly workflow generation by the Architect, launch choice, promotion to a reusable definition

- Ticket: https://github.com/whoz-oss/coday/issues/1751 (GitHub issue, type: enhancement / user story)
- Work branch: `feature/GH-1751-architect-custom-workflow` (base `workstream/forge/master`)
- Routes: **backend** + **frontend**
- Risk: **high** (touches the session sequencer, the result channel and definition resolution)

## 1. Expected outcome

A steering agent that launches work without a named workflow asks the user to choose between an existing workflow, an upfront co-designed one, or an Architect-generated one; in the third mode a bootstrap run starts with an Architect step that submits a validated continuation DAG through `FACTORY_WORKER__submitStepResult`, Factory grafts it onto **that run only** and keeps executing it in the same session/worktree, and a run expanded this way can later be saved as a new immutable, versioned catalog definition.

## 2. Acceptance criteria

From the ticket (AC1–AC6), refined where the code imposes it. Items marked **(derived)** are mine.

1. **AC1 Launch triage.** The `factory-workstream` skill asks the user (via `queryUser`, one question with 3 options) how to proceed when no workflow type is given: (1) existing workflow, (2) create one upfront (hand over to `factory-workflow-authoring`), (3) Architect on the fly (start `architect-custom-flow`). It never picks one silently.
2. **AC2 Continuation submission.** `POST /api/factory/agent-step-results` accepts an optional `result.continuation = { steps: [...] }` (canonical `WorkflowStepDefinition` JSON), **only** on `PASS`, **only** for a step whose definition declares `expansion`.
3. **AC3 Synchronous validation.** An invalid continuation is rejected with `400 RESULT_SCHEMA_INVALID` and `details.violations[]` (`path`, `code`, `message`, never echoing submitted values). The capability is **not** consumed, so the Architect can fix and resubmit in the same turn. Checks: acyclic graph, step contracts, no id collision with base steps, valid `dependsOn`, routing/join rules, enabled namespace agents.
   - **(derived)** if the namespace agent list cannot be read, the continuation is accepted and the expansion evidence records `agentsVerified=false`, the same semantics as the existing `WorkspacePrecheckService` ("unverified", never assumed missing).
4. **AC4 Instance expansion.** An accepted continuation is persisted on the `WorkflowInstanceRecord` (instance + projection) and on the `WorkflowProjectionRecord`. Its roots depend on the Architect step. An audit evidence `workflow-expansion` is recorded, the steps show up in Cockpit through the normal projection + SSE, and they run in the same session, worktree and `rootCaseId`. **The definition catalog is unchanged** (no `saveDefinition`).
   - **(derived)** Idempotent and crash-safe: a replay of the same accepted result never grafts twice. A crash between the step finalization and the graft is reconciled on the next sequencer pass.
5. **AC5 Bootstrap definition.** `architect-custom-flow@1.0.0` is bundled in `resources/sessions/` and seeded like the other bundled sessions. It has a single agent step `architect-plan` (`Archay`) that declares `expansion`.
6. **AC6 Promotion.** For an expanded run, Factory exposes the canonical expanded definition as a **draft**: the base steps plus the grafted steps, with `expansion` removed. Cockpit opens it in the existing composer, where the user picks type, version and title and generalizes the prose, then registers it through the existing immutable `POST /api/factory/workflow-definitions` (`If-None-Match: *`). An authoring agent can do the same with `FACTORY_AUTHORING`.
7. **(derived) v1 restrictions**, rejected with explicit violation codes so they are never silently dropped:
   - At most one expander step per definition. It must be an `agent` leaf step (no dependents), with no `decision`.
   - Continuation steps cannot declare `expansion` (no recursive expansion) or `outcomeTransitions`. `OutcomeTransitionService.initialize` refuses runs that already have step states (`OUTCOME_LEGACY_RUN_REQUIRES_NEW_RUN`).
   - No expansion inside parent-Run fragments (`runId` present).
   - 1–50 continuation steps.

## 5. Design

### 5.1 Principle

The catalog stays immutable. An expansion is **instance-scoped data** attached to the run: the base definition stays pinned by `(workflowType, definitionVersion, definitionHash)`, and the run carries an `expansion` record. The effective definition is always computed by **one** resolver: base + expansion, re-validated, with its hash checked. Every consumer that today resolves the definition goes through this resolver. That replaces three duplicated look-ups and is required for correctness, so it is not an opportunistic refactor.

### 5.2 Definition contract (new optional step field)

```json
"expansion": { "mode": "append" }
```

- Only `mode: "append"` is accepted.
- Allowed on exactly one `agent` step with no dependents and no `decision`.
- Omitted from the normalized output when absent, so the hashes of existing definitions are unchanged.

### 5.3 Result contract (new optional business field)

```json
"continuation": { "steps": [ { "id": "...", "name": "...", "responsibility": {"kind":"agent","name":"Frontend"}, "dependsOn": [], "entry": [], "mission": "...", "exit": [] } ] }
```

- PASS only, 1–50 steps.
- Each step uses the canonical step schema (`decision` and `join` allowed).
- An empty `dependsOn` means "after the expander": Factory rewrites it to `[<expanderStepId>]`.
- `dependsOn` may reference only the expander or other continuation steps.
- The field is part of the canonical result hash. A divergent replay is a `RESULT_SEMANTIC_COLLISION`, as today.

Violation codes (`details.violations[].code`). Paths use the form `result.continuation.steps[i]...`.

| Code | Meaning |
|---|---|
| `CONTINUATION_NOT_ALLOWED` | The step has no `expansion`, the status is not PASS, or the run is a parent-Run fragment. |
| `STEP_ID_COLLISION` | A continuation step id already exists in the base definition. |
| `INVALID_DEPENDENCY` | A dependency on a base step other than the expander. |
| `UNSUPPORTED_IN_CONTINUATION` | The step declares `expansion` or `outcomeTransitions`. |
| `MAX_ITEMS` | More than 50 continuation steps. |
| `AGENT_NOT_AVAILABLE` | An agent step references an agent that is not enabled in the namespace. |
| `<WorkflowDefinitionErrorCodes>` | Errors forwarded from the merged-definition validation (`DEPENDENCY_CYCLE`, `MISSING_DEPENDENCY`, `INVALID_RESPONSIBILITY`, `INVALID_VALUE` + reason, ...), with the path mapped back to the continuation index. |

### 5.4 Persistence of an accepted expansion (instance-scoped)

The accepted expansion is written to `instance.instance["expansion"]` and mirrored in `projection["expansion"]`:

```json
{ "sourceStepId": "architect-plan", "attemptId": "...", "resultId": "...", "resultHash": "sha256:...",
  "steps": [ /* normalized continuation steps, roots rewired */ ],
  "stepIds": ["..."], "effectiveDefinitionHash": "<sha256 of merged normalized definition>",
  "agentsVerified": true, "expandedAt": "ISO-8601" }
```

In addition:

- `projection.steps` receives the grafted steps with status `pending`.
- `workflow_step_states` are initialized as `pending` (evaluation promotes them to `ready`).
- A `WorkflowEvidenceItem` of kind `workflow-expansion` is recorded, with outcome `pass` and idempotency key `workflow-expansion:<workflowId>:<resultId>`.
- An SSE hint is published.

### 5.5 Execution flow

1. The Architect step runs with an explicit brief that includes a new `## Workflow expansion` section, which gives the continuation rules and lists the base step ids.
2. On submission, `AgentStepResultService.submit` calls `WorkflowExpansionService.validateContinuation(...)` next to `validateRouting`, before persistence. On violations it throws `ResultSchemaInvalidException(details = violations)`, which leaves the capability unconsumed.
3. In `SessionRunService.executeStep`, after `terminal == COMPLETED`, for a step with `expansion` and an accepted result carrying a continuation, it calls `expansionService.graft(...)` inside `newTransaction`. If the graft fails, the step is FAILED, using the same pattern as `acceptRouting`. A PASS without a continuation is rejected at submission (`CONTINUATION_REQUIRED`), so a successful expander always expands.
4. After the graft, `runSessionLocked` reloads `steps` from the resolver, sets the new steps `pending`, recomputes the loop guard and continues. The grafted steps then run sequentially, and `prepareAgentWorkspace`, `rootCaseId` and the worktree binding apply unchanged.
5. Crash safety: at the start of each loop iteration, `expansionService.reconcile(...)` grafts if the expander is COMPLETED, has an accepted continuation and has no expansion recorded yet. The operation is idempotent on `resultId`, and a different `resultId` raises `EXPANSION_IMMUTABLE`.

### Frontend/backend contract

The frontend shows the action when the projection read (`GET /api/factory/workflows/{id}?namespaceId=`, field `projection.expansion`) is present. Shape: `{ sourceStepId, attemptId, resultId, resultHash, stepIds: string[], effectiveDefinitionHash, agentsVerified: boolean, expandedAt }`. Grafted steps are ordinary entries of `projection.steps`.

```
GET /api/factory/workflows/{workflowId}/expanded-definition?namespaceId=<uuid>
200 { "data": {
  "workflowId": "...",
  "source": { "workflowType": "architect-custom-flow", "version": "1.0.0", "definitionHash": "<hex>" },
  "expansion": { "sourceStepId", "attemptId", "resultId", "resultHash", "stepIds", "effectiveDefinitionHash" },
  "definition": { "schemaVersion": "1", "workflowType": "architect-custom-flow-derived", "version": "1.0.0",
                  "title": "<run title>", "steps": [ /* base + grafted, canonical, 'expansion' removed */ ] } } }
404 WORKFLOW_NOT_FOUND | 409 WORKFLOW_NOT_EXPANDED
```

The `definition` passes `WorkflowDefinitionValidator` as is. Registration remains `POST /api/factory/workflow-definitions` (existing, unchanged). No new write endpoint is added, and the server never auto-registers.

## 7. Verification criteria

### New tests (backend, `factory-service`)

- `workflow/domain/WorkflowContinuationValidatorTest`:
  - A valid continuation is merged and its roots are rewired.
  - Rejections: id collision, cycle, unknown dependency, dependency on a non-expander base step, nested `expansion`, `outcomeTransitions`, more than 50 steps, invalid contract, unavailable agent.
  - A null agent list gives `agentsVerified=false`.
  - Violations never contain submitted values.
- `WorkflowDefinitionValidatorTest` (additions):
  - Accepts `expansion` on a leaf agent step.
  - Rejects it on human or code steps, on a step with dependents, with `decision`, and when two expanders exist.
  - A definition without `expansion` keeps its normalized keys, and its `CanonicalHash` is unchanged.
- `AgentStepResultValidationTest`: `continuation` is accepted on PASS only, malformed shapes are rejected, and the boolean validation stays equivalent to violations.
- `AgentStepResultServiceIntegrationTest` (additions):
  - An invalid continuation gives `RESULT_SCHEMA_INVALID` with violations, the payload stays `capability-reserved` and the outbox is empty, then the corrected resubmission is accepted.
  - A continuation on a non-expander step is rejected.
  - An expander PASS without a continuation is rejected.
- `workflow/WorkflowExpansionIntegrationTest` (new, modelled on `ConditionalRoutingIntegrationTest`): run `architect-custom-flow`, the expander PASSes with a 2-step continuation (agent + human), then check:
  - The instance and projection contain the grafted steps, and the evidence `workflow-expansion` is present.
  - The steps run in order on the same `rootCaseId`.
  - The catalog is unchanged (`listDefinitions` size and hashes).
  - Replaying the result is a no-op.
  - A simulated crash after finalization is reconciled.
  - Tampering with `effectiveDefinitionHash` gives `WORKFLOW_DEFINITION_MISMATCH`.
  - A human checkpoint inside the continuation can be replied to (this covers the `WorkflowService` resolver path).
- `WorkflowControllerHttpTest` (addition): `expanded-definition` returns 200 with a draft that validates through `POST /workflow-definitions/validate`, and 409 `WORKFLOW_NOT_EXPANDED` for a plain run.
- `SessionDefinitionCatalogTest` (addition): `architect-custom-flow@1.0.0` loads and validates.

## 8. Out of scope (separate tickets proposed)

- Continuations with `outcomeTransitions` (needs the ledger to be initialized after a graft).
- Recursive or multiple expansions, and expansion inside parent-Run fragments.

- Automatic generalization of prose during promotion (an LLM-assisted rewrite).
- Consolidating the remaining duplicated definition look-ups in `RunService.buildFragmentOutcome`. This is not needed, because fragments cannot expand.
