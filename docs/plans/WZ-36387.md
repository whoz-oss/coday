# WZ-36387 — Extract blocker classification out of the Cockpit action bar

Jira: https://whoz.atlassian.net/browse/WZ-36387 (Task, epic WZ-36044 "FP - Forge - Feb 2027")
Branch: `work/forge/WZ-36387-extract-blocker-classification` → PR base `workstream/forge/master`
Sides: **frontend only** (`apps/factory-cockpit`). No backend, API or template behaviour change.

## 1. Expected outcome

The blocker classification logic of the Factory Cockpit action bar (kind, grouping, icon, group title) lives in a
pure, unit-tested module under `apps/factory-cockpit/src/app/core/`, and `ActionBarComponent` only delegates to it,
with exactly the same rendered output as today.

## 2. Acceptance criteria

From the ticket:

- **AC1**: the blocker classification (`blockerKind`, `blockerGroups`, `blockerIcon`, `groupTitle`) is moved out
  of `action-bar.component.ts` into a pure function `classifyBlockers` under `apps/factory-cockpit/src/app/core/`.
- **AC2**: the blocker tests of `action-bar.component.spec.ts` become unit tests of that function; **one**
  rendering test of the blockers stays in the component spec.
- **AC3**: no behaviour change (same groups, same order, same CSS classes, icons, labels and group titles).

Derived (flagged **[derived]**):

- **AC4 [derived]**: `action-bar.component.ts` falls back to the ~200-line guideline (it is ~297 lines today;
  removing ~90 lines of classification brings it near 205).
- **AC5 [derived]**: `action-bar.component.html` and `action-bar.component.scss` are not modified (the template
  keeps calling `blockerGroups()`, `blockerIcon(...)` and `groupTitle(...)`).
- **AC6 [derived]**: the component tests that check that a blocker alone never renders an action form
  (`renders no retry form without the allowed action, even for a failed-step blocker`,
  `does not show a research form from the blocker alone`) stay in the component spec: they test the
  allowed-actions invariant, not the classification.

## 4. Analysis

### 4.1 Current code

`apps/factory-cockpit/src/app/features/session/action-bar/action-bar.component.ts`:

- `blockerKind(blocker)` (protected method): switch on `blocker.code` →
  `WAITING_HUMAN_INTERACTION`→`waiting`, `NEEDS_RESEARCH`→`research`, `ATTEMPT_FAILED`|`VERIFICATION_FAILED`→
  `failure`, `STEP_BLOCKED`→`consequence`, `REAL_COST_PAUSED`→`cost`, `UNKNOWN_RUNTIME`→`indeterminate`,
  default→`unknown`.
- `blockerGroups` (computed): `{ failures, consequences, waiting, research, cost, indeterminate, unknown }`, each
  a `filter` of `blockers()` preserving input order; `unknown` = every blocker that is none of the six other kinds
  (strictly equivalent to `kind === 'unknown'` since the kind union is exhaustive).
- `blockerIcon(blocker)`: `waiting`→`person_alert`, `research`→`info`, `failure`→`error`,
  `consequence`→`link_off`, `cost`→`paid`, `indeterminate`→`help`, default→`warning`.
- `groupTitle(kind: 'failure'|'consequence'|'waiting'|'cost'|'indeterminate'|'unknown')`: `Root failures`,
  `Blocked steps (consequence)`, `Waiting for human`, `Budget pause`, `Indeterminate state`, default
  `Other blockers`.
- `hasBlockers` (computed, `blockers().length > 0`) — stays in the component (view concern).

Template `action-bar.component.html` uses `blockerGroups().failures|consequences|research|waiting|cost|
indeterminate|unknown`, `blockerIcon(blocker)` and `groupTitle('failure'|'consequence')`. Nothing else in the
cockpit references these members (search on `blockerKind` returns only this component).

Models: `WorkflowBlocker` and `BlockerCode` in `apps/factory-cockpit/src/app/core/models.ts`.

### 4.2 Pattern to follow

`apps/factory-cockpit/src/app/core/step-command-feedback.ts` (+ `.spec.ts`): a framework-free module of exported
types and pure functions in `core/`, imported by the component, tested with plain Jest `describe/it` without
`TestBed`. Same file naming (kebab-case, no `.service` suffix).

### 4.3 Regression risk areas

- Template bindings: if the component members are renamed or removed, the template breaks at compile time
  (caught by `build`/tests). Keeping the same member names avoids touching the template.
- Group order inside each bucket must stay the input order ("preserving ALL root failures").

## 5. Scoped change (frontend only)

### 5.1 New file `apps/factory-cockpit/src/app/core/blocker-classification.ts`

Pure module, no Angular import. Imports only `WorkflowBlocker` from `./models`. Exports:

```ts
export type BlockerKind = 'waiting' | 'research' | 'failure' | 'consequence' | 'cost' | 'indeterminate' | 'unknown'

/** Blockers bucketed by kind; each bucket keeps the input order. */
export interface BlockerGroups {
  failures: WorkflowBlocker[]
  consequences: WorkflowBlocker[]
  waiting: WorkflowBlocker[]
  research: WorkflowBlocker[]
  cost: WorkflowBlocker[]
  indeterminate: WorkflowBlocker[]
  unknown: WorkflowBlocker[]
}

export function blockerKind(blocker: WorkflowBlocker): BlockerKind
export function classifyBlockers(blockers: readonly WorkflowBlocker[]): BlockerGroups
export function blockerIcon(blocker: WorkflowBlocker): string
export function blockerGroupTitle(kind: Exclude<BlockerKind, 'research'>): string
```

- Move the bodies **verbatim** (same switch cases, same return strings) and move the KDoc of `blockerKind`
  (kind meanings) and of `blockerGroups` ("preserving ALL root failures, never picking a single first one").
  Add the `NEEDS_RESEARCH → research` line that is missing from the existing KDoc list.
- `classifyBlockers`: build the seven arrays in one loop (`for … of`, push into the bucket of `blockerKind(b)`)
  or keep the seven `filter`s; either preserves the input order. `unknown` = `kind === 'unknown'`.
  Always return all seven keys, empty arrays included.
- `blockerGroupTitle` keeps the current parameter type (research excluded) so no behaviour or typing widening.

### 5.2 `apps/factory-cockpit/src/app/features/session/action-bar/action-bar.component.ts`

- Delete the `blockerKind` method, the `blockerGroups` computed body, `blockerIcon` and `groupTitle` methods.
- Import from `'../../../core/blocker-classification'` and keep the same template-facing member names:
  ```ts
  protected readonly blockerGroups = computed(() => classifyBlockers(this.blockers()))
  protected readonly blockerIcon = blockerIcon
  protected readonly groupTitle = blockerGroupTitle
  ```
- Keep `hasBlockers` as is. No other change in the component (inputs, outputs, intents, KDoc of the class).

### 5.3 Not modified

`action-bar.component.html`, `action-bar.component.scss`, `_action-card.scss`, `core/models.ts`.

### 5.4 Out of scope (separate ticket to propose if wanted)

- The template repeats the same blocker row markup seven times; factoring it into an `ng-template` or a small
  `sf-blocker-row` component would shrink the template, but it is a template refactor, not part of this ticket.
- The legacy `.blocker--blocked` CSS class in the SCSS is no longer produced; removing it is a separate cleanup.

### 5.5 Implementation order

1. Create `core/blocker-classification.ts` and its spec (green on its own).
2. Wire the component to it and delete the moved members.
3. Move/trim the blocker tests of the component spec (§6.1).

## 6. Verification criteria

### 6.1 Tests

New `apps/factory-cockpit/src/app/core/blocker-classification.spec.ts` (plain Jest, no `TestBed`), taking over
the classification assertions of the component spec:

- `blockerKind` maps each of the 7 `BlockerCode` values to its kind, and an unknown code (cast
  `'SOMETHING_ELSE' as BlockerCode`) to `unknown`.
- `classifyBlockers`:
  - `ATTEMPT_FAILED` and `VERIFICATION_FAILED` land in `failures` (from "classifies ATTEMPT_FAILED and
    VERIFICATION_FAILED as real failures");
  - `STEP_BLOCKED` lands in `consequences`, not `failures` (from "groups STEP_BLOCKED as consequences": 1 failure,
    2 consequences);
  - `UNKNOWN_RUNTIME` lands in `indeterminate`, not in `failures`/`consequences` (from "renders UNKNOWN_RUNTIME as
    indeterminate");
  - `NEEDS_RESEARCH` lands in `research`, not in `failures`/`indeterminate` (from "renders NEEDS_RESEARCH as
    information/access needed" — classification half);
  - several root failures are all kept, in input order (`toEqual([build, test])`) (from "supports multiple root
    failures simultaneously");
  - an empty input returns the seven keys with empty arrays; an unknown code lands in `unknown` only.
- `blockerIcon`: one expectation per kind (`person_alert`, `info`, `error`, `link_off`, `paid`, `help`, `warning`).
- `blockerGroupTitle`: the six titles, exact strings.

`apps/factory-cockpit/src/app/features/session/action-bar/action-bar.component.spec.ts`:

- Remove the four classification tests listed above (`classifies ATTEMPT_FAILED…`, `groups STEP_BLOCKED…`,
  `renders UNKNOWN_RUNTIME…`, `supports multiple root failures…`) and `renders NEEDS_RESEARCH…`.
- Keep **one** rendering test, `renders blockers with a visual class per blocker nature`, extended so that it
  still proves the template wiring of every bucket: input one blocker of each of the 7 codes + one unknown code;
  assert 8 `.blocker` elements, one each of `.blocker--failure`, `--consequence`, `--research`, `--waiting`,
  `--cost`, `--indeterminate`, `--unknown` (failure group having 2 with `VERIFICATION_FAILED` is optional), the
  headers `.blocker-group-title--failure` (text `Root failures`) and `.blocker-group-title--consequence`, and the
  research label `Information or access needed`.
- Keep unchanged: `renders no action button when nothing is authorized`, `renders no retry form without the
  allowed action, even for a failed-step blocker`, `does not show a research form from the blocker alone`, and
  every action/intent test.

No "fails before / passes after" case: this is a behaviour-preserving refactor; the kept rendering test is the
non-regression guard and must pass both before and after the change.
