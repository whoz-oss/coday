# WZ-36379 — Stopping a workflow run does not stop AgentOS agents and leaves the run RUNNING

- Jira: https://whoz.atlassian.net/browse/WZ-36379 (Bug)
- Branch: `work/forge/WZ-36379-stop-run-kills-agents` → base `workstream/forge/master`
- Sides concerned: **backend only** (factory-service). The Factory Cockpit already renders `cancelled`; no frontend change.
- Risk level: **medium** (concurrency between the cancel command and the sequencer thread; durable state machine; parent Run driver).
- Revision 2: corrected after the review of PR #1770 (see section 9, *Review feedback*).

## 1. Expected outcome

Clicking **Stop** on a running Factory run kills the AgentOS case and all its active descendant sub-cases with an authenticated
request, and the step and the run leave `running` for the terminal `cancelled` state (backend projection and cockpit).

**Observed vs expected.** Observed: `POST /api/factory/workflows/{workflowId}/attempts/{attemptId}/cancel` moves the durable attempt to
`interrupted / USER_CANCELLED`, but the AgentOS case keeps running and the step + run stay `running` forever (runs
`45717d0c-ede8-3ea9-b8e1-cf01447dc6bf`, `ddcb8f34-35af-317f-bc8d-8c8b0060a0d7`); the cockpit hides Stop because the attempt is terminal.
Expected: agents stopped, step `cancelled`, run `cancelled`. Reproduction steps: **complete** (start any agent workflow, click Stop
while the agent step runs).

## 2. Acceptance criteria

1. (ticket) Stop sends an authenticated kill to AgentOS (`POST /api/cases/{caseId}/kill` with `X-External-User-Id`), which stops the
   case and its active descendants (AgentOS `CaseServiceImpl.killCase` already kills `findActiveDescendants`).
2. (ticket) The stopped step and the run transition out of `running` to the terminal `cancelled` state, in the backend projection
   and in the cockpit. For a fragment of a parent Run, the parent Run becomes `cancelled` too (no next fragment).
3. (ticket, **amended**) The execution slot is freed: the per-workflow sequencer lock is released and the durable continuation
   is drained. The worktree occupancy of the cancelled attempt is **retained** (fail-closed): AgentOS gives no proof that a tool
   still running in the worktree has stopped. Its release is a follow-up (section 6, *Out of scope*). To be confirmed by the reporter.
4. (derived) A kill HTTP failure is logged at WARN with the case id and status, never silently swallowed, and never throws.
5. (derived) A user Stop is **final** for the run: step `cancelled`, dependents `blocked`, run `cancelled`, nothing dispatched
   afterwards, including by a later continuation. Retrying or continuing a cancelled run is not allowed (same rule as WZ-36045,
   which refuses `cancelled` runs); resuming the work means starting a new run.
6. (derived) Runs already stuck (attempt `interrupted/USER_CANCELLED`, step `running`) are sealed `cancelled` by the next
   `runSession` of that workflow, without dispatching a new agent turn and even when the workspace precheck would fail.
7. (derived) Only the user who launched the run (the persisted `controllerRequest.actorId`) can stop it; anyone else gets
   `403 ACTION_NOT_ALLOWED` before any write or remote call.
8. (derived) The outcome is deterministic whichever side wins the race between the cancel command and a sequencer that finalizes
   the attempt (section 5).

## 4. Root cause (proof)

Four combined defects:

1. **Unauthenticated kill, silently swallowed** —
   `factory/factory-service/src/main/kotlin/io/whozoss/factory/adapter/agentos/DefaultAgentOsExecutionAdapter.kt`, `postKill(caseId)`:
   `client.post().uri("/api/cases/$caseId/kill").retrieve().toBodilessEntity()` sends no `X-External-User-Id` (every other call of
   the adapter does) and `catch (_: Exception) { // ignored }`. *Derived from the code, not from logs*: `killCase` is guarded by
   `Case DELETE`, so a request without identity cannot be authorized, and the error is hidden; this matches the observed symptom (the
   case keeps running). The new adapter tests prove the header is now sent and a refusal is logged.
2. **Fencing exception leaves the step RUNNING** — `BridgeCancellationService.requestCancel` → `Neo4jDurableAgentAttemptRepository.cancel`
   rotates `ownerToken` to `cancel:$attemptId`. The sequencer then calls `DurableAgentAttemptService.finalize(... reservation.ownerToken ...)`
   → `assertNotFenced` throws `AttemptLeaseFencingException`. `SessionRunService.executeStep` catches it and returns `null`; the step
   stays `running` and `SessionSequencer.terminalStatus` persists the run as `running`.
3. **No continuation when no sequencer observes** — the cancel command only mutates the attempt. On replay, `runSessionLocked`'s prelude
   turns a `RUNNING` step with a terminal attempt into `READY` (`hasFinalizedAttempt`) and `terminalAgentExecution` classifies the
   interrupted attempt as `AgentFailed(AGENT_INTERRUPTED)` → `failed`, never `cancelled`; and nothing enqueues that replay.
4. **Kill-then-cancel ordering** (found in review) — the original command killed first, then wrote the durable cancel. A sequencer
   observing the case receives `KILLED` (derived `Interrupted` through `interruptReasons`) and can finalize the attempt with its still
   valid owner token before the cancel is written: no fencing, step `failed`, and the cancel then fails after the agents were killed.

## 5. Design

**The sequencer stays the only writer of step/run status.** The cancel command never writes the projection.

**Authority for a user stop: the durable cancel, written first.** `requestCancel` order is
(1) Factory-side authorization, (2) durable revision-fenced cancel (`INTERRUPTED/USER_CANCELLED`, owner token rotated),
(3) authenticated kill, (4) post-kill reconcile, then the controller enqueues a continuation. Consequences, one per ordering:

- **Cancel commits first** (normal case): every later write of the live sequencer (`transition`, `finalize`) is fenced; the sequencer
  catches `AttemptLeaseFencingException`, recognises the user cancellation and seals the step `cancelled`. The kill can no longer
  produce a competing `failed` verdict.
- **Sequencer finalizes first** (the agent finished, or failed, just before the click): the attempt is already terminal, the cancel is
  rejected `409 ATTEMPT_INVALID_TRANSITION` **before** any kill; the step keeps its real verdict. Nothing is left running.
- **Stale revision**: `409 REVISION_CONFLICT` before any kill.
- **Cancel committed, kill refused or unreachable**: the step and run are still sealed `cancelled` (the user's intent is durable),
  `killAcknowledged=false` is returned and logged at WARN; the operator can kill the case from AgentOS.

**Recognising a user cancellation is bound to the attempt being sealed**, never to "some old attempt of the step":
the guard is true only when the latest attempt of the step is `INTERRUPTED/USER_CANCELLED`, the step is in a status a live attempt
holds (`RUNNING` or `WAITING_HUMAN`, **not** `READY`/`PENDING`), and, for outcome-managed runs, the attempt is pinned to the
step's current execution (`contextEnvelope.inputs.stepExecutionId == execution.executionId`). A legitimate re-arm (retry, research
resumption, answer resumption) either registers a new attempt or leaves the step `READY`, so it is never re-sealed.

**Identity and authorization.** Factory acts as the workflow principal only for the user who owns the run: the caller must equal the
persisted `controllerRequest.actorId`, checked before any write; the kill then carries that same identity. No other user can stop a
run through Factory (admin stop of somebody else's run: follow-up).

## 6. Scoped change (backend, file by file)

### 6.1 `factory/factory-service/src/main/kotlin/io/whozoss/factory/adapter/agentos/AgentRuntimeAdapter.kt`
Identity-carrying overload, defaulted so existing adapters/fakes stay source-compatible and fail-closed:
`fun interrupt(caseId: String, reason: String, externalUserId: String?): Boolean { interrupt(caseId, reason); return false }`.

### 6.2 `.../adapter/agentos/DefaultAgentOsExecutionAdapter.kt`
- `postKill(caseId, externalUserId: String?): Boolean`: sets `X-External-User-Id` **only from the explicit argument** (no fallback to
  the recorded identity), returns `true` on 2xx, logs WARN with case id and HTTP status otherwise, never throws.
- `interrupt(caseId, reason, externalUserId)`: records `interruptReasons[caseId]`, returns `postKill(caseId, externalUserId)`.
- `interrupt(caseId, reason)` and `kill(caseId)` call `postKill(caseId, null)`: the escalation and shutdown kills keep their current
  (unauthenticated) request, only the swallowed error becomes a WARN log.

### 6.3 `.../agentattempt/service/BridgeCancellationService.kt`
- Constructor: `attempts`, `adapter`, `workflowRepository: WorkflowRepository? = null`. **No** occupancy service.
- `requestCancel(scope, ns, wf, attemptId, expectedRevision, reason, actorId: String)` (actor now required):
  1. find the attempt (404), idempotent return when already `INTERRUPTED`, `409` when terminal otherwise (unchanged);
  2. `owner = persisted controllerRequest.actorId`; if `owner == null || owner != actorId` → throw
     `workflowException(WorkflowErrorCodes.ACTION_NOT_ALLOWED, "Only the user who launched the run can stop it.")` (403). Also
     applied on the idempotent path, before returning;
  3. durable `attempts.requestCancel(..., USER_CANCELLED)`;
  4. `killed = adapter.interrupt(attempt.caseId, reason, owner)`;
  5. `runCatching { adapter.reconcile(caseId) }`;
  6. return `CancellationOutcome(..., killAcknowledged = killed)`.
- Remove `releaseOccupancy` and its call (occupancy retained, AC3).

### 6.4 `.../workflow/web/WorkflowController.kt` — `cancelAttempt`
- Pass `caller.actorId` (required).
- After the outcome, including on an idempotent replay: best-effort `sessionRunSubmissionService.submit(..., "attempt-cancelled:$attemptId", null)`
  with the same repo-root resolution as `runInternal`; WARN and skip when no root resolves; never turns the committed cancel into a 500.
- Response: additive `killAcknowledged`.

### 6.5 `.../capability/CapabilityExecutionService.kt`
- `const val USER_CANCELLED = "USER_CANCELLED"`.
- `fun userCancelledAttemptId(scope, ns, wf, stepId): String?` replaces the boolean `isUserCancelled`: returns the latest attempt id
  when it is `INTERRUPTED/USER_CANCELLED` **and**, when the step state carries an `execution`, that attempt's
  `contextEnvelope.inputs.stepExecutionId` equals the current `executionId`; `null` otherwise. Remove `latestAttemptId` (the id comes
  from this call).

### 6.6 `.../workflow/service/SessionRunService.kt`
1. `recordStepCancellation(..., attemptId, ...)` takes the bound attempt id (evidence `session-step`, `outcome=cancelled`,
   `code=USER_CANCELLED`, `attemptId`, `executionId`, idempotency key `session-step-cancelled:<wf>:<step>:<attemptId>`), CANCELLED
   transition and status in one fresh transaction (unchanged shape).
2. `executeStep`, fencing catch: `userCancelledAttemptId(...)?.let { recordStepCancellation(...); return CANCELLED }`, else the
   existing hand-off `return null`.
3. **Ordering in `runSessionLocked`**: after `outcomeTransitionService?.initialize(...)`, move `loadProgress(...)` and a new
   cancellation prelude **before** `workspacePrecheckService?.precheck(...)`. Prelude: for each agent step whose status is in
   `USER_CANCELLABLE_STATUSES = {RUNNING, WAITING_HUMAN}` (drop `READY`) and `userCancelledAttemptId(...) != null`, seal it. If any step
   is `CANCELLED` after the prelude, call `applyEvaluation` (blocks dependents), skip the precheck and the loop, and go straight to
   `terminalStatus`/`persistProjection`/`onFragmentSessionUpdated`. Otherwise keep the existing precheck and replay prelude unchanged.
4. Dispatch guard after `applyEvaluation` in the loop: keep `if (any CANCELLED) return@run` (AC5: a Stop is final for the run).
5. `persistProgressProjection`: keep the `CANCELLED && none RUNNING -> CANCELLED` branch.

### 6.7 `.../workflow/domain/SessionSequencer.kt` — `terminalStatus`
Keep the first rule `any CANCELLED && none RUNNING -> CANCELLED`.

### 6.8 `.../run/service/RunService.kt` — `onFragmentSessionUpdated` (new)
When `sessionResult.status == WorkflowStatuses.CANCELLED`: do **not** call `selector.reduce/next`. In the existing transaction, seal the
parent Run with a `RunDecisionRecord(decisionKey = fragmentId, decisionType = "cancelled", reason = "USER_CANCELLED: fragment <id> stopped by the user")`,
fragment status `cancelled`, run status `RunStatuses.CANCELLED`, the `run-flow-decision` evidence and the SSE publish (same helpers as
`FlowDecision.Fail`), then `notifyRunFinished`. Idempotent through the existing `decisions.containsKey(fragmentId)` guard.

### 6.9 OpenAPI
`factory/factory-service/openapi/factory-openapi.yaml`: the cancel route responds with `WorkflowDataEnvelopeMapStringObject`
(free map), so `killAcknowledged` needs no schema change. Update the route summary to
`"Explicitly cancel a durable agent attempt (owner only, durable cancel then authenticated kill + reconcile)."` and keep the file in
sync with the generated one if the build checks it.

### Out of scope (separate tickets to open)
- Release of the worktree occupancy of a cancelled attempt, once AgentOS exposes a proof that the case and its descendants stopped
  (kill completion / runtime quiescence).
- Stop by a namespace admin who is not the run owner (needs an AgentOS-side permission check on the caller).
- Authenticated escalation and shutdown kills, and authenticated adapter reads after a Factory restart.
- Cockpit: a dedicated "stopped" chip instead of `failed` for a `cancelled` run.

## 7. Contract

No frontend change. `POST .../attempts/{attemptId}/cancel`: request unchanged; response gains `killAcknowledged: boolean`; new error
`403 ACTION_NOT_ALLOWED` when the caller is not the run owner (the cockpit already surfaces errors and only shows Stop on the user's
runs in practice). Step/run/parent-Run status may be `cancelled`, already handled by the cockpit
(`mapWorkflowStateToRunStatus('cancelled') → 'failed'`). AgentOS contract: `POST /api/cases/{caseId}/kill` with
`X-External-User-Id: <run owner>`.

Implementation order: 6.1 → 6.2 → 6.5 → 6.7 → 6.6 → 6.8 → 6.3 → 6.4 → 6.9.

## 8. Verification criteria

New or corrected tests (each fails before the change, passes after):
1. `DefaultAgentOsExecutionAdapterTest`: interrupt with an identity sends the header and returns true; a 403 kill returns false and
   never throws; `kill(caseId)` sends **no** header (scope unchanged).
2. `SessionSequencerTest`: `terminalStatus` is `cancelled` with a cancelled step and pending dependents, `running` while another step runs.
3. `StopRunCancellationIntegrationTest` (embedded Neo4j), **deterministic orderings**:
   - *Cancel first*: the fake `interrupt` only records the identity; the test releases the observation latch **after** `requestCancel`
     returned. Expect step `cancelled`, B `blocked`, run `cancelled`, one cancellation evidence bound to the attempt, attempt still
     `INTERRUPTED/USER_CANCELLED`, kill identity = run owner.
   - *Sequencer first*: the observation returns a FAIL/PASS result and `runSession` completes; then `requestCancel` → `409`, no
     `interrupt` call, step keeps its verdict.
   - *Stuck run*: as today, plus a variant where the workspace precheck throws: the run is still sealed `cancelled`.
   - *No dispatch after cancel* and *execution slot freed*: a second `runSession` returns immediately (not blocked on the lock),
     changes nothing, dispatches nothing; the `attempt-cancelled:<id>` outbox event is drained.
   - *Re-arm not resealed*: a step whose latest attempt is user-cancelled but which is `READY` (or whose execution id differs) is
     **not** sealed and is dispatched.
4. `BridgeCancellationServiceTest`: a caller other than the owner gets 403 with no cancel and no kill; the owner gets the durable cancel
   before the kill (assert the attempt is `INTERRUPTED` when the fake `interrupt` is invoked); occupancy is untouched.
5. `WorkflowCancelAttemptHttpTest`: one `session_run_requested` outbox event `attempt-cancelled:<attemptId>`, `killAcknowledged` in the
   response, 403 for a non-owner.
6. `RunService` test (parent Run): a fragment returning `cancelled` seals the run `cancelled`, creates no next fragment, never calls
   the selector, and is idempotent on replay.

Existing tests that must stay green: `BridgeCancellationServiceTest`, `DefaultAgentOsExecutionAdapterTest`,
`DurableAttemptSealingTest`, `DurableAgentOsBridgeIntegrationTest`, `SessionSequencerIntegrationTest`,

## 9. Review feedback (PR #1770, review of the plan at c739a64c)

The implementation commit `61ea6780` already follows revision 1 and already writes the durable cancel before the kill. Corrections for
Builder, by blocking defect:

1. **Guard not bound to the execution / no policy for retry** — plan error. Replace `isUserCancelled`/`latestAttemptId` by
   `userCancelledAttemptId` (6.5), drop `READY` from `USER_CANCELLABLE_STATUSES` (6.6.3), bind to the execution for outcome-managed
   runs. Policy made explicit (AC5): a Stop is final, a cancelled run cannot be retried or continued, consistent with WZ-36045 (now
   listed in section 3). Test: *re-arm not resealed* (8.3).
2. **Race kill vs durable cancel** — plan error (section 4.4). The ordering is now decided: durable cancel first, kill second (section 5),
   already done in `61ea6780`; keep it. Rewrite the live test so it is deterministic (latch released by the test after `requestCancel`,
   not inside `interrupt`) and add the *sequencer first* test (8.3).
3. **Security** — plan error.
   (a) Impersonation: add the owner check in `BridgeCancellationService` (6.3 step 2), make `actorId` required; revert the identity
   fallback in `postKill` so escalation/shutdown kills keep their behaviour (6.2).
   (b) Fail-open release: remove `releaseOccupancy` entirely (6.3); occupancy retained, AC3 amended, follow-up ticket.
   (c) Ambiguous handle: moot once the release is removed.
4. **Gaps** — plan gaps.
   1) Parent Run: implement 6.8 + test 8.6. 2) Execution slot: covered by construction (lock released on return, continuation drained),
   now verified by 8.3. 3) OpenAPI: 6.9. 4) Precheck ordering: move the cancellation prelude before the precheck (6.6.3) + precheck
   variant of the stuck-run test. 5) Section 4 now lists four defects, and states that the 401/403 is derived from the code.
