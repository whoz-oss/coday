# WZ-36423 — Surface workspace pre-check failures instead of leaving the run stuck in "Waiting"

> Source: Jira WZ-36423 (Bug, status **En cours** / In Progress, 3 technical pointers: handle the exception in
> `SessionRunService.runSessionLocked`, expose a blocker in `WorkflowService.workflowActions`, surface it in the
> Cockpit; no comments, no attachments, no links), re-read on this replay. The plan is derived from the code of
> `workstream/forge/master` (re-checked at `7e91b7e22`: the pre-check call site in `runSessionLocked` is unchanged)
> and from the validated plan and review notes of the closed PR #1796 (see section 7).

## 1. Expected outcome

When the read-only workspace pre-check refuses a run (missing agents, Git not configured, auto-worktree disabled,
unresolvable workstream...), the run ends in the `failed` state with a durable, explainable reason that the Cockpit
shows on the session page (action bar + event log) and on the run card, instead of staying in `ready` ("Waiting")
forever.

**Type:** bug.

- **Observed:** in `SessionRunService.runSessionLocked`, the `workspacePrecheckService?.precheck(...)` call (in the
  non-cancelled `else` branch) is not guarded. The `WorkspacePrecheckException` escapes the method: no evidence, no
  step state change, no `persistProjection`, no `sseHub.publish`. `OutboxDrainWorker` catches it, defers the
  continuation as non-transient (dead) and only logs a WARN. The projection keeps the `ready` status written by
  `WorkflowService.start`, and `workflowActions` returns `blockers: []`.
- **Expected:** refusing the run is correct, but the reason is persisted (evidence), the ready step(s) and the run
  become `failed`, dependants become `blocked`, the projection is refreshed and invalidated over SSE, and
  `GET .../actions` / `GET .../blockers` return an actionable blocker carrying the pre-check code, the message
  (missing agents) and the remedy.
- **Reproduction steps:** complete — launch any workflow whose agent step names an agent that is missing or disabled
  in the namespace (not returned by `GET /api/agent-configs/by-parentId/{namespaceId}`).

## 2. Acceptance criteria

1. AC1 — When `precheck(...)` throws `WorkspacePrecheckException`, `runSessionLocked` does not let it escape. It
   records ONE durable `WorkflowEvidenceItem` with `kind = "workspace-precheck"`, `outcome = "failed"`,
   `stepId = null`, and `facts` containing `code` (= `errorCode`), `message`, `remedy` and the other `details`
   entries the exception carries (`missingAgents`, `availableAgents`, `namespaceId`, `checkoutStatus`,
   `failureReason`, `workstreamId`...).
2. AC2 — Every step that is `ready` at that moment (on a first run: the root steps) becomes `failed` (session-step
   FAILED evidence + transition + step state); its dependants become `blocked` through `applyEvaluation`; the run
   becomes `failed`; the projection is persisted and an SSE invalidation is published.
3. AC3 — `runSession` returns normally (`SessionRunResult.status == "failed"`), so the outbox continuation completes
   instead of going dead. No agent turn, no `prepareAgentWorkspace`, no `resolveAndRecord`, no worktree resolution,
   no replay/resume prelude happens.
4. AC4 — `WorkflowService.workflowActions` returns a blocker `code = "WORKSPACE_PRECHECK_FAILED"`, `stepId = null`,
   a `message` containing the pre-check message (listing the missing agents) and the remedy, and `details` = the
   pre-check code (e.g. `REQUIRED_AGENTS_MISSING`). The same blocker (with `details`) is returned by
   `GET /api/factory/workstream-service/workflows/{workflowId}/blockers` and in `get_workflow.blockers`.
5. AC5 — Cockpit: `<sf-action-bar>` shows the blocker in the "Root failures" group with its message and its details;
   the run card shows the `failed` chip and the pre-check message; the session event log shows the pre-check
   evidence message.
6. AC6 (derived) — Replays are idempotent: a second continuation hitting the same refusal appends no second identical
   `workspace-precheck` evidence (idempotency key) and does not touch already terminal steps.
7. AC7 (derived) — Any other exception thrown by the pre-check keeps its current behaviour (propagates unchanged).
   The user-Stop path (`runCancelled`) is unchanged: it still runs before and without the pre-check.

## 4. Code analysis

### Root cause (single)

`factory/factory-service/src/main/kotlin/io/whozoss/factory/workflow/service/SessionRunService.kt`,
`runSessionLocked`, `else` branch of `if (runCancelled)`:

```kotlin
workspacePrecheckService?.precheck(scope = scope, namespaceId = namespaceId, callerExternalUserId = ...,
    requiredAgents = ..., requireGitWorkspace = requiresGitWorkspace)
```

The call is not wrapped. `WorkspacePrecheckException` (`factory/.../workspace/WorkspacePrecheckException.kt`, a
`FactoryException` with `errorCode` + `details: Map<String, Any?>`) unwinds through `runSession` (which only catches
`TransientWorkspaceAdoptionException`) to `OutboxDrainWorker`, whose generic catch defers the continuation as dead.
`loadProgress` has already put the root steps in `ready` (and, for outcome-managed runs,
`outcomeTransitionService.initialize` has already created the ledger), but nothing ever writes the failure, so the
projection remains the one published by `WorkflowService.start` (`status = ready`), and `workflowActions` — which
derives blockers only from projection steps, interactions, attempts, cost and `oracle-result` evidence — has nothing
to report.

### Regression risk areas
- Every continuation re-runs the pre-check (start, result submission, human resume). A refusal in the middle of a run
  (agent disabled after step 1) must only fail `ready` steps and never touch `running`, `waiting_human` or terminal
  steps.
- Outcome-managed workflows: `outcomeTransitionService.initialize` now runs BEFORE the pre-check (change brought by
  WZ-36379). `setStatus(FAILED)` therefore calls `outcomeTransitionService.record(..., executionId, FAILED)` on a
  ledger entry in `ready` — accepted by `record`. `advance` on a later continuation only reacts to an accepted agent
  FAIL, so it ignores these failures. Do not call `advance` on the refusal path.
- `persistProgressProjection` reports `running` when `executions` is non-empty and a step failed; the final
  `persistProjection(..., sessionStatus)` of the common tail writes the authoritative `failed` status.
- The user-Stop path must remain strictly before the pre-check.

## 5. Scoped change

### Backend (implement first)

**`SessionRunService.kt`** (only file with logic change)
1. Import `io.whozoss.factory.workspace.WorkspacePrecheckException`.
2. In `runSessionLocked`, introduce `var precheckRefused = false` next to `runCancelled`. In the `else` branch, wrap
   ONLY the pre-check call:
   ```kotlin
   try { workspacePrecheckService?.precheck(...) }
   catch (refused: WorkspacePrecheckException) {
       failOnWorkspacePrecheck(scope, namespaceId, workflowId, steps, statuses, refused, expectedRevision)
       precheckRefused = true
   }
   if (!precheckRefused) { /* existing replay/resume prelude loop, unchanged */ }
   ```
   Do not catch any other exception type.
3. In the `run { ... }` block, extend the first guard: `if (runCancelled || precheckRefused) return@run`. The common
   tail (terminal status, `persistProjection`, `sseHub.publish` with revision, `runService?.onFragmentSessionUpdated`)
   then runs unchanged, so a parent Run fragment also learns the failure. `effectiveRepoRoot` stays `repoRoot`.
4. New private `failOnWorkspacePrecheck(scope, namespaceId, workflowId, steps, statuses: SessionProgress,
   refused, expectedRevision: () -> Int)`:
   - `logger.warn` once with `refused.errorCode` and `refused.message`.
   - Workflow-level evidence, appended inside `runCatching { newTransaction { ... } }` with `logger.error` on failure
     (a persistence error must never mask the cause):
     `WorkflowEvidenceItem(evidenceId = UUID, namespaceId, workflowId, stepId = null, kind = "workspace-precheck",
     outcome = "failed", source = mapOf("kind" to "factory-session-sequencer"), facts = precheckFacts(refused),
     idempotencyKey = "workspace-precheck-failed:$workflowId:" + CanonicalHash.sha256Hex(code + "|" + message),
     createdAt = null)`.
     `precheckFacts(refused)` = `(refused.details as? Map<*, *>).orEmpty().entries.associate { it.key.toString() to it.value }
     + mapOf("code" to refused.errorCode, "message" to (refused.message ?: refused.errorCode))` (code/message win over
     a colliding detail key). `append` returns an `EvidenceAppendResult` (idempotent replay or collision are not
     exceptions): ignore it.
   - For every step whose `statuses.statuses[step.id] == WorkflowStatuses.READY`: in one `newTransaction`, append a
     `session-step` FAILED evidence (`facts = stepId, status = failed, code = refused.errorCode, message`,
     `idempotencyKey = null`) — **without** an `executed` or `verification` fact (otherwise `codeDiagnostic()` in
     `phase-detail.ts` renders it as a refused code step) —, then `transition(..., WorkflowStatuses.FAILED,
     expectedRevision())` and `setStatus(..., WorkflowStatuses.FAILED, statuses)`. Same `runCatching` fallback as
     `recordStepFailure` (keep the in-memory `FAILED`).
   - Then `applyEvaluation(scope, namespaceId, workflowId, steps, statuses)` so dependants become `blocked`.
   - Steps in `pending`, `running`, `waiting_human`, `needs_research` or terminal statuses are left untouched.
5. Update the KDoc of the `workspacePrecheckService` constructor parameter: a refusal is now recorded durably and
   fails the ready steps instead of propagating.

**`WorkflowActionsModels.kt`**
- Add `const val WORKSPACE_PRECHECK_FAILED = "WORKSPACE_PRECHECK_FAILED"` to `WorkflowBlockerCodes`.
- Add `val details: String? = null` as the LAST field of `WorkflowBlockerDto` (default keeps every call site and
  test unchanged).

**`WorkflowService.workflowActions`**
- Extend the local `blocker(...)` helper with an optional `details: String? = null` parameter passed to the DTO.
- Next to the `oracle-result` block: `evidence.lastOrNull { it.kind == "workspace-precheck" && it.outcome == "failed" }`
  → if present and `runStatus != WorkflowStatuses.COMPLETED`, add
  `blocker(WORKSPACE_PRECHECK_FAILED, null, message, details = facts["code"] as? String)` where `message` =
  `facts["message"]` (fallback `"The workspace pre-check refused the run."`) + `facts["remedy"]?.let { " Remedy: $it" }`.
- The per-step `ATTEMPT_FAILED` blockers for the failed ready steps stay (they name the steps). No retry action
  appears for them (no durable attempt exists) — unchanged logic.

**`WorkstreamServiceController.blockerView`**
- Return the 3 existing keys plus `"details" to blocker.details` only when non-null.

**`factory-openapi.yaml`**
- `WorkflowBlockerDto.properties`: add `details: { type: string }` (not required).

### Contract between backend and frontend

`GET /api/factory/workflows/{workflowId}/actions` → `data.blockers[]` gains, for a refused run:

```json
{
  "code": "WORKSPACE_PRECHECK_FAILED",
  "stepId": null,
  "message": "Required agent(s) Reviewer are not available in namespace 'ns-1'. Remedy: Publish/enable the required agents in the namespace.",
  "details": "REQUIRED_AGENTS_MISSING"
}
```

Existing blockers now also serialise `"details": null` (harmless: `extractBlockers` ignores non-strings).
`GET .../workstream-service/workflows/{id}/blockers` → `items[]` with `code`/`stepId`/`message`, plus `details` when
non-null. `GET .../evidence` gains an item `kind = "workspace-precheck"`, `outcome = "failed"`, no `stepId`,
`facts = { code, message, remedy, missingAgents?, availableAgents?, namespaceId?, ... }`. Projection `status`
becomes `failed`; ready steps `failed`, dependants `blocked`.

**Implementation order:** backend (SessionRunService → models → workflowActions → controller → openapi) with its
tests, then the Cockpit (models → classification → action bar → run summary mapper → run card) with its specs.

### Out of scope (propose separate tickets)

- A RUNNING step whose attempt is finalized when a mid-run continuation is refused stays `running` (the replay
