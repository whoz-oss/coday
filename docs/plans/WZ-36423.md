# WZ-36423 — Surface workspace pre-check failures instead of leaving the run stuck in "Waiting"

> Source: Jira WZ-36423 (Bug, status **En cours** / In Progress; 3 technical pointers: handle the exception in
> `SessionRunService.runSessionLocked`, expose a blocker in `WorkflowService.workflowActions`, surface it in the
> Cockpit; no comments, no attachments, no links). Plan derived from the code at `7e91b7e22`
> (`workstream/forge/master`, the base commit of this worktree). Fresh start on a new branch requested by the user;
> it supersedes the plan-only drafts PR #1796 and PR #1799 (both closed without merge) and keeps the review notes
> made on #1796 (folded into section 5, see section 7).

## 1. Expected outcome

When the read-only workspace pre-check refuses a run (missing required agents, Git not configured, auto-worktree
disabled, unresolvable workstream...), the run ends `failed` with a durable, explainable reason that the Cockpit shows
on the session page (action bar + event log) and on the run card, instead of staying `ready` ("Waiting") forever.

**Type:** bug.

- **Observed:** in `SessionRunService.runSessionLocked`, the `workspacePrecheckService?.precheck(...)` call (in the
  non-cancelled `else` branch of `if (runCancelled)`) is not guarded. `WorkspacePrecheckException` escapes: no
  evidence, no step state change, no `persistProjection`, no `sseHub.publish`. `OutboxDrainWorker` catches it, marks
  the continuation dead and only logs a WARN. The projection keeps the `ready` status written by
  `WorkflowService.start`; `workflowActions` returns `blockers: []`.
- **Expected:** refusing the run is correct, but the reason is persisted (evidence), the ready step(s) and the run
  become `failed`, dependants `blocked`, the projection is refreshed and invalidated over SSE, and
  `GET .../actions` / `GET .../blockers` return an actionable blocker with the pre-check code, the message (missing
  agents) and the remedy.
- **Reproduction steps:** complete — launch any workflow whose agent step names an agent missing or disabled in the
  namespace (absent from `GET /api/agent-configs/by-parentId/{namespaceId}`).

## 2. Acceptance criteria

1. AC1 — When `precheck(...)` throws `WorkspacePrecheckException`, `runSessionLocked` does not let it escape. It
   records ONE durable `WorkflowEvidenceItem` `kind = "workspace-precheck"`, `outcome = "failed"`, `stepId = null`,
   `facts` = `code` (= `errorCode`), `message`, plus every `details` entry (`missingAgents`, `availableAgents`,
   `remedy`, `namespaceId`...). (ticket pointer 1)
2. AC2 — Every step `ready` at that moment becomes `failed` (session-step FAILED evidence + transition + step state);
   dependants become `blocked`; the run becomes `failed`; the projection is persisted and an SSE invalidation is
   published. (ticket pointer 1)
3. AC3 — `runSession` returns normally (`SessionRunResult.status == "failed"`), so the outbox continuation completes
   instead of going dead. No agent turn, no `prepareAgentWorkspace`, no `resolveAndRecord`, no worktree resolution,
   no replay/resume prelude, no `outcomeTransitionService.advance`. *(derived)*
4. AC4 — `WorkflowService.workflowActions` returns a blocker `code = "WORKSPACE_PRECHECK_FAILED"`, `stepId = null`,
   `message` = pre-check message + remedy, `details` = pre-check code (e.g. `REQUIRED_AGENTS_MISSING`). The same
   blocker (with `details`) is returned by `GET /api/factory/workstream-service/workflows/{id}/blockers` and in
   `get_workflow.blockers`. (ticket pointer 2)
5. AC5 — Cockpit: `<sf-action-bar>` shows the blocker in "Root failures" with its message and details; the run card
   shows the `failed` chip and the pre-check message; the session event log shows the pre-check evidence message.
   (ticket pointer 3)
6. AC6 *(derived)* — Idempotent replays: a second continuation hitting the same refusal appends no second
   `workspace-precheck` evidence and does not touch already terminal steps.
7. AC7 *(derived)* — Any other exception thrown by the pre-check propagates unchanged. The user-Stop path
   (`runCancelled`) is unchanged and still runs before and without the pre-check.

## 4. Code analysis

### Root cause (single)

`factory/factory-service/src/main/kotlin/io/whozoss/factory/workflow/service/SessionRunService.kt`,
`runSessionLocked`, `else` branch of `if (runCancelled)`: `workspacePrecheckService?.precheck(scope = ...,
requiredAgents = ..., requireGitWorkspace = requiresGitWorkspace)` is not wrapped. `WorkspacePrecheckException`
(`factory/factory-service/src/main/kotlin/io/whozoss/factory/workspace/WorkspacePrecheckException.kt`, a
`FactoryException` with `errorCode` and `details: Any?` — a `Map` in practice) unwinds through `runSession`, which
only catches `TransientWorkspaceAdoptionException`, to `OutboxDrainWorker`'s generic catch. `loadProgress` has
already written the root steps `ready` (and `outcomeTransitionService.initialize` the ledger), but nothing writes the
failure; `workflowActions` derives blockers only from projection steps, interactions, attempts, cost and
`oracle-result` evidence, so it has nothing to report.

### Regression risk areas
- Every continuation re-runs the pre-check (start, result submission, human resume). A mid-run refusal must only fail
  `ready` steps, never `running`, `waiting_human`, `needs_research` or terminal ones.
- Outcome-managed runs: `initialize` runs BEFORE the pre-check; `setStatus(FAILED)` records FAILED on a `ready`
  ledger entry (accepted by `OutcomeTransitionService.record`); `advance` only reacts to an accepted agent FAIL and
  must not be called on the refusal path.
- `persistProgressProjection` reports `running` when `executions` is non-empty and a step failed; the final
  `persistProjection(..., sessionStatus)` of the common tail writes the authoritative `failed`.
- The user-Stop path stays strictly before the pre-check.

## 5. Scoped change

### Backend (implement first)

**`SessionRunService.kt`** (only file with logic change)
1. Import `io.whozoss.factory.workspace.WorkspacePrecheckException`.
2. In `runSessionLocked`, add `var precheckRefused = false` next to `runCancelled`. In the `else` branch wrap ONLY
   the pre-check call:
   ```kotlin
   try { workspacePrecheckService?.precheck(...) }
   catch (refused: WorkspacePrecheckException) {
       failOnWorkspacePrecheck(scope, namespaceId, workflowId, steps, statuses, refused, expectedRevision)
       precheckRefused = true
   }
   if (!precheckRefused) { /* existing replay/resume prelude loop, unchanged */ }
   ```
   Catch no other exception type. Do NOT move the pre-check above `initialize` / `loadProgress` /
   `sealUserCancelledSteps`.
3. In `run { ... }`, the first guard becomes `if (runCancelled || precheckRefused) return@run`. The common tail runs
   unchanged (terminal status, `persistProjection`, `sseHub.publish` with revision, `onFragmentSessionUpdated`).
4. New private `failOnWorkspacePrecheck(scope, namespaceId, workflowId, steps, statuses: SessionProgress, refused,
   expectedRevision: () -> Int)`:
   - one `logger.warn` with `refused.errorCode` and `refused.message`;
   - workflow-level evidence inside `runCatching { newTransaction { ... } }` (`logger.error` on failure — a
     persistence error never masks the cause): `WorkflowEvidenceItem(evidenceId = UUID, namespaceId, workflowId,
     stepId = null, kind = "workspace-precheck", outcome = "failed", source = mapOf("kind" to
     "factory-session-sequencer"), facts = precheckFacts(refused), idempotencyKey = "workspace-precheck-failed:" +
     workflowId + ":" + CanonicalHash.sha256Hex(code + "|" + message), createdAt = null)`, with
     `precheckFacts = (details as? Map<*, *>).orEmpty().entries.associate { it.key.toString() to it.value } +
     mapOf("code" to errorCode, "message" to (message ?: errorCode))` (code/message win). The `EvidenceAppendResult`
     (idempotent replay / collision) is ignored;
   - for every step with `statuses.statuses[step.id] == WorkflowStatuses.READY`: in one `newTransaction`, append a
     `session-step` FAILED evidence whose facts are exactly `stepId`, `status = failed`, `code = errorCode`,
     `message` — **never `executed` nor `verification`** (else `codeDiagnostic()` renders a refused code step) —,
     `idempotencyKey = null`; then `transition(..., FAILED, expectedRevision())` and `setStatus(..., FAILED, statuses)`;
     same `runCatching` fallback as `recordStepFailure` (keep the in-memory `FAILED` + `completedAt`);
   - then `applyEvaluation(scope, namespaceId, workflowId, steps, statuses)` so dependants become `blocked`.
5. Update the KDoc of the `workspacePrecheckService` constructor parameter: a refusal is recorded durably and fails
   the ready steps instead of propagating.

**`WorkflowActionsModels.kt`**
- `const val WORKSPACE_PRECHECK_FAILED = "WORKSPACE_PRECHECK_FAILED"` in `WorkflowBlockerCodes` (with a KDoc line).
- `val details: String? = null` as the LAST field of `WorkflowBlockerDto` (+ KDoc); defaults keep all call sites.

**`WorkflowService.workflowActions`**
- The local `blocker(...)` helper gains `details: String? = null`, passed to the DTO.
- Next to the `oracle-result` block: `evidence.lastOrNull { it.kind == "workspace-precheck" && it.outcome == "failed" }`
  → when present and `runStatus != WorkflowStatuses.COMPLETED`: `blocker(WORKSPACE_PRECHECK_FAILED, null, message,
  details = facts["code"] as? String)` with `message = (facts["message"] as? String ?: "The workspace pre-check
  refused the run.") + ((facts["remedy"] as? String)?.let { " Remedy: $it" } ?: "")`.
- Per-step `ATTEMPT_FAILED` blockers for the failed ready steps stay; no retry action appears (no durable attempt).

**`WorkstreamServiceController.blockerView`** — the 3 existing keys, plus `"details" to blocker.details` only when
non-null.

**`factory-openapi.yaml`** — `WorkflowBlockerDto.properties.details: { type: string }` (not required).

### Contract between backend and frontend

`GET /api/factory/workflows/{workflowId}/actions` → `data.blockers[]` gains, for a refused run:

```json
{
  "code": "WORKSPACE_PRECHECK_FAILED",
  "stepId": null,
  "message": "Required agent(s) Reviewer are not available in namespace 'ns-1'. Remedy: Publish/enable the required agents in the namespace.",
  "details": "REQUIRED_AGENTS_MISSING"
}
```

Other blockers now serialise `"details": null` (harmless: `extractBlockers` ignores non-strings).
`GET .../workstream-service/workflows/{id}/blockers` → `items[]` with `code` / `stepId` / `message`, plus `details`
when non-null. `GET .../evidence` gains `kind = "workspace-precheck"`, `outcome = "failed"`, no `stepId`,
`facts = { code, message, remedy?, missingAgents?, availableAgents?, namespaceId?, ... }`. Projection `status` =
`failed`; ready steps `failed`, dependants `blocked`.

**Implementation order:** backend (SessionRunService → models → workflowActions → controller → openapi) with its
tests, then the Cockpit (models → classification → action bar → run summary mapper → run card) with its specs.

### Out of scope (separate tickets to propose)

- Running the pre-check synchronously in `WorkflowService.start` to refuse the launch with a 422.
- A RUNNING step whose attempt is finalized when a mid-run continuation is refused stays `running` (prelude skipped):
  same as today, not made worse.
- Rendering `details` for every blocker group in the action bar.
