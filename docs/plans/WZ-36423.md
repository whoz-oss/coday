# WZ-36423 — Surface workspace pre-check failures instead of leaving the run stuck in "Waiting"

> Source: ticket content supplied by the reporter in the Factory session (the Jira API returned 404 for WZ-36423 with the
> available credentials, so the ticket could not be read or transitioned from the agent side).

## 1. Expected outcome

When the read-only workspace pre-check refuses a run (missing agents, Git not configured, auto-worktree disabled,
unresolvable workstream...), the run stops in the `failed` state with a durable, explainable reason that the Cockpit shows
on the session page (action bar + event log) and on the run card, instead of staying in `ready` ("Waiting") forever.

**Type:** bug.

- **Observed:** `SessionRunService.runSessionLocked` calls `workspacePrecheckService?.precheck(...)` before `loadProgress`
  and the step loop. The `WorkspacePrecheckException` escapes the method: no evidence, no step state, no
  `persistProjection`, no `sseHub.publish`. `OutboxDrainWorker.executeContinuation` catches it, calls
  `deferContinuation(..., transient = false)` (the continuation goes dead) and only logs a WARN. The projection keeps the
  `ready` status written by `WorkflowService.start`, and `workflowActions` returns `blockers: []`.
- **Expected:** blocking the run is correct, but the reason is persisted (evidence), the run and its ready step(s) become
  `failed`, the projection is refreshed and invalidated over SSE, and `GET .../actions` / `GET .../blockers` return an
  actionable blocker carrying the error code, the message (missing agents) and the remedy.
- **Reproduction steps:** complete — launch any workflow whose agent step names an agent that does not exist / is disabled in
  the namespace (`GET /api/agent-configs/by-parentId/{namespaceId}` does not return it).

## 2. Acceptance criteria

1. AC1 — When `precheck(...)` throws `WorkspacePrecheckException`, `runSessionLocked` does not let it escape: it records
   ONE durable `WorkflowEvidenceItem` with `kind = "workspace-precheck"`, `outcome = "failed"`, `stepId = null`, and
   `facts` containing `code` (= `errorCode`), `message`, `remedy` and the other `details` entries (`missingAgents`,
   `availableAgents`, `namespaceId`, `checkoutStatus`, `failureReason`... whatever the exception carries).
2. AC2 — Every step that is `ready` at that moment (on a first run: the root steps) becomes `failed` (step state +
   `session-step` FAILED evidence + transition); its dependants become `blocked` through the normal evaluation; the
   workflow status becomes `failed`; the projection is persisted and an SSE invalidation is published.
3. AC3 — `runSession` returns normally (`SessionRunResult.status == "failed"`), so the outbox continuation is completed
   instead of going dead; no agent turn, no root case, no worktree, no outcome-ledger initialisation happens.
4. AC4 — `WorkflowService.workflowActions` returns a blocker `code = "WORKSPACE_PRECHECK_FAILED"`, `stepId = null`, a
   `message` that contains the pre-check message (listing the missing agents) and the remedy, and `details` carrying the
   pre-check error code (e.g. `REQUIRED_AGENTS_MISSING`). The same blocker is returned by
   `GET /api/factory/workstream-service/workflows/{workflowId}/blockers`.
5. AC5 — Cockpit: `<sf-action-bar>` shows the blocker in the "Root failures" group with its message and details; the run
   card shows the `failed` chip and the pre-check message; the session event log shows the pre-check evidence message.
6. AC6 (derived) — Replays are idempotent: a second continuation that hits the same pre-check failure does not append a
   second identical `workspace-precheck` evidence (idempotency key) and does not re-fail already terminal steps.
7. AC7 (derived) — Non-precheck exceptions keep their current behaviour (unchanged propagation to the worker).

## 4. Code analysis

### Root cause (single)

`factory/factory-service/src/main/kotlin/io/whozoss/factory/workflow/service/SessionRunService.kt`, in
`runSessionLocked`, the call

```kotlin
workspacePrecheckService?.precheck(scope = scope, namespaceId = namespaceId, ..., requiredAgents = ..., requireGitWorkspace = ...)
```

is placed before `loadProgress(...)` and is not wrapped. `WorkspacePrecheckException`
(`factory/.../workspace/WorkspacePrecheckException.kt`, a `FactoryException` with `errorCode` + `details`) therefore
unwinds through `runSession` (which only catches `TransientWorkspaceAdoptionException`) to
`OutboxDrainWorker.executeContinuation` (`factory/.../agentattempt/service/OutboxDrainWorker.kt`), whose generic catch
defers the continuation as non-transient (dead) and logs. Nothing ever writes the failure into the workflow state, so the
projection remains the one published by `WorkflowService.start` (`status = ready`), and `workflowActions` — which derives
blockers only from projection steps, interactions, attempts, cost and `oracle-result` evidence — has nothing to report.

### Regression risk areas
- Every continuation re-runs the pre-check (start, result submission, human resume). A pre-check failure in the middle of
  a run (agent disabled after step 1) must only fail the `ready` steps and never touch `running` / terminal steps.
- Outcome-managed workflows (`outcomeTransitions`): the ledger is initialised after the pre-check; the failure path must
  return before `outcomeTransitionService.initialize(...)`. `setStatus` → `outcomeTransitionService.record` is a no-op
  without `executionId`, so it is safe.
- `persistProgressProjection` reports `running` when `executions` is non-empty and a step failed (FAIL-return budget);
  the final `persistProjection(..., sessionStatus)` call writes the authoritative terminal status.

## 5. Scoped change

### Backend (implement first)

**`SessionRunService.kt`**
1. Wrap only the pre-check call:
   ```kotlin
   try { workspacePrecheckService?.precheck(...) }
   catch (refused: WorkspacePrecheckException) {
       return failOnWorkspacePrecheck(scope, namespaceId, workflowId, steps, refused, expectedRevision, effectiveTicket, repoRoot)
   }
   ```
   (import `io.whozoss.factory.workspace.WorkspacePrecheckException`). Do not catch anything else.
2. New private `failOnWorkspacePrecheck(...)`: 
   - `logger.warn` once with code + message.
   - Append the workflow-level evidence (inside `newTransaction { }` like the other failure writers, wrapped in
     `runCatching` + `logger.error` like `recordStepFailure` so a persistence error never masks the cause):
     `WorkflowEvidenceItem(evidenceId = UUID, namespaceId, workflowId, stepId = null, kind = "workspace-precheck",
     outcome = "failed", source = mapOf("kind" to "factory-session-sequencer"), facts = precheckFacts(refused),
     idempotencyKey = "workspace-precheck-failed:$workflowId:${CanonicalHash.sha256Hex(code + "|" + message)}", createdAt = null)`.
     `precheckFacts` = `mapOf("code" to refused.errorCode, "message" to refused.message) + (refused.details as? Map<*,*>)
     .orEmpty().mapKeys { it.key.toString() }` (code/message win over a colliding detail key). An idempotent replay or a
     collision result is simply ignored (append returns a result, it does not throw).
   - `val progress = loadProgress(scope, namespaceId, workflowId, steps)` (initialises root steps to `ready` on a first run,
     reads durable states otherwise).
   - For every step whose status is `READY`: in one `newTransaction`, append a `session-step` FAILED evidence
     (`facts = stepId, status = failed, code = refused.errorCode, message = refused.message`; do **not** put an `executed`
     fact — the Cockpit treats it as a code diagnostic), `transition(..., WorkflowStatuses.FAILED, expectedRevision())`
     and `setStatus(..., WorkflowStatuses.FAILED, progress)`. Reuse the `recordStepFailure` shape (extract a small shared
     helper only if it avoids duplication without changing existing behaviour).
   - `applyEvaluation(scope, namespaceId, workflowId, steps, progress)` so dependants become `blocked`.
   - `val status = SessionSequencer.terminalStatus(steps, progress.statuses)`;
     `persistProjection(scope, namespaceId, workflowId, steps, progress, status, ticket)`; `sseHub.publish(...)` with the
     committed revision (same block as the end of `runSessionLocked`).
   - Return `SessionRunResult(namespaceId, workflowId, status, statusesOf(steps, progress.statuses))`. Call
     `runService?.onFragmentSessionUpdated(...)` exactly as the normal exit does, so a parent Run fragment also learns
     the failure.
   - Steps in `running`, `waiting_human` or terminal statuses are left untouched.
3. Update the KDoc of the `workspacePrecheckService` constructor parameter: a refusal is now recorded durably and fails
   the ready steps instead of propagating.

**`WorkflowActionsModels.kt`**
- Add `const val WORKSPACE_PRECHECK_FAILED = "WORKSPACE_PRECHECK_FAILED"` to `WorkflowBlockerCodes`.
- Add an optional `val details: String? = null` to `WorkflowBlockerDto` (default keeps every existing call site and
  test unchanged).

**`WorkflowService.workflowActions`**
- Next to the `oracle-result` block, take `evidence.lastOrNull { it.kind == "workspace-precheck" && it.outcome == "failed" }`
  and add (through the local `blocker(...)` dedup, extend it with an optional `details` parameter):
  `WorkflowBlockerDto(code = WORKSPACE_PRECHECK_FAILED, stepId = null, message = "<facts.message>" + (facts.remedy?.let { " Remedy: $it" } ?: ""), details = facts.code as? String)`.
  Only emit it while the run is not `completed` (a later successful run of the same workflow id cannot exist, but keep the
  guard cheap: `runStatus != WorkflowStatuses.COMPLETED`).
- The per-step `ATTEMPT_FAILED` blocker for the failed ready steps stays as is (it names the step). No retry action is
  offered (no durable attempt exists) — unchanged logic.

**`WorkstreamServiceController.blockerView`**
- Add `"details" to blocker.details` only when non-null (keep the existing 3 keys otherwise).

### Frontend (implement second)

**`core/models.ts`** — add `'WORKSPACE_PRECHECK_FAILED'` to `BlockerCode`; add optional `failureReason?: string` to
`RunSummary`.

**`core/blocker-classification.ts`** — `case 'WORKSPACE_PRECHECK_FAILED': return 'failure'` (root failure group, `error`
icon); update the KDoc list.

**`features/session/action-bar/action-bar.component.html` / `.scss`** — in the failure group (and only there, to keep
the change small), render `blocker.details` when present as a secondary mono line
(`<span class="blocker-details sf-mono">{{ blocker.details }}</span>` inside `.blocker-body`). The label already carries
the backend message (missing agents + remedy) through `extractBlockers`.

**`core/mappers/workflow.ts`** — in the run-summary mapping (near `summary.cardState = ...`), set
`summary.failureReason` to the `label` of the first blocker with code `WORKSPACE_PRECHECK_FAILED` of the detail, if any.
`cardState` needs no change: it becomes `failed` from `detail.status`.

**`features/workstreams/run-card/run-card.component.html` / `.scss`** — under the header, when
`r.run?.failureReason` is set, render one line `<p class="failure-reason" role="status">{{ r.run.failureReason }}</p>`
(ellipsis on overflow, full text in `title`).

**Event log** — no code change: `mapEvidenceToEvents` already emits a `log` event whose text is `facts.message` for the
`workspace-precheck` evidence (global view) and for the step `session-step` FAILED evidence (step view). Covered by a test.

### Contract between backend and frontend

`GET /api/factory/workflows/{workflowId}/actions` → `data.blockers[]` gains, for a refused run:

```json
{
  "code": "WORKSPACE_PRECHECK_FAILED",
  "stepId": null,
  "message": "Required agent(s) Reviewer are not available in namespace 'ns-1'. Remedy: Publish/enable the required agents in the namespace.",
  "details": "REQUIRED_AGENTS_MISSING"
}
```

Existing blockers now also serialise `"details": null` (harmless; `extractBlockers` ignores non-strings).
`GET .../workstream-service/workflows/{id}/blockers` → `items[]` with the same `code`/`stepId`/`message` and `details`
when non-null. Evidence (`GET .../evidence`) gains an item `kind = "workspace-precheck"`, `outcome = "failed"`, no
`stepId`, `facts = { code, message, remedy, missingAgents?, availableAgents?, namespaceId?, ... }`. Projection
`status` becomes `failed`; ready steps `failed`, dependants `blocked`.

**Implementation order:** backend (SessionRunService → models → workflowActions → controller) with its tests, then the
Cockpit changes with their specs.

### Out of scope (propose separate tickets)
- A governed "re-run after fixing the namespace" action for a pre-check-refused run (today the operator relaunches).
- Running the pre-check synchronously in `WorkflowService.start` to refuse the launch with a 422 before any instance is
  created.
- Rendering `details` for every blocker group in the action bar.
