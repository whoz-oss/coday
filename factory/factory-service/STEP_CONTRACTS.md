# Explicit workflow step contracts (WZ-36102)

A workflow step may declare an ordered, human-readable work contract alongside its existing identity, responsibility and dependencies:

```json
{
  "id": "implement",
  "name": "Implement the requested change",
  "responsibility": { "kind": "agent", "name": "Dev" },
  "dependsOn": ["initialize-branch"],
  "entry": ["Inspect and sync the authorized branch before writing using AgentOS tools."],
  "mission": "Implement only the authorized request, following the project's AgentOS skills.",
  "exit": ["Commit scoped changes and push before reporting success.", "Report exact checks and commit evidence."]
}
```

`entry` is preparation before the mission, not a DAG dependency predicate. `mission` is the step's work, not an agent persona or a template. `exit` describes completion obligations and deliverables. These are prose obligations for the executor, **not machine-verified predicates**. For a human or code step the prose documents intent; it does not add agent execution or alter the existing approval/verifier semantics. Never place secrets in these operator-visible fields or the user request.

All three fields must be supplied together. `mission` must be nonblank, at most 16,000 characters. `entry` and `exit` are ordered arrays (possibly empty), at most 50 nonblank strings each, at most 4,000 characters per string. Unknown step fields remain rejected; nulls, partial contracts and wrong types are invalid. Order is preserved by normalization and hashing. The same contract is retained in workflow projections.

## Mandate assembly and ownership

For explicit agent steps Factory assembles the actual turn text in this order:

1. Original user request, current step identity and scope, ticket context and durable dependency inputs/run-brief handoff when present.
2. Entry / Preparation, Mission, Exit / Deliverables, in declared order.
3. Existing context contributions from configured plugins, when present.
4. Factory execution protocol: clarification continuation, `FACTORY_WORKER__submitStepResult`, Factory-generated `attemptId` and submission idempotency key, structured payload/schema correction, PASS/FAIL/NEEDS_RESEARCH and stopping after acceptance.

An explicit contract bypasses the legacy name-based Gitay brief and inferred entry-step framing/deliverable instructions. It does not change dependency scheduling, approvals, trusted workspace binding, result capability issuance, result validation, configured plugin validators or oracle checks. Prose cannot turn off those controls. Plugin contributions retain their existing extension semantics and should supply context rather than duplicate workflow business instructions. Reusable work conventions belong in AgentOS skills, not in Factory's mandate renderer.

The rendered mandate (including resolved attempt identifiers) is frozen in the existing durable attempt `brief` and reused unchanged during replay. A new attempt remains a separate record. The authenticated, tenant/namespace-scoped attempt read surface exposes this turn text as `effectiveMandate` once `startedAt` exists; it does not expose capability tokens, leases or the raw context envelope. This is the payload used by dispatch, not proof that the remote agent received or fulfilled every obligation (an interrupted/ambiguous dispatch remains governed by the existing recovery protocol). It includes user/dependency content, so treat it with the same confidentiality as the run. No truncation or reconstruction from a later workflow definition is used.

The cockpit definition page shows a read-only dependency diagram. Select a node (native keyboard-accessible button) to edit **Pre-actions / Prompt / Post-actions**, mapped internally to `entry` / `mission` / `exit`. Actions are individually editable multiline text, not newline-parsed JSON. There is no topology editor, drag/drop, or required global JSON editing; JSON remains a read-only reference. Agent prompts replace legacy business instructions, not Factory authorization, result submission or validation. Human/code contracts only document intent and do not replace approval/verifier implementation. The session phase detail shows that configuration and the frozen effective mandate for the **selected attempt**, including older retries. Missing/legacy or not-yet-dispatched mandate data is explicitly unavailable, never synthesized from configuration. Plain-text interpolation preserves line breaks without executing HTML.

## Compatibility and adoption

Schema version remains `1`. Steps omitting **all three** fields remain legacy steps: normalization injects no new keys, preserving their canonical definition shape/hash. They retain historical root-step clarification/run-brief framing, downstream handoff preservation, inferred deliverable guidance, special Gitay/A11y instructions and existing plugin contributions. Existing persisted attempts replay their frozen brief without regeneration. No stored definition or bundled catalog is silently rewritten.

Adopt explicit contracts deliberately by registering a new workflow version with all three fields on each agent step being migrated. Specify the needed business framing, artifact/handoff preservation, review scope and deliverables in those fields rather than relying on inferred root position or persona name. Do not change a definition used by an active run: existing hash mismatch protections still apply. Warning: omitting a required handoff/artifact obligation is not a validation error; authors must state it explicitly. Factory can relay an existing ancestor run-brief, but prose validation does not prove that an agent produced or preserved the required artifact. Empty arrays mean no additional preparation/exit prose, not a request for legacy defaults. This opt-in compatibility lane is intentional; removal/migration of all legacy defaults is not part of this change.

## Illustrative Git checkpoint workflow — agent obligations only

The validated fixture is `src/test/resources/workflows/git-checkpoint-contract.json`. It is intentionally not seeded into production. It declares two dependent **agent** steps: initialize an authorized branch before any writing, then inspect/sync on entry, perform scoped work, commit and push before success, and report durable evidence. AgentOS agents use existing AgentOS Git tools and skills. Factory does not execute Git operations from `entry`/`exit`, parse them as commands, add a Git adapter or implement checkpoint verification. Actual Git checkpoints belong to parent WZ-36049 and remain out of scope. A prose instruction to push is not proof that a remote branch exists; a PASS is still subject only to the existing structured result and explicitly configured validators.

## Cockpit editing and safe persistence

Open **Workflows → a definition → a diagram node**. Editing creates a page-local draft; selecting another step keeps the draft. Blank prompts/actions and the contract size bounds are validated before save. Remove an action rather than leaving it blank; empty action lists are allowed. Discard removes all drafts. Navigation/browser-unload guards warn about unsaved work; saving locks editing and navigation. API errors retain drafts, and success reports the server-computed hash.

Save registers a **new version of the same workflow type** using the existing JSON POST endpoint with `If-None-Match: *`. This optional precondition is enforced by an atomic Neo4j MERGE with ON CREATE assignments under the existing unique definition-id constraint: an existing identity returns 409 `WORKFLOW_DEFINITION_ALREADY_EXISTS` and is never updated, even under concurrent editor saves. Unsupported precondition values return 400. JSON registration and multipart upload without this header also reject replacement with different content (409); identical re-registration remains accepted. This intentional HTTP compatibility tightening closes the old overwrite path behind pinned runs. Internal bootstrap APIs are unchanged. No schema migration is involved. Only changed steps' contract fields and the new version are replaced; ids, dependencies, responsibility, other step fields, execution/plugin configuration and untouched steps are preserved. The source definition/hash and pinned runs are unchanged. This is not a global lock on internal repository writers or the pre-existing delete API.

**Explicit launch selection:** the Launch page lists each `workflowType@version` with its hash prefix, not collapsed workflow types. When several definitions are available, no option is auto-selected. The canonical `POST /api/factory/workflows` accepts `definitionVersion` and `definitionHash` together with `workflowType`; Factory resolves the exact organization-owned record and checks the canonical hash before creating or submitting the run. Partial/malformed references return 400, missing/foreign versions 404, stale hashes 409 `WORKFLOW_DEFINITION_MISMATCH`. No automatic latest selection or type renaming is introduced. New versions can therefore coexist and launch independently. Existing runs retain their pinned version/hash; retrying an existing creation resolves that pin, and changing its selection conflicts. Compatibility callers without a selection still work for a unique type; a new run with several candidates fails explicitly rather than choosing silently. Use the canonical endpoint and explicit pair for multi-version types. Do not delete definitions required by existing runs. After save the editor holds the newly registered version; its route remains the original source URL, so reloading that URL opens the original source again. The registered new version is reachable from the Workflows list.

Legacy steps are never displayed as an empty editable prompt. The panel explains hidden position/name-derived instructions and points to a dispatched attempt's frozen mandate for exact runtime text. **Adopt explicit instructions** is deliberate and available for generic agent steps only: it copies clarification/framing, root run-brief creation or downstream unchanged handoff preservation, and analysis/implementation/review deliverable obligations into editable actions. The initial prompt is the step name, not a claimed extraction of a hidden custom business prompt; the author must review/refine it. Other steps remain legacy. Plugin contributions and the technical result protocol remain assembled by Factory.

Automatic adoption of **Gitay** and **A11yReviewer** is blocked: their branch selection/tool constraints and authoritative PR file/range/fail-closed scope are runtime-derived and currently bypassed by explicit contracts. Safely migrating those requires separating that runtime context from legacy business prose in the backend; copying a static prompt would silently lose obligations. Legacy human/code steps also remain read-only rather than suggesting that static prose changes their execution. No catalog definition is silently migrated.

Full agent CRUD tools for workflow definitions and full graph **topology** editing remain followups; the per-step property editor and clickable diagram are now in scope and implemented. PR creation, review/merge automation and Git checkpoint automation are not implemented here.

## Explicit conditional routing

Steps optionally declare `decision: {"mode":"single|multiple","routes":[{"name":"frontend","target":"implement-front"},{"name":"backend","target":"implement-back"}]}`; the convergence step declares `join: "architect"` and lists every target in `dependsOn`. One group, 2–16 unique names/distinct targets, and single-step branches only: each target depends only on the decision and feeds only the join. Nested/overlapping/multi-step topologies are rejected. Extra join dependencies retain ordinary AND semantics. Schema remains 1, with no keys injected into legacy definitions or hashes.

Decisions must be agent steps. The standard worker result tool submits `selectedRoutes` separately from PASS/FAIL/NEEDS_RESEARCH, only on PASS of a decision. Missing/unknown/duplicate/out-of-mode selections are rejected. Fullstack selects `["frontend","backend"]`. After capability validators and auto-oracles succeed, Factory atomically persists the result ID/hash, attempt ID, selected route names, decision completion and target activation/skip before dispatching a branch. Nonselected steps are skipped with executed=false, not successful capability executions. Only the explicit join may consume those skips; every selected branch must complete successfully. Human/research waits do not satisfy it. Execution stays sequential.

Recovery fails closed if completed decision activation is missing or a recovered success lacks durable validator acceptance proof. It never guesses routes or treats a bare submitted PASS as proof that validators ran. These cases require diagnosis rather than silent rerouting. A normal restart after committed activation reuses durable state without selecting again.
